# Design System: SillyBunny

## 1. Overview

**"Simple by default, powerful when needed"**

SillyBunny is an LLM roleplay client that best embodies the HIG (human interface guidelines) of the GNOME project. Although great inspiration is taken from this project, SillyBunny still stands on its own with its own personality and branding based on its focus on roleplay and storywriting. The shell is deliberately kept out of the way so the user can focus on the main content until configuration and navigation are needed.

Intuitive wording, tactile and easily glanceable feedback, and deliberate purpose define the shell. Complex configuration remains available to the user if they wish to seek it (as per upstream SillyTavern), but a good default experience is mandatory and implied - the goal is for a new user to navigate the shell with minimal to no difficulty. Configuration remains behind the shell at all times until called for. All elements of the shell must remain themeable with user CSS themes, and be fully compatible with SillyTavern data, presets, extensions, and settings.

The design philosophies of the GNOME project and its HIG should always be taken into consideration. This means accessibility through lack of distractions, animations that guide the user to what is clicked/tapped, responsive layouts, predictable touch targets, and nothing getting in the way of the main user experience. Mobile design must remain purposefully designed alongside the desktop, adapting libadwaita to a smaller and more touch-heavy window.

With this in mind, SillyBunny can inject its own fun in the design too. After all, it is a roleplay and storywriting client at heart.

This project rejects UI creep, nested menu spirals, configuration sprawl, screen bloat, mystery meat navigation, desktop-only assumptions, and generic SaaS polish.

**Key Characteristics:**
- Content-first main area with no unsolicited permanent configuration panels.
- Familiar controls that disclose depth through deliberate input, not visual noise.
- Guided animations that promote accessibility and intuitive motion.
- Stable desktop and mobile interaction vocabulary, safe shell behaviour for WebKit, Gecko, and Chromium browsers.
- Personality expressed through usefulness.

## 2. Colours

The palette is a neutral base for customisation and exploration: the accent dictates user interaction. Values follow the libadwaita dark style (the bundled Libadwaita Dark theme); Libadwaita Light maps the same roles onto the libadwaita light style. Every role below is derived from the user's theme colours, so the hex values describe the bundled Libadwaita Dark theme only.

Deviation: the HIG asks an app to follow the system's light or dark style; SillyBunny applies the theme the user saved and defaults to the dark bundled theme, because themes are user data and the app has no system-following mode. Review when the app gains a mode that follows the system's style.

### Primary
- **Accent** (`#b1e2ff` dark, `#16508b` light): `--sb-accent`, a 62/38 mix of the theme quote colour and body colour. The bundled quote colour is `#81d0ff` (dark) and `#0461be` (light). Used for suggested actions, checked checkboxes and radios, the range thumb, and the selected-item icon. Use it as a signal, never as ambient ornament.
- **On Accent** (`--sb-on-accent` / `--sb-on-solid-accent`): Text and glyphs on a solid accent fill. Black on the bundled dark theme and white on the bundled light theme. Deviation: libadwaita always uses white on `#3584e4` (about 3.8:1); SillyBunny picks the ink that reaches 4.5:1, because text on a solid accent fill must stay readable. Review when libadwaita changes this value.
- **Soft Accent** (`#9ab9cd` dark, `#395e86` light): Secondary accent for quiet helper states and badges. Selected backgrounds use neutral fills, not Soft Accent.
- **Link:** A link is Accent and underlined. Visited, it is Accent mixed 80% with the View ink; on hover its saturation and lightness are each multiplied by `1.1`; pressed, it returns to Accent; disabled, it takes the disabled strength. On a dark overlay (a tooltip) a link is Accent mixed 50% with white, visited 75%; a toast and an in-app notification are on the Popover layer, not a dark overlay, so a link in them takes the colours above. The underline stays, so a link never relies on colour alone.
- **Text selection:** Selected text sits on the View ink at 10%; in the field that has focus it sits on Accent at 30%.

### Secondary
These are libadwaita's standalone status colours. The light style uses `#007c3d`, `#c30000`, and `#905400`, switched by `data-sb-surface-tone='light'`.
- **Success Green** (`#78e9ab`): Positive completion and healthy connection feedback. It must not compete with Accent for primary actions.
- **Destructive Red** (`#ff938c`): Destructive actions and errors that require attention.
- **Warning Yellow** (`#ffc252`): Caution and transient operational warnings.

A layer that names a libadwaita role renders that role's colour on the bundled themes. A layer with no role keeps the value its mix gives on the bundled themes; their BlurTint and ChatTint carry 0.9 alpha, which `color-mix()` takes into account before the layer is forced opaque, so such mixes come out a few steps lighter than the same mix of opaque colours (checked in Chromium, 2026-10-19). The mixes of the layers with a role are chosen for that alpha.

- **The content surface** is the raw chat tint on mobile (upstream's rule) and `--sb-chat-view-bg` on desktop, so the bundled 0.9 tints stay opaque and lower tints show the background. The window background behind the content mixes BlurTint toward Body, so the main window stays distinct from the canvas in every theme.
- **Bars:** a bar is flat and recedes, so messages and lists carry the visual weight; do not raise it into a heavier, toolbar-style band. The top bar uses Header bar, and the composers and bottom bar use Bottom bar, which takes the header bar fill as libadwaita's bottom bars do. Where two layers share a colour, as a bar and the View do in the light tone, the `1px` shade line separates them, as in libadwaita.
- **Overlays:** shell drawers continue the top bar and separate from the view by tone and one overlay shadow. Popovers, menus, in-app notifications, and alerts use the Popover and Alert layers, a step lighter than the Canvas in the dark tone; dialogs and windows use the Window layer, as `AdwDialog` does. Each separates from what is behind it by its edge and overlay shadow. In the light tone these layers are the lightest and rely on that edge and shade.
- **Raised Panel** (`#38383c`) and **Hover Panel** (`#434347`) are `--sb-raised-bg` (10%) and `--sb-raised-hover-bg` (15%) over Window. Raised Panel is a control fill, not a layer.
- **Foreground** (`#ffffff`) and **Dim Foreground** (`#9c9c9d`, `--sb-muted-fg`): 55% of the body colour on the dark tone, as libadwaita's `.dimmed`, and 74% on the light tone (see Typography). Under `prefers-contrast: more` dim text is 90% on both tones. Dim text is never the sole carrier of meaning.
- **Strengths:** Lines, dimmed content, disabled controls and troughs are the body colour at a fixed strength, so they follow every theme. Each value has a stronger one under `prefers-contrast: more`. These are libadwaita's values unless a deviation says otherwise. Existing surfaces move to the high-contrast strengths as each surface is rebuilt.
- **Border and separator:** `1px`, 15%; under `prefers-contrast: more`, 50% of the body colour, as libadwaita draws it. Deviation: libadwaita draws a border as the text colour at this strength; SillyBunny draws it in the theme's border colour at the normal contrast, because the border colour is part of the user's theme (The Theme Alias Rule). Review when libadwaita changes this value.
- **Disabled:** 50% opacity; under `prefers-contrast: more`, 40%, so a disabled control stays distinct from the stronger enabled one. An icon or label inside an already faded control (a toggle, the edit icon of an entry row) fades again to 30%.
- **Quiet marks:** Indicators and separators inside menus are 30%; under `prefers-contrast: more`, 80%.
- **Trough:** 15%, 20% on hover, 25% pressed; under `prefers-contrast: more`, 30%, 40% and 50%. The outline of a checkbox or radio is a `2px` ring at the trough strength; under `prefers-contrast: more` it takes the border strength.
- **Window outline:** a dialog or sheet edge is a `1px` ring of white at 7%; under `prefers-contrast: more`, 30%.
- **Shadow Ink** (`#000006`): Shade and shadow tint only. Never a text colour.
- **Texture:** An opt-in texture or background image over the canvas and content surface. It takes its colours from the active theme and never overrides border or message tints. Deviation: the HIG advises against text over textures or graphical backgrounds; SillyBunny allows an opt-in texture or background image, because the user chooses it and it must still meet the Contrast Rule. Review when the HIG changes this advice.

### Named Rules
**The Signal Scarcity Rule.** Accent appears for action, selection, focus, or meaningful state. If removing it does not reduce comprehension, remove it.

**The Theme Alias Rule.** New work consumes `SmartTheme*`, `color-*`, `sb-*`, spacing, and radius aliases. Do not hard-code a new color that bypasses saved user themes. `white` and `black` may be mixed into a theme colour with `color-mix()` to lighten or darken it, as libadwaita's stylesheet does; there they are operands, not colours of their own. Deviation: the HIG asks for style variables rather than fixed colours; SillyBunny lets an illustration's backdrop keep its own colour in every theme, because the backdrop belongs to the artwork. It is dropped under forced colours and is never used for anything but the illustration. Review when the HIG changes this advice.

**The Contrast Rule.** Body and placeholder text target at least 4.5:1 contrast; large text targets at least 3:1. Muted text can be quiet, but never illegible. Colour is never the only carrier of information; pair it with text, an icon, or shape (HIG UI Styling). Surfaces stay usable under `prefers-contrast: more` and `forced-colors: active`. Deviation: WCAG 2.2 asks `3:1` for the edge of a control; the outline of an unchecked checkbox, radio or selection check keeps libadwaita's strength (the trough, about `1.6:1` on the dark tone and `1.3:1` on the light tone at rest; the border under `prefers-contrast: more`, `4.0:1` and `2.8:1`), because SillyBunny keeps libadwaita's controls, and a check always stands on the item or beside the label it belongs to. Deviation: dim text keeps libadwaita's `55%` on the dark tone, which is `5.9:1` on the window but `4.0:1` to `4.5:1` on rows with a hover, selected or raised fill, under the `4.5:1` target, because SillyBunny keeps libadwaita's dim strength; under `prefers-contrast: more` dim text is 90%. Review both when libadwaita changes these values.

**The Opaque Shell Rule.** Header bars, drawers, popovers, menus, dialogs, toasts, and in-app notifications are opaque. No `backdrop-filter` on shell layers; background images may show only through the canvas and the content surface at the theme's own tint alpha. Tooltips and overlaid controls are the two translucent exceptions.

**The Single Shell Rule.** The shell has one libadwaita direction; UI themes, custom CSS, and the accent colour are the theming surface.

## 3. Typography

**Interface Font:** Adwaita Sans, then `system-ui`, Noto Sans, and the platform sans stack (`--mainFontFamily`).

**Mono Font:** Adwaita Mono for code-like, structured, or machine-readable text (`--monoFontFamily`).

**Character:** One dependable sans keeps all interface text in the same voice. Weight and size create hierarchy. libadwaita uses no letter-spacing, and neither does SillyBunny's interface text. Interface chrome avoids italic and oblique faces (HIG Typography); italics in chat messages are user formatting and are unaffected.

### Hierarchy
| Role | Token | Weight | Size | Line | libadwaita |
|---|---|---|---|---|---|
| Display | `--sb-type-display` | 800 | 1.81 | 1.12 | `.title-1` |
| Headline | `--sb-type-headline` | 800 | 1.36 | 1.18 | `.title-2` |
| Title | `--sb-type-title` | 700 | 1.0 | 1.18 | `.heading` |
| Body | `--sb-type-body` | 400 | 1.0 | 1.55 | `.body` (1.4) |
| Label | `--sb-type-caption` | 700 | 0.82 | 1.35 | `.caption-heading` |
| Caption | `--sb-type-caption` | 400 | 0.82 | 1.4 | `.caption` |
| Mono | `--monoFontFamily` | 400 | 0.84 | 1.45 | `.monospace` |

- **Display:** The one large heading of a welcome or first-run page; never a control label.
- **Headline:** Major page and opened-panel headings.
- **Title:** Group headings, shell titles, and header bar titles.
- **Body:** Long-form and settings prose, and the titles of rows in boxed lists, at regular weight, as a libadwaita row title. Deviation: libadwaita's `.body` line height is 1.4; SillyBunny uses 1.55, because long-form reading needs it. Review when libadwaita changes this value. Keep prose near 65-75ch where the surface permits.
- **Document:** The main content of a view, such as the text of an article or a book, is document text. libadwaita sets it in the document font, which raises the font size and the line height to make long text easier to read (example `12pt`, line height 140%; `.document`); other long text in the interface is Body. In SillyBunny document text is Body at the user's text size (`--mainFontSize`), and the Body line-height deviation applies to it.
- **Numeric figures:** Numbers that change or line up in a column (counts, times, progress text, a column of values) use tabular figures (`font-variant-numeric: tabular-nums`), so the width of a number does not change as its digits do.
- **Label:** Compact metadata and state labels; capitalisation follows the Capitalisation Rule. Dimmed labels use `--sb-muted-fg`, the equivalent of `.dimmed`: 55% of the body colour on the dark tone, as libadwaita, and 74% on the light tone. Deviation, light tone only: libadwaita's `.dimmed` is 55%; SillyBunny uses 74%, because 55% gives 3.2:1 there, under 4.5:1. Review when libadwaita changes this value.
- **Caption:** Row subtitles and help captions; sentence capitalisation. It shares the size token of Label and is dimmed in the same way.

Existing rows and titles move to these roles as each surface is rebuilt.

### Named Rules
**The Interface Sans Rule.** Use the interface stack for controls, tabs, labels, and dense settings. Decorative type must never make repeated work harder.

**The User Scale Rule.** Product type follows `--mainFontSize` and existing user preferences. Do not add viewport-driven type or a parallel density system.

**The Wrap Safety Rule.** Headings use balanced wrapping where supported, and all labels must tolerate long translations, zoom, and narrow mobile widths without overflow.

**The Emoji Face Rule.** Emoji are drawn by a bundled colour font where a surface asks for it, in a family that covers emoji code points only and leads the stack of that surface, so a text face is never replaced and a page that shows no emoji never requests the file. A preference turns it off, and a browser that draws the face blank falls back to the device's own emoji. Deviation: GNOME draws emoji with the system's emoji font; SillyBunny bundles one, because the same pictures on every device keep a shared reading of a message the same, and the emoji of one system look different on another. The reason is proposed here for the maintainer to confirm or replace. Review when the system emoji fonts agree.

**The Capitalisation Rule.** Follow the HIG Writing Style, and for the label of a control, that control's own HIG page.
- **Header capitalisation** for headings (group, list, page, sheet, dialog, and status page titles), header bar and view titles, view switcher and tab labels, application names, button labels, menu items, tooltips, switch labels, text field labels, system notification titles, and the titles of rows in boxed lists of every kind (switch, combo, entry, spin, action, button, expander, and property rows). Capitalise the first and last word, nouns and verbs of any length, hyphenated words, and every word of four or more letters: "Find and Replace", "Self-Test", "Document Cannot Be Found".
- **Sentence capitalisation** for the labels of checkboxes, radio buttons, drop-downs, spin buttons, and sliders that are not boxed-list rows, labels that run on into other text, drop-down items, placeholders, row subtitles, captions, and body text in dialogs, system notifications, in-app notifications, banners, toasts, and status pages.
- Headings omit articles and auxiliary verbs ("Three Documents Updated"). An informal heading is written as a full sentence, with its articles and auxiliary verbs, in sentence capitalisation, and stays bold ("File has changed on disk"). Banner, toast, and in-app notification titles use the informal heading style; a system notification's title takes header capitalisation. A short question that heads a confirmation is a heading, not a sentence, and keeps header capitalisation: "Replace File?", "Save Changes?" (`AdwAlertDialog`).
- Word choice: buttons and command menu items are imperative verbs ("Save"), setting menu items are adjectives, and switch and view labels are nouns ("Automatic Location", "Albums") (HIG Buttons, Menus, Switches, View Switchers).
- Never all caps, and no uppercase tracked kickers.
- Group headings are bold (`.heading`) and carry no icon, as libadwaita's group titles.
- Deviation: the HIG Drop-Downs and Spin Buttons pages ask for sentence capitalisation on those controls' labels, and the Writing Style page asks the same for text field labels, while the Text Fields page asks for header capitalisation and libadwaita writes every boxed-list row title in header capitalisation, combo and spin rows included. SillyBunny follows libadwaita for row titles, so a group reads consistently, and each control's own HIG page for a label outside a row. Review when the HIG resolves this conflict.
- Upstream SillyTavern strings keep their upstream wording and `data-i18n` keys.

## 4. Layout

- **Adaptive sizes (HIG Scaling & Adaptiveness):** Every layout works from `360×294px` (phone) up, and down to `320px` wide nothing overlaps and nothing scrolls sideways; the HIG's smallest supported desktop size is `1024×600px`. Content sits in containers with a maximum width so lines and controls do not spread apart on large windows; groups and lists have a minimum and a maximum width. Crossing a breakpoint never makes a control or icon disappear without a transition, and the same functions stay available at every width.
- **Breakpoints:** Alerts, Dialogs and Windows become bottom sheets at `max-width: 450px` or `max-height: 360px`, the AdwDialog condition (the overlay breakpoint). Menus and pickers become sheets in the whole mobile layout, at `max-width: 768px` or `max-height: 360px`, so a menu opened in the mobile layout is never a desktop popover. The shell layout breakpoint is `768px`, because libadwaita leaves layout breakpoints to each app. A mobile-only surface whose trigger exists only in the `768px` layout keeps its sheet tied to that breakpoint. Above the mobile layout a few small steps remain, all at `1280px`: from it section tabs stop centring and a drawer's width stops following the window, and with a fine pointer a checkbox is drawn about `1.5px` larger above it. No settings page steps there, nothing steps at `1440px`, and a docked panel and the main view do not step at either width. A phone held in landscape is matched by `max-height: 450px`, because a landscape phone 375 to 430px tall would otherwise take the desktop layout. Deviation: libadwaita writes breakpoints in `sp`, which follows the system's text scale; SillyBunny writes them in `px`, because a media query cannot read the application's text size setting, so a text-scaled unit would follow only the browser's default size. Review when a media query can read a custom property. Implementation: [docs/dialogs.md](docs/dialogs.md#breakpoints).
- **Text size and `sp`:** A width in `sp` is a pixel times the user's text size (`--fontScale`), as libadwaita's `sp` follows the system's text scale. A width that holds text, such as a sidebar, a clamp or a Window, is written in `sp`, so it grows with the text and keeps its labels whole. Breakpoints stay in `px` (see Breakpoints).
- **Touch targets:** Every interactive control is at least `44px` on coarse pointers and at least `32px` on fine pointers. The size and the set of controls shown follow `(pointer: coarse)`, never the viewport width. Where this document quotes a libadwaita size that is under a floor, that is the drawn size of the control, and its target still meets the floor. Deviation: libadwaita controls are `34px`; SillyBunny uses at least `44px` on coarse pointers, because fingers need larger targets. Review when libadwaita changes this value.
- **Icons (HIG UI Icons):** Interface icons are symbolic: simple, monochrome, drawn on a `16px` grid and recoloured with the text colour. Use them at `16px`, or at `32px`, `64px` and `128px` where the icon is the focus of attention; avoid other sizes, which render fuzzy. A compact status page's `96px` icon is libadwaita's own exception. A large icon uses a heavier stroke (libadwaita weight `134`, `267` for a spinner). Status icons take the status colours of the icon palette: success, warning, error and Accent. A control shows an icon or a label, not both (Buttons); sidebars and view switchers are the exception. Use only icons users recognise, such as search, menu, back, forward and share. Some icons are recognised only as a set: a stop square needs play and pause beside it, a remove line needs an add. Deviation: GNOME uses symbolic icons drawn on a `16px` grid; SillyBunny uses the Font Awesome glyph set, sized by the text around it, because upstream markup and extensions use that set. Review when the icon set is replaced.
- **Density:** Compact mode (`--sb-density-scale`) reduces row heights, padding, and targets without changing hierarchy, and never goes under the target floors above. Containers pad `12px`, and `9px` in compact mode (`--sb-density-container-padding`).
- **Spacing:** The spacing scale is `3`, `6`, `9`, `12`, `18`, `24`, and `36px` (front matter `spacing`; `--spacing-2xs` to `--spacing-2xl`), libadwaita's rhythm. New and rebuilt surfaces use the scale. A measure in these documents that is off the scale is libadwaita's own value, quoted with its component, a value that follows from a target size (a gap that keeps a `44px` target), or part of a recorded deviation.
- **Mobile:** Preserve the same destinations, ordering, action names, and control shapes as desktop. Use safe-area-aware sheets, comfortable touch targets, and no hover-only discovery. Controls stay usable with the software keyboard open.
- **Pointer (HIG Pointer & Touch):** The primary action activates, opens or selects. The secondary action (right-click, long press) opens a context menu (see Menus and Popovers, Secondary and context menus). Esc cancels a pointer operation in progress, such as a drag. Avoid double-click and chording. Text never names a device ("move the mouse"). Controls that exist only for some pointing devices are never the only way to do something.

### Named Rules
**The WebKit Reliability Rule.** Prefer solid surfaces on mobile. Fixed layers must respect safe areas, keyboard resizing, scrolling, and focus behavior in Safari/WebKit.

**The Layer Order Rule.** Layers stack in this order, lowest to highest: dropdown, sticky, shell, overlay, modal, toast. The toast place holds both toasts and in-app notifications. A new layer takes the place of the kind it is and never sits above a toast or an in-app notification.

## 5. Elevation

SillyBunny uses tonal layering first and restrained shadows second. The main content surface stays visually calm. A shadow is reserved for a card or group at rest (the Card Shadow), an opened shell, or an overlay that must sit above the content. Overlays (sheets, drawers, dialogs) keep a `1px` border with one overlay shadow; a popover's edge is a `1px` ring inside its shadow, not a border (libadwaita 1.10).

### Shadow Vocabulary
All shadows mix `--SmartThemeShadowColor`, so themes control the ink.
- **Header bar shade** (`--sb-headerbar-shade`): a `1px` line at the edge of a bar. No blurred shadow.
- **Card Shadow** (`--sb-shadow-card`, with the card fill `--sb-card-fill`):** libadwaita's card style for a card or group at rest: a `1px` ring at 3% and two soft shadows, `0 1px 3px 1px` at 7% and `0 2px 6px 2px` at 3%, all in the shade colour. Under `prefers-contrast: more` the ring takes the border colour. A card has no separate border.
- **Popover Shadow** (`--sb-shadow-popover`): `0 1px 5px 1px` and `0 2px 14px 3px` at low shade alpha, inside a `1px` ring (`0 0 0 1px` at 5%), not a border. Menus, dropdowns, pickers, search results, and in-app notifications.
- **Dialog Shadow** (`--sb-shadow-dialog`): `0 0 14px 2px` and `0 0 5px 2px` at low shade alpha, plus the `1px` border and, in dark mode, a `1px` inner highlight. Dialogs and shell drawers.
- **Dialog Backdrop** (`--sb-dialog-backdrop`): shade colour at about 50% (dark) or 14% (light). No backdrop blur.
- **Toast Shadow** (`--sb-shadow-toast`): `0 1px 3px 1px` and `0 2px 6px 2px` at low shade alpha, libadwaita's toast shadow. A toast takes the Popover Shadow with its ring, as an in-app notification (see Toasts).
- **Page Transition Shade:** while one page slides over another in a page stack, the covered page dims under shade colour that deepens as it is covered, to about half the Dialog Backdrop (25% dark, 7% light), and the sliding page casts a soft `56px` shadow from its leading edge. Both exist only while the page moves; no page carries them at rest, and reduced motion, which removes the slide, removes them too. This is libadwaita's navigation transition shade. Deviation: libadwaita keeps the Dialog Shadow while a page slides; SillyBunny drops it from the dialog surface and restores it when the motion ends, because the clip that moves the dialog's height cuts a shadow that lies outside the box, and a shadow that followed the visible edge would be repainted on every frame, which stalls WebKit. Review when the height of a dialog can move without a clip, or when WebKit's repainting of blurred shadows changes.
- **Focus Ring** (`--sb-focus-ring-inset`: `inset 0 0 0 2px` of `--sb-focus-ring-color`): The focus treatment for buttons, tabs, and menu rows. Fields draw the same colour as their border plus a `1px` inset, which reads as the same `2px` ring (see Text Fields). Do not stack it with an outline or an outer ring. A button with a solid fill (a suggested or destructive action, the send button) and a control on a picture (an avatar) draw the ring outside instead, as libadwaita draws it for opaque and on-image buttons: a `2px` outline in `--sb-focus-ring-color` with a `1px` gap, and no inset ring. Inside a toast, which is dark in both tones, the ring takes a light form of the accent, as libadwaita's toast does; an in-app notification is on the Popover layer, so its controls take the ordinary ring. Checkboxes, radios, and ranges use a `2px` `--sb-focus-ring` outline with an offset instead. Under forced colours every focused element also draws a `Highlight` outline, because forced colours remove shadows. Deviation: libadwaita's ring is 50% of its accent colour; SillyBunny's is about 55% on the dark tone and about 66% on the light tone, because 55% gives about 2.5:1 on the light tone and 3:1 is the target. Review when libadwaita changes this value.
  The ring is drawn in Accent, as libadwaita's.
  Deviation: libadwaita draws the ring of checkboxes, radios, and ranges inside the control; SillyBunny draws it outside with an offset, because the ring then stays visible around a small control. Review when libadwaita changes this rule.
- **Drop Target:** An element that accepts a drop draws Accent as an inset `2px` ring when it is a button, and `1px` for any other element, with no change of fill. A whole drop area, such as a thumbnail or a drop zone, takes a `2px` ring at 40% Accent and a 10% Accent fill. Every drag-and-drop action has a keyboard route, and Esc cancels a drag (HIG Keyboard, Pointer & Touch).

### Flat Fill Vocabulary
Flat and raised controls use fills mixed from `--SmartThemeBodyColor`, so they follow light and dark themes without a new color. These are libadwaita's values.
- **Flat:** transparent at rest; `--sb-flat-hover-bg` (7%), `--sb-flat-active-bg` (16%), `--sb-flat-selected-bg` (10%), and `--sb-flat-selected-hover-bg` (13%).
- **Raised:** a secondary button is a raised button: `--sb-raised-bg` (10%) at rest, `--sb-raised-hover-bg` (15%) on hover, and `--sb-raised-active-bg` (30%) when pressed.
- **Boxed rows:** A row that activates fills 3% on hover and 8% when pressed. Rows are separated by a `1px` line in the shade colour; under `prefers-contrast: more` the line takes the border strength.
- **Sidebar rows:** The flat fills apply, and a selected row that is pressed fills 19%. Under `prefers-contrast: more`, hover, pressed and selected rows add a `1px` ring at the border strength.
- **List-view rows:** Hover 4% and pressed 8% of the body colour. A selected row fills Accent at 25%, 32% on hover and 39% pressed; under `prefers-contrast: more` it adds a `1px` ring at the border strength.
- **Trough:** the range trough and the switch's off trough are 15%.
- **Toolbars:** Bars are separated by a `1px` shade line only. A busy state may use an accent border and a progress bar; no glow.

### Named Rules
**The Layer Before Shadow Rule.** Establish a tonal surface before adding elevation. If a shadow is doing all the work, the surface token is wrong.

**The Flat Toolbar Rule.** Toolbar and navigation buttons are transparent at rest. Hover, press, and selection use neutral fills mixed from the body color, with no borders, bottom stripes, underlines, glows, or hover lift. Hover fills apply only under `(hover: hover)`.

## 6. Shapes

Nothing is larger than `18px`, except pills and circles.

- **Control** (`--sb-radius-control`, `9px`, libadwaita `$button_radius`): controls in bars (destinations, section triggers, Back, actions, and fields in a bar), as libadwaita's header bar buttons, plus menu and search result rows, tooltips, and segments. Back and section buttons are flat.
- **Card** (`--sb-radius-card`, `12px`, libadwaita's card radius): groups inside editors, dialogs, windows, and side panels, and the boxed rows of list sidebars.
- **Overlay** (`--sb-radius-overlay`, `15px`): popovers, menus, dialogs, windows, shell drawers, in-app notifications, and bars that float over content. Bottom sheets round their top corners only. Docked side panels are square.
- **Alert** (`--sb-radius-alert`, `18px`): alert dialogs.
- **Pill** (`999px`): a primary text button in open space (HIG Buttons). A circle is for Close, which has a tonal fill, and for an icon-only suggested action.
- **Toast** (`999px`): a pill, as libadwaita's toast (`150px`). A toast that wraps on a narrow window takes half the height of a one-line toast instead (see Toasts).
- **Content:** content buttons, fields, and icon-only content controls take the Control radius; content cards and preference groups take the Card radius. The older names `--sb-radius-button`, `--sb-radius-sm`, `--sb-radius-md`, `--sb-radius-lg`, `--sb-radius-xl`, and `--sb-shell-control-radius` remain as aliases of these two for existing rules and user CSS.
- **Inner** (`--sb-radius-inner`, `6px`): a small part inside a control or a row, such as a keycap or the title of an expander, as libadwaita's.
- **Small controls:** checkboxes are rounded squares (radius `30%` of their size); radios, switches, and selection-mode checks are round.

## 7. Motion

Motion shows where something came from and where it went. It never delays a task.

### Tokens
| Token | Value | Use | libadwaita |
|---|---|---|---|
| `--sb-transition-fast` | `200ms` `--sb-ease-out-quad` | Hover, press, focus, selection, colour and fill changes | `$button_transition`, `$focus_transition` |
| `--sb-transition` | `250ms` `--sb-ease` | Reveals, expanders, height changes, banners | GtkRevealer, AdwExpanderRow |
| `--sb-transition-slow` | `300ms` `--sb-ease` | Toasts and large surface fades | AdwToast |
| `--sb-duration-fast`, `--sb-duration-normal`, `--sb-duration-slow` | `200ms`, `250ms`, `300ms` | The durations of the three transitions alone, for a delay or a property whose easing is set elsewhere | |
| `--sb-ease-out-quad` | `cubic-bezier(0.25, 0.46, 0.45, 0.94)` | State changes | `$ease-out-quad` |
| `--sb-ease` | `cubic-bezier(0.25, 0.1, 0.25, 1)` | Timed animations | `ADW_EASE` |
| `--sb-ease-out-cubic` | `cubic-bezier(0.33, 1, 0.68, 1)` | Exits and fades | ease-out-cubic |
| `--sb-ease-out-back` | `cubic-bezier(0.34, 1.56, 0.64, 1)` | The slide of an in-app notification as it enters and leaves, and its scale as it enters | GNOME Shell `EASE_OUT_BACK` |

Springs are sampled from libadwaita's AdwSpringAnimation into CSS `linear()` easings, with a cubic-bezier fallback where `linear()` is unsupported (Safari before 17.2). `public/scripts/sillybunny-motion.js` owns the JS presets.
- **Dialog spring** (0.62, 1, 500): about 510ms, peak 1.08. This is the only spring with a pronounced overshoot; the one other overshoot is the in-app notification's `--sb-ease-out-back`, GNOME Shell's banner easing (see By Pattern).
- **Sheet spring** (0.8, 1, 400): about 470ms, near-critical.
- **Navigation spring** (1, 1, 1000): about 330ms, critically damped.
- **Closing** uses the clamped spring or `--sb-ease-out-cubic` and never overshoots, except an in-app notification, which leaves with GNOME Shell's `--sb-ease-out-back` while it fades out of view.

### By Pattern
- **Overlays:** Alert and Dialog open with the Dialog spring, scaling `0.8 → 1` and fading from the centre, and close clamped over 200ms to scale `0.9`. A Window opens with the Sheet spring (`0.96 → 1`) and fades to `0.98` over 200ms. Shell drawers use the Sheet spring with a fade and scale `0.96 → 1` from the trigger, and close with a 200ms fade and scale to `0.98`. Bottom sheets slide up with the Sheet spring and down to close. The backdrop fades with the surface.
- **Popovers and menus:** 200ms fade and scale `0.96 → 1` from the trigger edge; close is a 150ms fade. Deviation: GTK4 popovers do not animate; SillyBunny fades and scales them from the trigger edge, because the user then sees what opened. Review when libadwaita changes this behaviour.
- **Pages:** The Navigation spring (`334ms`) pushes and pops dialog pages and section pages on narrow layouts, with the Page Transition Shade. A Popup page pops over 200ms with `--sb-ease-out-cubic`. A List → Split Editor list shrinks to a sidebar while the editor slides in from the right, with continuous compression, and reverses on close; picking another row swaps the editor content without replaying the slide. Deviation: `AdwNavigationView` holds the larger of the two pages' sizes during the transition and the dialog takes the new size when it ends, and `AdwDialog` does not animate its size; SillyBunny moves the visible height of a content-sized Dialog or Window from the old height to the new over the slide, holding the surface at the larger size behind a clip that follows its corners and border, because pages of different heights are common in SillyBunny's dialogs, unlike in many libadwaita apps, and the snap at the end of the slide is visible. Review when libadwaita animates the size of a dialog or a navigation view with its pages.
- **Toasts:** libadwaita's toast motion. In over 300ms (`--sb-ease`): a slide by the toast's own height and margin, so the toast comes out of the edge it sits at, which clips it: up from below at a bottom position (the window edge, or the top of the bar or keyboard it sits above), down from above at a top position. A toast does not fade in. Out over 300ms: a fade (`--sb-ease-out-cubic`) and a scale to `0.95` from its centre. Under reduced motion, a fade.
- **In-app notifications:** GNOME Shell's banner motion. In over `200ms`: a fade (`--sb-ease-out-quad`) with a slide from one height beyond the edge they sit at and a scale from `0.9` to `1` (`--sb-ease-out-back`). Out over `200ms`: a fade with a slide back by their own height (`--sb-ease-out-back`). They come out of the edge they sit at, which clips them, as GNOME Shell's message tray clips its banners at the edge of the work area. When one of several comes or goes, the others move to their new places over `200ms` with `--sb-ease-out-quad`; GNOME Shell shows one banner at a time and has no motion for this. Under reduced motion, a fade.
- **Tabs and expanders:** Tabs and page sections crossfade over 200ms (AdwViewStack). Expanders reveal over 250ms; the chevron rotates over 200ms.
- **Side panels:** The main content shifts over `--sb-transition` (`250ms`) when a panel docks or closes. The panel appears after the content has settled.

### Named Rules
**The State-Only Motion Rule.** Animate state, origin, and destination only. No decorative choreography, ambient loops, or hover lift. A loading indicator or a spinner shows the busy state and may move in place while it lasts. Deviation: the HIG animates to show state, origin, and destination; SillyBunny also lets an illustration move in place, because the art is content, not interface motion. Review when the HIG changes this rule. Such motion stays inside the illustration, the indicator or the spinner, never moves layout, pauses while it is hidden, and stops under the Reduced Motion Rule, which shows the first frame (a loading indicator shows finished; a spinner shows its still arc).

**The Reduced Motion Rule.** `prefers-reduced-motion: reduce` or the Reduced Motion setting removes movement and scale. State changes become instant or a crossfade of 200ms or less. JS helpers are no-ops under reduced motion.

## 8. Components

Patterns follow the HIG pattern groups. Sizes and corners come from Layout and Shapes.

### Containers

#### Dialogs
- **Implementation:** [docs/dialogs.md](docs/dialogs.md) is the code reference for Alerts, Dialogs, Windows, pages, and side panels: the `openDialog` and `openAlert` APIs, the Popup hook, page chains, adapters, and a testing checklist. Read it before you build or change one.
- **Tiers:** **Alert** is for messages, confirmations, one-field prompts, and at most one boolean option: `300px` preferred and `372px` maximum (`600px` when wide), content-sized and centred, with a centred heading and body. **Dialog** is for forms and action dialogs: `min(640px, 100% - 32px)` wide with a `360px` minimum, a header bar, and one scrolling body. **Window** is for lists, editors, and viewers: at least `640px` and at least as wide as the main content column, never wider than the viewport minus `32px` and never wider than `1440sp`, whatever the width of the main content column or the window (`min(max(640px, var(--sheldWidth)), 100% - 32px, 1440sp)`). A Dialog or Window that shows something beside its content, such as an illustration, is wider by that width (`--sb-dialog-aside`), and the `1440sp` ceiling includes it. Below the ceiling a Window keeps following the width of the main content column. Dialog and Window heights follow their content up to `90dvh`; a Window that fills (document viewers and editors) is `90dvh` tall. How a surface picks its tier is in the implementation reference.
- **Short and wide Alerts:** In a short view (`max-height: 360px`) an Alert tightens: `24px` above the message, `18px` between its parts and at its sides, `18px` around the responses with `9px` above them, and `16px` button padding with no minimum width. Its responses stay in one row and the Alert grows as needed, so no label is cut. Otherwise, two or more responses that do not fit in a row stack. An Alert with short labels may prefer a row at medium widths, which makes it wider, to `600px`.
- **Primary and secondary windows (HIG Windows):** A primary window hosts the main functions of the application and is independent of any other primary window. A secondary window belongs to a primary one and closes with it; the Dialog and Window tiers are secondary windows. A secondary window is modal to its parent, except one that offers the same functions as the primary window, such as a pop-out. It is no bigger than its parent and holds limited, simple content. Avoid stacking secondary windows (see Pages and stacking). Esc closes a modal window. A primary window restores its previous size with its previous view.
- **Surface:** An Alert uses the Dialog layer. A Dialog or Window uses the Window layer, as `AdwDialog` uses `window-bg`; a Window header uses Header bar, and the body of a Window that shows a document uses View. All three have a `1px` border, Dialog Shadow, and a Dialog Backdrop without blur.
- **Headers:** Cancel comes first and the affirmative last, as in GNOME; custom responses sit between them. An explicit-action Dialog or Window puts Cancel at the header start and the affirmative action at the end, with no Close. An immediate-apply surface shows Close at the end. With three or more responses, other responses sit in a bottom bar aligned to the end. Responses use the primary and secondary button families; Close is a circle with a tonal fill.
- **Pages and stacking:** One Alert may open above any surface. A Dialog or Window opened over another becomes a page in the same frame, never a second visible frame, and the parent becomes inert. A pushed page shows Back at the start. With explicit responses, Cancel acts as Back and the affirmative stays at the end, with no Close; without them, Close sits at the end. Back and Esc pop one page. Close closes the whole frame one page at a time, from the top, and stops at a page that refuses to close. A page over a bottom sheet keeps the sheet's shape and grab handle, and a downward swipe on the handle pops the page.
- **Use (HIG Dialogs):** A dialog opens only in direct response to a deliberate action, never unexpectedly. Prefer inline controls to action dialogs. Alert dialogs carry one to three responses. Action dialogs label the affirmative response with a specific verb ("Save", "Export"), never "OK" or "Done", and keep it insensitive until required options are set. Deviation: the HIG prefers a specific verb to a generic "OK" on the affirmative button of an action dialog and shows an error dialog with a single button that closes it; a popup with one response that only informs the user keeps "OK" where upstream SillyTavern shows it, because upstream's wording and its translation keys stay (see the Capitalisation Rule). Review when upstream popups name their responses. Avoid error dialogs; show non-critical errors inline, in a toast, or in an in-app notification.
- **Shortcuts overview (`AdwShortcutsDialog`):** A Dialog titled "Keyboard Shortcuts" that lists the shortcuts of the application. It opens from the primary menu and with Ctrl+? (HIG Keyboard reference). It is `600px` wide. Shortcuts are grouped in sections, titled and ordered by menu-bar convention, with the most general in "General" rather than "File"; an untitled section subdivides a long one. A search entry fills the header bar, `400px` at most, with the placeholder "Search shortcuts"; Ctrl+F focuses it. With no match the dialog shows a status page, "No Results Found" and "Try a different search". A shortcut is a row at least `36px` tall with `9px 12px` padding: the title and an optional dimmed caption at the start and the keys beside them, wrapping below the title when the row is narrow; an item with no shortcut reads "No Shortcut". Each key is a keycap: a 10% body-colour fill, `6px` radius, `6px` padding, `20px` minimum width, a `2px` lower edge in the shade ink (`#000006`) at 36% on the dark tone and 7% on the light tone, and a `1px` border at the border strength under `prefers-contrast: more`. With four or more sections and twenty or more shortcuts, round buttons (`3px 12px` padding) let the user jump between sections. List only shortcuts the application has.
- **Preferences dialog (`AdwPreferencesDialog`):** Settings are gathered into pages of groups. The dialog is `640px` wide and works down to `360px`. A page content column is clamped to `600px`, with `24px 12px` margin and `24px` between groups. The page switcher sits in the header bar; when the dialog is narrower than `400px`, or than `110pt` (about `147px`) for each page, the switcher moves to a bottom bar, and a dialog with one page shows its title instead.
  - **Search:** When search is on, a toggle button with the search icon at the header start (tooltip "Search") swaps the title for a search entry, `400px` at most, with the placeholder "Search preferences". Ctrl+F opens it and typing while the dialog has focus starts it. Results are rows from every page; activating one opens its page at that row. Up from the first result returns focus to the header. A hidden page is left out of the results.
  - **Page banner:** A page can show a banner above its groups and outside the scrolling area.
- **About dialog (`AdwAboutDialog`):** Opened by the primary menu item "About" followed by the application's name. A Dialog `360px` wide, every part optional. The main page is centred: the application icon (`128px`, hidden from assistive technology), the name in the Display role, the developer's name, and the version as a pill button (`999px` radius, `3px 18px` padding, Accent text) that copies the version. Rows below open pages: What's New (the release notes of one version), Details (a long description, the website and extra links), Troubleshooting (Support Questions, Report an Issue and debug information that cannot contain markup or links and can be saved to a file), Credits (Developers, Designers, Artists, Documenters, Translators) and Legal. The main page has `12px` margin, `6px` between items and `18px` around the name block; a subpage has `18px 12px` margin and `18px` between items.
- **Keyboard:** Initial focus goes to the control the user is expected to operate first. Esc activates Cancel. Return activates the affirmative response only when it is neither destructive nor irreversible; otherwise there is no default response. On close, focus returns to the opener, or to the nearest visible control when the opener is gone.
- **Destructive actions (HIG Dialogs, Toasts):** A destructive action that cannot be reversed is confirmed with an alert dialog: Cancel first and focused, the destructive response in Destructive Red. A destructive action that can be reversed is done at once and offers Undo in a toast. Changes inside an editor with explicit save need no confirmation, because Discard restores them. Existing confirmations of reversible actions stay until each action offers Undo.
- **Sheets:** Under the overlay breakpoint every overlay is a bottom sheet: full width, a grab handle, safe-area padding, and scrolling content. A downward swipe from the handle or header (on an Alert, from the handle or heading) follows the finger, closes the sheet, and springs back when short. An Alert stacks its responses full-width at `44px`, with the affirmative on top and Cancel at the bottom. A Dialog or Window keeps Cancel and the affirmative in its header. Deviation: libadwaita keeps alert dialogs floating and gives its dialog sheet no grab handle; SillyBunny makes every overlay a bottom sheet with a grab handle, because a sheet gives `44px` rows and reach for the thumb, and the grab handle is the only visible cue that a sheet can be swiped away. Review when libadwaita changes this behaviour.
- **Choosers (`GtkEmojiChooser`):** A popover, or a bottom sheet in the mobile layout, for picking one item from a large set of symbols. A search entry sits on top, the sections below it as headings over a wrapping grid of equal cells, and a toolbar of one button per section at the bottom, with a Recent section first that is hidden while empty. A cell is a flat button at the Control radius, `3px` from its neighbours, and its accessible name is the item's name, not the symbol alone. The grid is one Tab stop with a roving focus: arrows move by cell and by line, Home and End to the ends of the line, Page Up and Page Down by a page, and Enter in the search entry picks the first result. A pick closes the chooser; Shift keeps it open for several. An item with variants opens a small panel of them in the chooser on a long press, a secondary click, Shift+F10 or the Menu key. Sections are built in pieces, one task at a time, so opening never holds the page for longer than a frame budget, and a jump to a section has a button, not only a key. On a touch device the first focus is the grid, so the on-screen keyboard does not hide it. A wait and a failure use the status page in its compact form. Deviation: the HIG asks a popover to cover no more than about a third of the window; a chooser of this size covers more on a small window, because a grid of a few hundred cells needs the room, and the sheet takes the mobile layout. The reason is proposed here for the maintainer to confirm or replace. Review when libadwaita adds a chooser.
- **Bottom sheet (`AdwBottomSheet`):** A sheet attached to the bottom edge at full width, its top corners at the Overlay radius (`15px`). The grab handle is a `54×6px` pill with `15px` margin, in the body colour at 25%; it also lets a pointer drag the sheet, so a sheet without a handle cannot be dragged with a pointer. A modal sheet dims what is behind it with the shade colour at twice its alpha, and its edge is a `1px` ring of white at 7% (30% under `prefers-contrast: more`) inside the shadow. The sheet follows its content's height and leaves a gap above it of `30px`, growing from a viewport height of `720px` to `120px` at `1440px`. A header bar under a handle is at least `36px` tall. It opens and closes with the Sheet spring; under reduced motion the spring is critically damped. A persistent sheet is non-modal and has a bottom bar that expands into the sheet when pressed; use one only where the sheet is part of the layout, and a Dialog for anything transient. A sheet is not adaptive: at larger widths replace it with a sidebar or another layout.

#### Menus and Popovers
- **Surface:** Popover layer, overlay radius, Popover Shadow. Padding is `6px` for a menu list and `8px` for any other popover. The edge is a `1px` ring inside the shadow, not a border.
- **Rows:** `32px` minimum height (`44px` on coarse pointers and in sheets), `0 12px` padding, Control radius, and full-opacity labels with dimmed icons. Hover, press, and keyboard selection use the flat fills.
- **Items (HIG Menus):** Verbs for commands and adjectives for settings, in header capitalisation. Keep actions, checkbox items, and radio items in separate sections. Order by importance, task order, or frequency, with the most important items at the top or bottom. No nested submenus. Menus hold three to twelve items. Omit items that do not apply rather than disabling them, and never add commands only to reach three. Destructive items sit last in their own section, in Destructive Red, and follow the rule for destructive actions (see Dialogs). Deviation: the HIG holds a menu to three to twelve items; a menu that carries extension items, Move Up and Move Down, saved views, or items that upstream SillyTavern adds for the connected backend may exceed twelve, because extensions, users and the backend add items, and the HIG itself asks for the move items. Deviation: the HIG asks for no nested submenus; a menu that upstream SillyTavern or an extension builds keeps its own submenus, because SillyBunny does not rebuild those menus. Menus that SillyBunny builds have none. Review both when the HIG changes these rules.
- **Icons:** Every command item has an explicit, relevant icon; a generic placeholder icon is never shown. Check and radio items use their state indicator. Deviation: GNOME menus show labels only (HIG UI Icons: a control has a label or an icon, not both); SillyBunny gives every command item an icon, because icons aid scanning in long menus. Review when the HIG changes this rule.
- **Menu buttons:** A secondary menu uses the vertical ellipsis (`view-more-symbolic` in GNOME). A primary menu, where a surface has one, uses the menu icon (`open-menu-symbolic` in GNOME). The tooltip and accessible name name the menu: "Main Menu" for a primary menu, and for a secondary menu the item it applies to (for example "Document Menu").
- **Primary menu (HIG Menus):** The menu of the whole application, for the features every application has. Its button uses the menu icon (`open-menu-symbolic` in GNOME) and carries the tooltip and accessible name "Main Menu". It sits at the end of the header bar, or above the list when the window has a sidebar. With hierarchical navigation it shows only on the top-level view; deeper views use a secondary menu if they need one. The standard items form the last group: Preferences, Keyboard Shortcuts, Help, and About followed by the application's name, for those the application has; About is always there. A primary menu has no Close or Quit item.
- **Secondary and context menus (HIG Menus, Pointer & Touch):** A secondary menu sits in the header bar and holds actions and settings for the current view or item, such as a document, contact or photo. It is optional, used only when there are enough items, and does not repeat Preferences or About. A context menu opens on the secondary click, a long press, Shift+F10 or the Menu key, for what is under the pointer or focus, and F10 opens the header bar's menu. The secondary click opens a menu and never runs an action itself, such as Delete. A context menu appears only when it has relevant items, and every action in it is also reachable by keyboard.
- **Popovers (HIG Popovers):** Small and simple, covering no more than about a third of the window. No Close or Done button. A heading only when the content's purpose is unclear. Esc closes the popover and returns focus to its trigger.
- **One at a time:** Select dropdowns and search results follow the same surface and row rules. A second click on an open trigger, or on a select row's background, closes its popup instead of reopening it. Opening another menu, picker, or popover closes the current one first.
- **Sheets:** In the mobile layout (`max-width: 768px` or `max-height: 360px`), menus and pickers become bottom sheets with a grab handle and the same swipe to close as Dialogs. Deviation: GTK popovers stay popovers on mobile; SillyBunny turns menus and pickers into sheets, because a sheet gives `44px` rows and reach for the thumb, and the grab handle is the only visible cue that a sheet can be swiped away. Review when libadwaita changes this behaviour. A type-ahead list (the completions or suggestions under a text field) is not a menu: it stays anchored below its field at every size, because the field and the on-screen keyboard must stay in view while the user types.

#### Boxed Lists and Rows
- **Groups:** Preference groups are libadwaita boxed lists (`AdwPreferencesGroup`) in the card style: the card fill (`8%` of the body colour on the dark tone, View on the light tone, as libadwaita's card background) and Card Shadow, with no separate border; `1px` separators between rows, and `24px` between groups. The bold heading and optional description sit `6px` above the list, not inside it. A group may have no title, as an `AdwPreferencesGroup` may; its box then names itself with an accessible label. A set of settings that depends on a switch is its own group: the switch is its first row, and the rows after it are insensitive while the switch is off (see Selection Controls). Content that is not a row, such as a grid or a text area, sits in the group as a full-width block with the same inset as a row. A settings page pads its content `24px` at the top and `12px` at the sides, as a libadwaita preferences page. Groups never take a coloured side stripe.
- **Cards:** Cards are working surfaces, not a repeated icon-heading-text grid; prefer an open list, tab row, or inline section when that is clearer. A welcome or first-run view may use a centred icon and text, if it stays sparse, labelled, and helpful rather than decorative.
- **Rows:** At least `50px` tall, with `6px` block and `12px` inline padding and `6px` between their parts, as libadwaita's action row; a subtitle makes the row as tall as its two lines need. The title (Body at regular weight) and an optional dimmed subtitle (Caption) sit at the start, the control at the end. The control stays beside the title at every width and moves under it only when the two do not fit; no width breakpoint decides it. Bounded labels and flexible controls keep widths stable across varied label text; controls with an intrinsic width keep it. Expanders put a trailing chevron after any suffix controls, pointing down when collapsed and up when expanded. The expander's header toggles it with a click, Enter or Space, and a suffix control in it keeps its own focus; collapsed content is out of the tab order, and several expanders may be open at once, as libadwaita's. Row text, subtitles included, keeps at least 4.5:1 contrast; placeholders and secondary text use `--sb-input-placeholder` (78% body colour mixed with theme tint). Existing rows move to these roles as each surface is rebuilt.
- **Row types:** Choose by the Selection Controls hierarchy; the row factories are in the implementation reference. A switch row puts `role="switch"` on its native checkbox and never adds `aria-checked` (ARIA in HTML forbids it on `input type=checkbox`). The whole row toggles its switch or check. A switch sits at the end of its row and a check at the start. A toggle row (`AdwToggleGroup`) is an exclusive choice, not a view switcher: label-only native radio segments in a named `radiogroup`, drawn as a toggle group (see Selection Controls); filled, it puts the title above equal-width segments whose labels wrap at word boundaries. A select row (`AdwComboRow`) shows the value and opens the shared searchable picker; a row built on a native form control keeps that control as its source of truth. A select row whose items can be grouped or starred, and which has item actions, shows a trailing menu button only when it has actions.
  - **Property row:** A read-only name and value. The name is the title at the smaller Caption size and dimmed; the value is the subtitle, at full strength and selectable, so it stands out and can be copied. A value that is code or an identifier uses the Mono role. A property row has no control.
  - **Spin row:** A row with an exact number, right-aligned at the end, with a round minus and a round plus button of `30px` beside it, `6px` apart with a fine pointer and `14px` apart with a coarse one, so each button keeps a `44px` target. The number takes the free width of the row, so its placeholder shows in full. The number's own field draws no outline of its own; the row draws the focus ring. Use it when the exact value matters; otherwise a slider (HIG Spin Buttons). A number in a property bar and the counter beside a slider carry no buttons.
  - **Button row:** A row that acts as a button, at the end of a list or for an action that is part of the list, such as adding an item. It has a title in the Title role between an optional icon at the start and one at the end, `40px` tall inside, with `12px` side margin. A suggested button row fills the whole row with Accent and its ink, and a destructive button row takes Destructive Red text; a view still has at most one suggested or destructive button. Label rules follow Buttons, including the ellipsis rule.
  - **Pill button with a list:** A single action that needs attention or must stand apart from the list above it is a pill button below the list, not a row.
- **List rows:** In list sidebars, a row carries an optional leading grip and dimmed icon, a title with a one-line description, optional dimmed metadata, then at most a switch and a ⋮. Beside an open detail pane, rows hide their subtitles and ⋮ and keep the `52px` minimum. Deviation: the HIG allows a boxed-list row at most two controls; a reorderable row with a switch has a drag handle, a switch, and a menu button, three controls in all, because a reorderable row that can also be switched on and off needs all three. Review when the HIG changes this rule. There are never three trailing controls. In a narrow sidebar, a row that holds a grip, a switch and a menu tightens its gap and inline padding to `6px`.
- **Boxed-list rules (HIG Boxed Lists):** A row holds one control, two at most. Clicking the row background activates its control; the control takes keyboard focus, not the row. A button row that opens a new view ends with a trailing arrow instead of an ellipsis. Deviation: the HIG reserves boxed lists for small, static sets of rows; the sidebars of List → Split Editor use boxed rows (card radius, card fill, Card Shadow) for collections of any size, and load large ones in batches with a Show More row, because one visual language serves every list, and large collections load in batches. Review when the HIG changes this rule. A list inside an editor whose page size upstream SillyTavern saves for the user keeps a pager with that size instead of Show More, because its items are edited in place, and in an ordered list of thousands of items a page keeps each item's place stable. Rows that upstream SillyTavern builds and that extensions reach through their markup keep that markup and take the row metrics through styles, because extensions depend on it.
- **Keyboard in long lists (HIG List & Column Views, `AdwSidebar`):** A list sidebar or any list that loads in batches is one Tab stop, as libadwaita's sidebar (`GTK_LIST_TAB_ITEM`): Tab enters on the selected row (or the one last visited, or the first; Shift+Tab with none of these, the last), passes through that row's own controls, and leaves the list. Up and Down move between rows, Home and End to the first and last, Page Up and Page Down by a page; in a grid Left and Right move between cards, and Up and Down by a line of cards. The arrow keys move focus only, never into a row's controls, and hidden, filtered and disabled rows are skipped. Show More is the row after the last one; pressed from the keyboard, it focuses the first row it added. Reorderable rows keep Alt with the arrows as the moves. Boxed lists on settings pages keep every row in the Tab order, as `GtkListBox` does (`GTK_LIST_TAB_ALL`).
- **List and column views (HIG List & Column Views):** The alternative to a boxed list for very large or dynamic collections. Keep rows simple and regular: one or two elements each. Differentiate several text elements by size and weight, and use symbolic icons. Order the list in the way that is most useful. A list has a minimum and a maximum width. A column view has a header per column that sorts it: clicking an unsorted header sorts in natural order and shows a down arrow, clicking again reverses it and shows an up arrow. Natural order is alphabetical, smallest number first, earliest date first or checked items first. A list view shares its data with a grid view, so the two can offer the same collection in two forms. Selected rows follow the List-view rows fills.
- **Reordering:** Rows that can be reordered offer Move Up and Move Down in their menu, which the HIG requires for accessibility, beside drag and grip keyboard actions; all three share one saved order. Omit a move at its boundary and while a search or filter is active, and keep focus on the moved row. A long list may also offer Move to Top and Move to Bottom in the same section, omitted at the boundary like the other moves. Existing reorderable rows without move menu items move to this rule as each surface is rebuilt. Deviation: lists whose rows and drag handles come from upstream markup get keyboard moves instead of move menu items: the row or its handle takes focus, Alt+Up and Alt+Down move it one place and Alt+Home and Alt+End to the ends, and the move is saved and announced as a drag would be; SillyBunny adds no row menus there, because the markup stays upstream's for compatibility with upstream and its extensions. Review when the HIG changes its reordering advice.
- **Moving a row between sections:** A list in sections that sort themselves, such as favourites above the rest, moves a row to another section by dragging the whole row, with no grip. The whole section, its heading included, is the drop target and takes the area ring of Drop Target. A section that is empty and hidden shows as a drop zone with a one-line hint while a drag runs, and a collapsed section stays a thin strip to drop on and opens when the pointer rests on it for half a second. That opening lasts for the drag and is undone when the drag ends, except for the section that receives the drop. Sections keep their own order, so a drop shows no insertion marker: the row lands at its place and shows a short Accent highlight that fades into its own fill (a plain fill under reduced motion). Esc cancels the drag. On touch a long press lifts the row and a move drags it; a long press released without a move opens the row's menu, so a row that can be dragged also has a context menu. Two other routes make the same move, and both keep focus on the row and announce it: an item in the row's menu that names the section ("Add to …", "Remove From …"), and Alt+Up and Alt+Down on the focused row, up to the section above and down to the section below. While a search filters the list, dragging and the Alt keys are off and the menu items stay.
- **Folders in a list of rows:** A list whose rows the user files into folders shows each folder as a section of the same list, one level deep. The heading of a folder is a button, with a chevron at the start, the folder's colour dot, its name and the number of rows it shows. The sections read from the top: the section that sorts itself (such as favourites, shown only while it holds a row), the folders in the user's order, and the rest. An empty folder keeps its heading. A row is in one section; a row that is also a favourite shows only in the favourites section and keeps its folder, so that it returns there when it is no longer a favourite. The heading opens and closes the folder with the motion of Expanders, and each folder remembers its state; a closed folder shows the number of its unread rows as a badge. A folder's heading has a context menu (secondary click, long press, Shift+F10, the Menu key) with Rename, Colour and Delete, and Delete asks first and leaves the rows in the rest. Folders are ordered where they are managed, so that menu has no Move Up or Move Down. A row reaches a folder by the routes of Moving a row between sections, where Alt+Up and Alt+Down go to the neighbouring section in the order above, folders included. A move into a closed folder opens it, so that the row stays in sight with the focus on it; an Alt key opens it only for the row, and the folder closes again when the same row leaves it by the next Alt key. A menu item that sets only the folder of a row that is also a favourite leaves the row where it is, and says why. While a search filters the list, folders without a match are hidden, folders with one show open, their headings do not open or close, and dragging and the Alt keys are off.
- **Adding and removing:** A list that can change has an add button at the top of the list or an add row at its end. Each row has a remove button at its end. A list that can also be reordered has a drag handle at the start of each row, and a menu button at the end in place of the remove button, with Move Up, Move Down and Remove; the move items are required for accessibility.

#### Grid Views
- **Grid (HIG Grid Views):** A grid of images, such as thumbnails of items or a chooser of pictures. Each item has its own thumbnail where possible. Order items by what is most useful to the user; most recently added is often best. Style the grid to the content: minimal, so the content shines; outline a cell only where images are irregular or inconsistent. Offer a list view of the same collection where extra details (dates, authors) help. Give a grid a maximum width so rows do not grow uncomfortably long, and test it across window sizes. The cards of a wide grid of cards keep one width, `190px`, and the columns are centred in the page, so a wider window adds a column and does not resize the cards; the last row starts at the first column. A phone keeps two stretching columns. A grid cell has the Control radius and a `3px` inset; its fills are those of a list-view row, and under `prefers-contrast: more` hover and pressed cells add a `1px` ring.

#### Header Bars and Toolbars
- **Header bars (HIG Header Bars):** Every top-bar control has a tooltip. Header content updates to match the current view, and essential main-content controls stay labelled and visible. Header actions that do not fit move into the ⋮ menu as space runs out. As a bar narrows, its title shortens first; then labelled buttons drop their labels and keep their icons and tooltips; then the title hides, once less than `60px` of it would show; last, the buttons that still do not fit move into a ⋮ menu named by what it holds. An editor's view switch (Edit/Preview) moves into its item menu on a phone before the title shortens, so the item's name keeps its room; an editor with no item menu keeps the switch. Each step stays taken as the bar narrows further, and nothing in the bar is clipped, scrolled out of view or drawn over another control. A bar that hides its labels, whether by its width or by a setting, shows the same controls in the same order, each with its label as its tooltip and accessible name. A bar keeps one row: its controls never wrap to a second row, because a control that changes rows loses the place the hand has learned; folding into the ⋮ menu is the only way a control leaves the row. The mobile layout states its own rows. At most one destination in a bar is active, the view on screen; a toggle keeps its own on state.
- **Heights:** One height for each kind of bar. A list's header bar, and the header of an editor beside or in place of a list, is `60px`. A settings page's sidebar and content bars are `60px`, and the content bar grows when its description wraps. A settings subpage bar is `56px`. The header bar of a Dialog, a Window, a side panel or a chat view is `56px`, and as a sheet it adds its grab handle above. The top bar is `54px` (`44px` on phones). Every bar has a `6px` inset at its ends and `6px` between its controls.
- **List headers:** A list header may carry the context of its list: state badges after the title, shown only when the state applies, and a subtitle that joins the context (the active preset, the backend) to the list's counts with a middle dot. When the bar cannot hold the title, the badges and every button, the list's name stays whole: the badges first join the subtitle as text, then a header button that still does not fit moves into the ⋮ menu as an item of the same name and action. The subtitle shortens with an ellipsis, and its tooltip is the full line. A page adds no pill or boxed list of context above its list, so the list keeps the page's height.
- **Toolbar buttons:** Buttons in any bar follow the Flat Toolbar Rule and use the Control radius. Back and section buttons are flat, as libadwaita's. Close is a circle with a tonal fill (`--sb-raised-bg`). A pill is for a primary text button in open space, and a circle for Close and for an icon-only suggested action (see Shapes). A toggle button in a bar is flat; when on, it takes a neutral fill with Accent on its icon (see Active State, and Buttons, Toggle button).
- **Grouping (HIG Header Bars):** Related buttons in a bar (back and forward, for instance) are grouped by a gap of `12px` between sets (libadwaita's spacer), not by joining them into a linked strip: a linked button keeps its background in a bar. A split button, one button with a connected drop-down, is the other way to group. A label-only button, a suggested or destructive button and a linked button are avoided in a primary window's bar; give a label-only button an icon instead. An action dialog's bar keeps its label-only buttons.
- **Composer:** A bottom bar that holds a text input stays available for writing, keeps the input central, and adjusts to keyboard and safe-area changes without covering the content. Adjacent bars join into one stack on the Bottom bar layer, split by a `1px` hairline. A control that opens a chooser to put a symbol into the input sits at the end of the input, before the send button. Where the bar is narrower than about `360px` the control is not drawn and its action is the first item of the menu that holds the other additions, because a fourth button would leave the input under about `150px`. The same action has the shortcut Ctrl+. in the input, as GTK's text widgets bind it, and the page leaves the key to the browser where the browser opens its own chooser on it.
- **Bar fields:** Selects, chips, and search fields in a bar use the Control radius, a borderless raised or neutral fill, and the inset focus ring.

#### List → Split Editor
- **Pattern:** A master list beside an editor, built from libadwaita parts with `AdwNavigationSplitView` collapse rules. Libadwaita sidebars are not user-resizable and no stock widget animates from a full-width list into a split view.
- **Sidebar:** Resizable sidebar `240–420px`, default `30%`; collapse at viewport `≤768px` or Editor pane `<720px`. These are defaults; a list inside a Window may set a narrower range and an earlier collapse. Collapsed, the editor is a full-screen page with a back button and no sidebar. A list with its own sidebar of locations collapses into three pages: locations, list, and detail.
- **Divider:** The edge between two resizable panes is a `1px` line at the border strength; a wide handle is `5px` with a `1px` line on each side.
- **Editor body:** Text-first editors keep the pane from scrolling: text areas take the remaining height (`flex: 1 1 0; min-height: 0`) and scroll internally. Multi-group editors scroll one body container; the shell and detail frame do not scroll. Main text areas there have a minimum height and Expand rather than competing for leftover height; on phones the focused text area stays visible as the visual viewport changes. Header and property controls stay outside the body; avoid nested group scrollers.
- **Explicit save:** The editor header shows, in this order, Back where the editor is a pushed page, an editable title, a dirty indicator, the token count, Edit/Preview where the editor has it, the item menu, Cancel, and Save, with the same control shapes and tooltips in every editor. Where the header collapses for a phone, the token count moves to the second row as a dimmed Caption toward its inline end: into the toolbar of a single-content editor, before its trailing toggles, in its short form (the full count stays in its accessible name), or beside the property summary of a list-content editor, outside the summary button; the context warning stays attached to it. Cancel discards local changes without closing the page. Back, row switches, and navigation ask first, with Cancel, Discard in Destructive Red, and Save as the suggested response, as libadwaita's save-changes alert, and keep a recoverable draft.
- **Property bar:** Item properties sit in a bar directly under the header. On collapsed layouts the bar becomes a `44px` summary button that opens a sheet holding the same controls, not copies.
- **Secondary pages:** Settings and overviews that belong to a list open from its ⋮ as detail pages, not as fixed list entries. Each has an in-pane Back and one scrolling body.

#### Selection Mode
- **Use (HIG Selection & Edit Modes):** Entered deliberately, and only offered when at least three actions apply to a selection. Clicking anywhere on a row toggles its selection. The checks sit at the start of the row and are `28px` circles on every device (libadwaita's size), with a `2px` outline at 15% of the body colour, filled with Accent and the shared check glyph when selected. Under `prefers-contrast: more` the outline takes the high-contrast border strength (50%), and 60% on hover.
- **Entering:** Outside selection mode a check shows over each item on hover; pressing it selects the item. A secondary click or a long press on an item also selects it. Where a secondary click on an item already opens that item's menu, the menu holds a Select item instead, no check shows on hover, and a long press on touch still selects. Once one item is selected, selection mode is active, with the header and the action bar below.
- **Edit mode:** Where each item has two or three actions that fit over or beside it, use edit mode instead: the actions show inline on every item. A dedicated Edit button enters it and a Done button leaves it. If editing is the main way users work with the collection, show the controls by default and have no mode.
- **One action (HIG Selection & Edit Modes):** The HIG offers selection mode when at least three actions apply. Deviation: a collection whose only action on several items is a destructive one, such as deleting, may offer selection mode with that one action, because the mode still gives what deleting item by item lacks: a count, a range, Select All and one confirmation that states how many items go. Its action bar holds that action alone. Review when the HIG changes this rule.
- **Range:** On a fine pointer a Shift-click takes a range. Where the natural range is one item and everything after it, the action bar also has Select to End, which only a coarse pointer shows; it takes every item from the first selected one to the end, so a touch screen reaches the range that Shift-click gives.
- **Header:** Cancel is at the start, a live selected-count title in the middle, and Select All at the end. Both buttons are raised text buttons (`--sb-raised-bg`), never a solid Accent button. Keep labels readable in forced colours and at user font scale.
- **Window header:** Selection mode replaces the header content. Close stays visible and other header controls are hidden. An open search closes, and its query returns on exit. When the count does not fit beside the buttons, it moves to a second header row.
- **Action bar:** The action bar sits at the bottom. A consumer may opt in to icon-only actions under the overlay breakpoint; the icons spread evenly, the bar is `44px` tall, and each action keeps its `aria-label` and `title`.
- **Scope:** Select All covers only the current filtered items and counts a duplicated item once. Selection gestures, keyboard behaviour, and focus return are the same wherever selection mode is used.

#### Side Panels
- **Implementation:** `registerSidePanel` and its options are in [docs/dialogs.md](docs/dialogs.md#side-panels).
- **Use:** Non-modal utility panes that keep the main view available, such as a notes or tools pane. Panels do not use a scrim or focus trap.
- **Docking:** Dock into the gaps beside the main view. Width is `280–420px`; the main view keeps its width and moves as little as possible to make room, and a panel never covers the main content column or top bar. The rule holds at every width of the desktop layout, down to the sheet threshold, so the main view does not change width at a breakpoint. When the main view would be narrower than `360px`, the main view returns to its normal width and the panels become sheets. In the mobile layout (`768px` and under) a panel never docks: it is a sheet, as an overlay split view collapses at its breakpoint. Deviation: libadwaita sidebars are `180px` to `280px` wide; SillyBunny side panels are `280–420px`, because a side panel holds a form, and under `280px` its labels wrap and its title is lost. Review when libadwaita changes this range. Deviation: libadwaita's overlay split view gives the content the width that the sidebar leaves; SillyBunny keeps the main view at the width the user set beside a docked panel, because that width is the user's choice. Review when libadwaita changes how the content of an overlay split view is sized.
- **Surface:** The Window layer with a `1px` border and square corners. A docked panel has no shadow. A panel sheet follows the Dialog surface.
- **Sides:** Each panel has a default side, and its header menu offers Move to Other Side. Two panels on one side split the available height. Save the side through the existing `movingUIState` keys; opening a panel is not persisted.
- **Default side (HIG Utility Panes):** A panel that affects the main view defaults to the start side; a subordinate one defaults to the end side. A panel that the user can show and hide uses F9 as its shortcut. A panel may be permanent or transient: transient ones are shown on request or while a feature is in use.
- **Sheet:** At most one panel at a time, persistent and non-blocking above the bottom bar, at most `50dvh`; the bottom bar remains visible and usable. It has its own scrolling, a grab handle, and Close.
- **Keyboard:** Escape closes the panel. Opening moves focus into the panel; closing returns it to its opener.

#### Illustrations
- **Pixel art:** drawn at a whole number of device pixels per art pixel (the screen scale rounded, at least 1), so a picture is the same size everywhere on one screen. Where no whole step fits, it is shrunk by a fraction and drawn smooth, never in uneven blocks.
- **In a Dialog or Window:** beside the content when the content column keeps its minimum width (`360px`, scaled with the text size) and the illustration fits the window's height; the window then grows by the illustration's width and does not narrow while it is open. Otherwise above the content, at most 30% of the viewport height, and hidden when too little of the figure would show.
- **Rows beside pixel art:** Deviation: in a Dialog or Window that shows pixel art, rows are at least `44px` tall (`52px` with a subtitle), with `16px` at their sides and `12px` between their parts, instead of the Boxed List row metrics, because the art lands on whole device pixels only at the window heights that these rows give. Review when the art's place no longer depends on the window's height.
- **Outside the shell:** a page shown before or beside the shell, such as a sign-in page, follows the same rule as a Dialog or Window, with the page's content column in the place of the window.
- **Accessibility:** a decorative illustration is hidden from assistive technology (`aria-hidden`, `alt=""`) and takes no focus.

### Navigation

#### Shell
- **Primary surface:** The main content view is the primary surface; a bottom bar holds the direct actions on it.
- **Top bar:** An always-visible top bar with a start group, a centred title, and an end group (HIG Header Bars). The title shows the name of the open item by default. Either group can hold an extension slot and configurable quick-access slots. Deviation: the HIG, and Layout, ask that the same functions stay available at every width; SillyBunny shows optional quick-access controls only where the bar has the width, which is on desktop, because a narrow bar has no room for them. This is the exception to that rule. Review when the HIG changes this rule. Deviation: the HIG asks a header bar for only a small number of controls; SillyBunny's top bar holds more, because this is a deliberate design decision. Review when the top bar is redesigned.
- **Settings:** Settings open as a full-screen page: a sidebar of pages with its own heading and settings search (HIG Sidebars), and a content pane headed by the page title and description. On the desktop layout the sidebar takes the split view width (see Pages and Sidebars) at every window width. The content of a page is clamped and centred in the pane, and the content bar keeps the full width of the pane with its title centred in it, as a header bar does. The clamp is libadwaita's `AdwClamp`: the content is as wide as the room between the page's side paddings up to the tightening threshold, grows less than the room beyond it, and stops at the maximum. Every page has the same side padding (`12px`) at every desktop width, as the margins of an `AdwClamp` are constant, so no page steps in width as the window passes a breakpoint. A preference page, whose rows sit in boxed lists, has a maximum of `1000sp` and a threshold of `667sp`. A page of lists, editors or grids is a visible frame that scrolls inside itself, so the frame is the clamped content and its scrollbars stay in it; its maximum is `1440sp` and its threshold `960sp`. In both the threshold is two thirds of the maximum, a value `AdwClamp` allows. A preference page scrolls in an element that spans the pane, so its scrollbar stays on the pane's end edge. The clamps apply from `769px`; the phone layout has none. Deviation: libadwaita clamps a preferences page to `600sp`, a width that suits a preferences window at its usual size (GNOME Settings opens at 980×640); SillyBunny clamps it to `1000sp`, because its settings fill the whole window, its rows hold sliders with number fields, segmented controls and action buttons, which need more width than libadwaita's switch and combo rows, and its settings carry long row descriptions from upstream SillyTavern, which a `600sp` column wraps onto two or three lines. Review when the rows of these pages need no more than a `600sp` column, or when libadwaita changes this value. A desktop preference turns the clamps and the Window ceiling (see Dialogs, Tiers) off, so content takes the full width of the pane and the sidebar rule stays. Deviation: libadwaita has no preference that turns the clamp off; SillyBunny offers one on the desktop, on by default, for users who prefer content at the full width of the window. Review when the HIG or libadwaita offers an equivalent, or when users no longer choose the unclamped view. Page labels are nouns in header capitalisation and of similar length. Settings that the application ships, the settings of its bundled extensions included, are built from the shared rows; the settings of third-party extensions keep their own markup and take only the restyled shared fields. Deviation: the HIG asks that, in preferences, one page's controls never change the controls on another page (HIG View Switchers); SillyBunny lets a setting that selects a mode decide which controls other pages show, because upstream SillyTavern behaviour depends on it. Review when upstream behaviour changes. Deviation: libadwaita gathers preferences in a dialog (see Dialogs, Preferences dialog); SillyBunny opens settings as a full-screen page with a sidebar of pages, because the settings fill more pages than a dialog holds. Review when the settings surface is redesigned.
- **Optional bars:** The user can hide optional bars in settings.

#### Pages and Sidebars
- **Depth (HIG Navigation, Browsing):** Hierarchies are generally one level deep below a view. A pushed page has its Back control at the top start. Close, where it shows, closes the whole frame.
- **Sidebars and panes (HIG Sidebars, Utility Panes):** A sidebar navigates between locations, such as a list of items to open or the list of a List → Split Editor. A utility pane holds tools or details for the main view, such as a settings pane. Both collapse at narrow widths: a sidebar becomes a pushed navigation stack, as `AdwNavigationSplitView` collapses, and a utility pane overlays the content or becomes a page.
- **Split views (`AdwNavigationSplitView`, `AdwOverlaySplitView`):** By default a sidebar takes 25% of the width, between `180sp` and `280sp`, and the content takes the rest; collapsed, it uses its maximum width where it fits. A pattern in this document that gives its own width (List → Split Editor, Side Panels) uses that width. A navigation split view collapses into a navigation stack with the sidebar as its root page; the content page's header bar then shows Back and the page title. An overlay split view collapses by hiding the sidebar and showing it above the content on request: a toggle button for it appears at the start of the content's header bar, and the primary menu button moves from the sidebar's header bar to the content's. The overlaid sidebar uses the Window colour, dims the content with the shade colour and casts a `56px` shadow from its edge, as a pushed page does (Page Transition Shade). On touch, an edge swipe shows it and a swipe from the sidebar hides it; Esc, or a press on the dimmed content, hides it while collapsed. A sidebar can sit before or after the content.
- **Sidebar parts (`AdwSidebar`, `AdwViewSwitcherSidebar`):** An optional prefix above the list and an optional suffix below it, each with `6px` margin (header bar controls that affect the list go above it). A row is at least `36px` tall, with `3px 14px` padding, `12px` between its icon and text, the Control radius and `6px` margin at its sides. Section headings use the Title role. A row can show a badge: a pill in the body colour at 40% with white bold text, at least `1.6em` high and wide, `6px` padding at the sides; a dot is `8px`. A row that needs attention uses Accent and its ink. A count above 999 reads "999+". Every badge has an accessible name. An empty sidebar shows a compact status page.
- **Active State:** Use a neutral selected fill, with Accent on the icon where it helps; a toggled button in a bar follows the same rule. No border, bottom accent stripe, or underline. Never use a thick left or right stripe.

#### Tabs and View Switchers
- **Tabs (HIG Tabs):** Tabs let a window hold a changeable set of content items, such as pages, documents or images; they suit editors and browsers, not a fixed set of sections (use a view switcher for those). A tab has a label and an icon only where an icon is needed. Keep labels short with the useful part first, so the label still works when it is cut with an ellipsis. The tab bar may always show, or hide until there is more than one tab. Each tab has a context menu: Move to New Window where that exists, Duplicate, Pin or Unpin, Mute and Reload where they apply, and Close last; avoid "left" and "right" in its items. The bar uses the Header bar colour with a `1px` shade line below it, at least `34px` tall. A tab is at least `26px` tall with `4px` padding and the Control radius; the selected tab uses the neutral selected fill, hover 7% and pressed 16%, and a lone tab has no fill. A tab's close button is a `24px` circle. Under `prefers-contrast: more` a hovered, pressed or selected tab adds a `1px` ring at the border strength. A `2px` Accent line at 50% (full Accent under `prefers-contrast: more`) shows where a dragged tab will land. Keys: Ctrl+Tab and Ctrl+Page Up or Page Down switch tabs, Ctrl+Home and Ctrl+End go to the first and last, Alt+1 to 9 go to one of the first nine.
- **View switcher (`AdwViewSwitcher`, HIG View Switchers):** A control for switching between three to five predefined views; more views suit a sidebar. Labels are nouns in header capitalisation and of similar length. Each button has an icon and a label (an exception to icon-or-label), and can show activity: a dot for new content, or a count (`999+` at most). In a header bar the buttons sit side by side, `3px` apart, `34px` tall, with `12px` side padding and `6px` between icon and label. When the header bar is too narrow for them, the switcher leaves it and a bar at the bottom edge takes its place, where each button shows its icon above a label at `0.75rem`. The bottom bar shows only with two or more views. The width at which this happens has no fixed value: it depends on the number and length of the labels (libadwaita uses `550sp` in its example and `110pt` for each page in its preferences dialog), so test it with the longest translations.
- **Inline view switcher (`AdwInlineViewSwitcher`):** The same switching placed in the content instead of the header bar: a toggle group whose toggles are the views, each showing an icon, a label or both, set once for the group. It takes the flat and round variants of the toggle group. Its toggles carry the tab role and its group the tab list role. A toggle can show a dot or a count. Dragging an item over an inactive toggle and holding for half a second switches to that view. Use it to switch between views of one piece of content; use the header bar switcher for the main views of the window.

#### Search
- **Behaviour (HIG Search):** Live as the user types, across the whole collection, with a status page when nothing matches. A search that filters rows hides the rows that do not match, for assistive technology too, shows how many rows match in each section it covers, and marks the matched text where the engine can. Every item stays reachable without search.
- **Placement:** Search sits in the header, revealed from an icon where space is short; Esc closes an open search before anything else. Filters sit beside the field or in the header, never in the ⋮ menu.
- **Activation (HIG Search):** The search bar slides down from under the header bar and stays hidden until the user activates it, in one of three ways: typing while no field has focus, Ctrl+F, or the header button, which toggles. Where search is central to the application, the field may stay visible elsewhere.
- **Tolerance:** Search accepts mistakes (approximate matching, suggestions of similar or related items) and broad terms: a list of cities can match a country or region. Results show as they are found, with the most relevant first. Deviation: a search that filters rows by their titles matches each word of the query at the start of a word, and does not match approximately, because a title is a few words and an approximate match would let unrelated rows through in a list of hundreds. Review when such a filter ranks its results.
- **Global search:** The entry is a borderless raised field with the Control radius and the inset focus ring. Results sit in a popover with flat rows, filled only on hover, press, or keyboard selection; group headings are dimmed.

### Controls

#### Buttons
- **Primary:** A libadwaita suggested action: Accent background, `--sb-on-solid-accent` text, `38px` minimum height (`44px` on coarse pointers), and `9px 12px` padding. Hover changes the fill slightly; there is no lift. A view has at most one button in the suggested or destructive style (HIG Buttons). Deviation: an alert in which more than one response destroys something that cannot be restored, such as deleting one item or all of them, shows each of those responses in Destructive Red, because a response in another style would read as the safe choice. Review when the HIG covers alerts with several destructive responses. Icon-only suggested actions, such as Send, are solid-accent circles. A disabled suggested button fades with libadwaita's disabled opacity (`50%`, `40%` under `prefers-contrast: more`).
- **Content:** Outside the top bar, a button shows an icon or a label, not both (HIG Buttons). The arrow on a button that opens a menu or expands content shows the button's state and is not an icon in this sense. Labels are short imperative verbs in header capitalisation ("Save", "Update"). A button whose action is unavailable is insensitive instead of showing an error when clicked. No actions on double-click or right-click of a button. Existing buttons that pair an icon with a label move to this rule as each surface is reworked.
- **Shape:** A button is a rounded rectangle at the Control radius. A pill has a full radius and `10px 32px` padding; a circle is `34px` at least. Shapes states where each applies.
- **Widths:** Use one or two button widths in a window, and give buttons side by side the same width.
- **Toggle button:** A button that switches between two states looks pushed in when set: a 30% fill, 35% on hover, 40% pressed. Use it for a mode or setting with an obvious binary nature where space is limited, as an alternative to a switch. A choice between several short options is a toggle group. In a bar a toggle button follows Active State.
- **Secondary:** A secondary button is a libadwaita raised button: a `10%` body-colour fill at rest (`--sb-raised-bg`), `15%` on hover, and `30%` when pressed, Foreground, at the same height and padding as the primary family. A flat button is transparent at rest and uses the flat fills (see the Flat Toolbar Rule). A button that keeps upstream markup also keeps its `1px` theme border. Deviation: libadwaita buttons have no border; SillyBunny keeps the border on buttons with upstream markup, because user themes style that markup. Review when those buttons are rebuilt.
- **States:** Default, hover, focus-visible, active, disabled, loading, and error are explicit. Focus-visible shows the inset ring with no outer glow. Every icon-only button has an accessible name and a tooltip. Fills use `:active`, so they do not stick after a tap. Selected tabs and nav items use a neutral fill without a bottom accent stripe or inset shadow.

#### Text Fields
- **Style:** Window background (`--sb-input-bg`), a `1px` theme border, the Control radius (`9px`), `--sb-field-min-height` as the height (`46px`, `40px` in compact, `44px` on a coarse pointer), and `12px` inline padding. Deviation: libadwaita fields are a `10%` fill without a border; SillyBunny keeps the Window colour as fill and a `1px` border, because a `10%` fill alone is about 1.4:1 against the window, so the border marks the field's edge. Review when libadwaita changes this value.
- **Focus:** The border turns `--sb-entry-focus-border` and a `1px` inset `--sb-entry-focus-ring` in the same colour completes a `2px` ring in the focus-ring colour (see Focus Ring). The fill does not change. A standalone field draws focus on the input; an entry row draws it around the whole row (see Entry rows). A multi-line input in a bar, the composer, keeps its own accent outline (`--sb-composer-focus-*`).
- **Behaviour (HIG Text Fields):** In forms and preferences, prefer entry rows to standalone fields. A field that holds a setting applies its change on Return or when it loses focus. Validation feedback appears as the field is edited and favours a positive "valid" cue over showing an error while the user is still typing. Placeholders read like labels, or as an instruction ending in an ellipsis for action fields ("Search for a city…"). Typing never starts a network action; connecting and testing stay behind explicit buttons.
- **Entry rows (`AdwEntryRow`):** The row is the field: it has no inner fill, border or radius, and its text sits in the row's editable area, `12px` from the row's edges like any row content. The row is as tall as any row (see Rows), not as a standalone field. The title is a linked `<label>`. While the row is empty and not being edited, the title sits where the text goes, at Body size and dimmed, and doubles as the placeholder; on focus, a value, or autofill it moves above the text at Caption size, still dimmed, as `AdwEntryRow`'s. A placeholder that an adopted input carries is kept as its accessible description and is not painted. The title is single-line with ellipsis and remains the accessible name. An edit icon at the end of the editable area, a `16px` symbolic icon in the text colour, marks the row as editable while it is not being edited. While the text has focus, the whole row carries the focus ring, inset by `1px`, and hovering does not change its fill; prefixes and suffixes (Reveal, key buttons) sit inside the row and inside the ring. A vertical separator, the height of an icon button in the row's separator colour, sets the buttons after the field apart from it and its edit icon, as GNOME Settings draws one before a row's separate button. A short value that may still hold a line break (a name, a version) keeps its multi-line control in the row: it shows one line and grows with its text, to about five lines. Existing stacked fields remain until each surface is migrated.
- **Secret fields:** Saved or missing key status is an icon with visually hidden text at the end of the field, before the edit icon, where `AdwEntryRow` keeps its indicator; an unknown status is hidden. Mask and offer Reveal only where `-webkit-text-security` is supported; never change the input type or invite a password manager. Deviation: libadwaita and the HIG use a dedicated password entry; SillyBunny masks an upstream text input and keeps its type, because this preserves upstream text inputs and avoids password-manager prompts. Review when upstream inputs change. Deviation: the HIG allows a boxed-list row at most two controls; a secret row may hold three (entry, reveal, and key management), because the function needs all three. Review when the HIG changes this rule.
- **Caps Lock:** A secret field shows a Caps Lock indicator at its end, a quiet icon at 30% (80% under `prefers-contrast: more`), while its text is masked and Caps Lock is on. It does not show while the text is revealed.
- **Help captions:** One-line help is a dimmed Caption below the field, linked by `aria-describedby`. Multi-line instructions and lists stay above the field, and visibility-gated warnings keep their gates. Deviation: `AdwEntryRow` has no subtitle; SillyBunny shows captions, because they preserve upstream help and status. Review when libadwaita adds a subtitle to entry rows.
- **Error / Disabled:** Destructive Red uses a readable tint and explicit text; disabled fields preserve label and layout context rather than disappearing.

#### Selection Controls
- **Choosing a control (HIG Switches, Checkboxes, Radio Buttons, Drop-Down Lists, Sliders, Spin Buttons):**
  - A switch is for an option with a clear binary nature, and is preferred to a checkbox for settings.
  - Checkboxes are for lists of independent choices, mixed states, and menu items. Label them by their checked effect and never negatively ("Play alert sound", not "Disable alert sound").
  - Two exclusive options use a segmented toggle or radio buttons, never a drop-down. Small exclusive sets use radio buttons or a segmented toggle; longer sets use a drop-down, with search for long lists.
  - A slider is for a fixed, ordered range with live feedback; pair it with a number field when exact values matter. A spin button is for an exact value, right-aligned.
  - A control that enables others sits directly above the controls it affects.
- **Hierarchy:** One boolean option uses a switch row. A pick-several list uses a check row per item, with Select All when there are more than five items. Two or three exclusive options use a segmented toggle; four or more use a combo or searchable select row.
- **Toggle group (`AdwToggleGroup`):** A set of exclusive toggles, each an icon, a label, both, or custom content; for a few options that short labels can express (HIG Buttons). It is a tray: the raised fill (the body colour at 10%) with `3px` padding and the Control radius. A toggle is bold, at least `28px` tall, and at least the target floors of Layout (`32px` with a fine pointer, `44px` with a coarse one) (`34px` wide for an icon), with a radius of `6px` and `8px` side padding around a label. The selected toggle is raised: white at 20% on the dark tone and white on the light tone, with two soft shadows (`0 1px 3px 1px` at 7% and `0 2px 6px 2px` at 3% of the shade colour). Hover fills a toggle 7% and press 16%. Under `prefers-contrast: more` the tray, a hovered or pressed toggle and the selected toggle gain a `1px` ring at the border strength. A disabled group fades its tray to the disabled strength. Focus draws the ring outside the toggle. A thin separator sits between toggles and is hidden beside a toggle that is selected, hovered or has keyboard focus. Variants: round (a pill tray, `17px` radius, `12px` side padding on labels), flat (no tray; the selected toggle is the neutral selected fill at 10%, 13% on hover, 19% pressed) and vertical (for icon-only toggles). An icon-only toggle has a tooltip, which is also its accessible description. Each toggle has the radio role, or the tab role when the group switches views. Tab moves focus into the group at the selected toggle and out of it again; arrow keys move between toggles. When space is not limiting, radio buttons are the better choice.
- **Checkbox:** Rounded square with a `2px` neutral outline at rest. Checked fills solid Accent with a check glyph in `--sb-on-solid-accent`. No highlights, glow, or inner shadow.
- **Mixed state:** A checkbox for a setting that holds for some of the selected items and not others shows a mixed state: the Accent fill of a checked box with a dash in place of the check. Pressing it once checks it and applies the setting to every selected item; pressing again unchecks it and clears the setting everywhere; a third press returns it to mixed and restores each item's own value.
- **Radio:** Circle with the same `2px` outline. Checked fills solid Accent with a centered dot in `--sb-on-solid-accent`. Segmented boolean radios keep their overlay input and are styled as the segment instead.
- **Range:** `4px` trough at `15%` of the body colour (libadwaita's trough) and an `18px` Accent thumb with a `1px` shade. Firefox fills the trough up to the value; WebKit and Blink show the trough only. Hover grows the thumb slightly on hover-capable pointers. When a row is too narrow to hold the title, the range, and the number field side by side, a slider row stacks its range and number field under the title. Deviation: libadwaita's range has a white thumb; SillyBunny's thumb is Accent, because libadwaita's next release changes the range again, so restyling it now would be done twice. Review when libadwaita 1.11 is released. Deviation: libadwaita's range fills the track up to the value; in WebKit and Blink SillyBunny shows the trough only, because those engines expose no pseudo-element for the filled part. Review when libadwaita 1.11 is released.
- **Switch:** A pill `26px` high, with a `20px` thumb and `3px` of padding around it, as libadwaita's, and wide enough for the thumb to travel its own width (`46px`); `38×22` in compact mode. It sets `appearance: none` and `-webkit-appearance: none`. Off uses a `15%` body-colour trough (the same trough as the range); on fills solid Accent with a circular thumb in `--sb-on-solid-accent`. The thumb travels with `inset-inline-*` so RTL mirrors. Reduced motion snaps with no travel.
- **Focus / Disabled:** Small controls use a `2px` focus-ring outline with an offset so the ring stays visible around the control. Disabled controls fade to the disabled opacity and show a `not-allowed` cursor.

#### Chips
- **Style:** Compact controls at the Pill radius, `3px 9px` padding, readable text, and a tonal background.
- **State:** Enabled or selected chips use a 16% Accent tint and a status icon. Inactive chips remain legible and low emphasis.
- **Tag lists (HIG Text Fields, `AdwWrapBox`):** A set of chips flows like words in a line: it wraps to the next line when the next chip does not fit, with a gap between the chips of a line and a gap between lines. A tag field shows each value as a chip inside the field, so it reads well and each value can be removed; it needs a custom implementation, as no standard field has tags. An editor's tags are one row that opens the shared picker, as a single choice does: the row's dimmed subtitle names the applied tags (two lines at most) and its value is their count; the picker ticks them and lists them first, each with a dot in the tag's colour, and a search that names no tag offers to create it. The row stays one row however many tags there are.
- **Status chips:** A non-interactive chip that names a row's state in words, placed before the row's buttons. A positive or finished state (Installed, Enabled, Done) takes a 16% Success Green tint and a leading check in Success Green; any other state (Not installed, Skipped) takes an 8% body-colour tint and no icon. The text uses the strong contrast ink rather than the body colour, so it reaches 4.5:1 on the tint in every bundled theme, and the check reaches 3:1. The words always carry the state; colour and the check only reinforce it.
- **Counted toggle chips:** A short row of chips under an item that people answer with a symbol, such as a message: one chip per distinct symbol, in the order each was first chosen, `4px` apart and `12px` between rows when they wrap, and no row at all while nothing was chosen. A chip is a toggle for the user's own choice: it is pressed when the user is among those who chose that symbol, and pressing it adds or takes back only the user's own choice, never anyone else's. It shows the symbol first and the count after it, from two choices on, in tabular figures in the text face, so a single choice shows no number. A pressed chip takes the 16% Accent tint, an Accent ring and a heavier count, and an unpressed chip an 8% tint with a ring at 26% Accent, so that colour is never the only cue. The ink is the body colour in both states, because a lighter ink on the tint is under `4.5:1` in a quarter of the bundled themes. Who chose a symbol is never behind hover: a secondary click, Shift+F10 or the Menu key on the focused chip, or a long press on touch, opens a popover at the chip that lists the people, the user first, each with their picture and name; the chip's tooltip repeats the names as a hint only, and the click that ends a long press does not toggle. A long press on the chip belongs to the chip, and the long press that starts selection on its row does not take it. The accessible name is the name of the symbol and the count ("Red Heart, 2 reactions"), and the pressed state is `aria-pressed`; the people are in the list, not in the name. A chip is drawn at `24px`, and at `32px` on a coarse pointer, and meets the touch-target floor through a hit area past its border: at least `32px` on a fine pointer and `44px` on a coarse one. The hit area takes only the room that the gaps leave, so that those of neighbours and of two rows never overlap, and it adds nothing to the height of a row. An item holds at most 20 distinct symbols: past that a symbol that is already there can still be toggled, and a new one is refused with a toast. A person counts once for a symbol.
- **Use:** Chips carry compact controls and metadata, and status chips sit in list rows; do not collect many chips in one bar.

#### Avatars and Overlaid Controls
- **Avatar (`AdwAvatar`):** A round image of a person or an entity. With no image it shows the initials of its name, in bold, on a gradient chosen by a hash of the name, so a name always gets the same colour; with no name it shows a generic person icon. Its size comes from the layout that holds it. It is an image to assistive technology, named by the name it shows.
- **Overlaid controls (HIG Overlaid Controls):** Semi-transparent controls that appear over content when the pointer moves over it, when it is tapped, or when focus enters it, so fewer controls show while the user is not interacting. Use them for content that is watched or read, not for content that is edited: where they would hide what the user needs to see, put the controls beside it. Follow the convention of the content: browse buttons at the left and right edges of an image, player controls at the bottom edge of a video. They attach to an edge or float. The fill is black at 70% and the ink white at 90% (the OSD colours); an OSD button is black at 65% and at least `32px`, and under `prefers-contrast: more` it gains a `1px` ring in its ink colour.

### Feedback

#### Toasts
- **Which messages are toasts (`AdwToast`):** A plain message: no title, at most one block of text and at most one button, no click action, and text that fits on one line within `34em` at the toast's font size. The width is measured against `34em`, never against the window, so a message takes the same form in every window. Every other message is an in-app notification (see In-app notifications).
- **Surface:** Popover layer and ink in both tones, as an in-app notification, a pill shape (libadwaita's toast radius is `150px`), Popover Shadow with its `1px` ring, no border. The label is bold (libadwaita's `heading`, the Title role). Text without a link takes the toast's ink. Deviation: libadwaita draws its toast in a dark grey (`#505053`) with white ink in both styles, so that it stands out over the content; SillyBunny draws it in the colours of an in-app notification, because a toast and an in-app notification often show at the same time, and two tones side by side read as two unrelated systems. Review when libadwaita changes the colour of its toast.
- **Status:** An error, warning, or success toast shows a status glyph at its start in the standalone status colour of the tone, as the icon of an in-app notification; an info toast has none. Deviation: libadwaita toasts have no status and no icon; SillyBunny shows the glyph, because the status comes from upstream SillyTavern's interface for raising a toast, and the colour of the label alone cannot carry it (a status never relies on colour alone; see the Contrast Rule). Review when libadwaita gives a toast a status.
- **Use (HIG Toasts):** Transient and dismissible, for events and completion summaries that only matter while the app is open. A button only when it is directly useful, such as Undo after a reversible destructive action. A toast is never the only place a persistent failure or state is shown.
- **Parts:** The label, then at most one button at the end of it, then a close button on every toast: round and flat, with "Dismiss" (libadwaita's string) as its tooltip and accessible name. Tapping or clicking the toast itself does nothing. The targets keep the floors of Layout.
- **Timing and queue:** A toast stays for 5 seconds (libadwaita's default); a toast with no timeout stays until it is dismissed. It does not disappear while it is hovered, pressed (on touch) or has keyboard focus inside it. It shows and hides over `300ms` (see Motion, By Pattern). A second toast waits behind the first; a toast of high priority, such as an Undo, shows at once and pushes the first back into the queue. Replacing a toast takes 500ms. A toast's button runs its action once and is then disabled. Toasts and in-app notifications each have a queue of their own, so a toast and an in-app notification can show at the same time, as an application's toasts and GNOME Shell's banners are separate. When both forms are set to the same position they share one stack: the toast keeps the edge and the in-app notification sits beyond it.
- **Metrics:** A toast has `12px` margin on every side and `24px` from the window edge it sits at, `6px` padding (`12px` at the start), and `6px` spacing between its parts, each part with `6px` margin at its sides, as libadwaita's. Under `prefers-contrast: more` it gains a `1px` ring at the border strength.
- **Width:** A toast is as wide as its text, at most `34em` and at most the window width minus `24px`; with a button it is at least `450px` wide (libadwaita's `NATURAL_WIDTH`), also where `34em` is narrower, though never wider than the window minus `24px`. Deviation: libadwaita lets a toast grow to the width of the window; SillyBunny stops at `34em`, because a single line across a wide window is hard to read, and a longer text is an in-app notification. Review when libadwaita limits the width of a toast.
- **Narrow windows:** On a window narrower than its text, a toast wraps, with a corner radius of half the height of a one-line toast. A message keeps the form it was shown in: a toast whose text grows past one line after it shows wraps in the same way, and does not become an in-app notification. Deviation: libadwaita keeps a toast's title to one line and ends a long one with an ellipsis; SillyBunny wraps it, because it never cuts a message, and only a window narrower than the text, or text that grows after the toast shows, does this: text longer than `34em` when the message is made is an in-app notification. Review when libadwaita changes this behaviour.
- **Position:** Bottom centre by default (HIG Toasts), `24px` from the window edge (libadwaita's `margin-bottom`). Above a docked bottom bar, such as a composer, and above the software keyboard, a toast keeps the same `24px` from the bar or the keyboard. Deviation: libadwaita places a toast at the bottom centre only; SillyBunny lets the user choose one of six positions, top or bottom at the left, centre or right, because the user can move it to their liking, as upstream SillyTavern's position setting has always allowed. Review when libadwaita lets an application place its toasts. While a dialog is open, a toast shows at its position in the window, above the dialog and its dimming, so it can be read and dismissed; the dimming covers a docked bottom bar, so a bottom toast sits `24px` from the window edge. When the dialog is a bottom sheet, the toast sits `24px` above the sheet's top edge, and when the sheet leaves no room above it, `24px` above the sheet's bottom action row. Deviation: libadwaita shows a toast inside a dialog only when the dialog has a toast overlay of its own (its preferences and about dialogs), and draws the window's toasts under a dialog's dimming; SillyBunny shows every toast above the dialog, because one rule for every dialog is consistent and a toast may report on the content of a dialog, as extensions do. Review when libadwaita changes how a dialog shows toasts.

#### In-app notifications
- **Use:** A message with a title, several blocks of text, several buttons or a click action, and a plain message whose text is longer than a toast holds (see Toasts). It is transient, like a toast, and is never the only place a persistent failure or state is shown. Its layout is GNOME Shell's notification banner drawn inside the window, because neither the HIG nor libadwaita describes an in-app notification.
- **Surface:** Popover layer and ink, in the place of the card colour of GNOME Shell's banner, with the Overlay radius (`15px`), Popover Shadow with its `1px` ring, and no border. Deviation: GNOME Shell's banner radius is `16px`; SillyBunny uses the Overlay radius, because that token is reused and the difference is `1px`. Review when Shell changes its banner radius or the Overlay radius changes. Deviation: GNOME Shell's banner casts one shadow (`0 2px 4px 2px`) and has no ring; SillyBunny uses the Popover Shadow with its `1px` ring, because on a light page a white card separated only by Shell's shadow reads weakly. Review when Shell changes the banner shadow or the Popover Shadow changes.
- **Width:** `34em` (GNOME Shell's banner width), at most the window width minus `24px`.
- **Layout (Shell's `.message`):** `6px` padding around a content box with `6px` padding of its own. The title is bold in the ink colour and the body is regular weight, `4px` apart. There is no header row. Deviation: GNOME Shell's message has a header row with the source's icon and name, the time, and expand and close buttons; SillyBunny has none, because inside the window the application is always the source, and a transient message carries no time. The close button ends the first row (see Dismissal).
- **Icon:** A message with the status error, warning or success shows an icon at its start, aligned to the top and `6px` before the text: a `48px` circle of the ink at 7% holding the `16px` status glyph in the standalone status colour of the tone. A message with the status info has no icon (Shell's icon is optional). Deviation: the icon of a GNOME Shell message is that of its source; SillyBunny's icon shows the status of the message, because the title is in the ink colour, as Shell's, so the status shows in the icon. Review when the HIG or libadwaita describes an in-app notification.
- **Expansion:** An in-app notification is always expanded: its full text and its buttons are always shown. Deviation: GNOME Shell shows one line of the body, up to six lines when expanded, and shows the buttons only when the banner is expanded by the pointer moving into it; SillyBunny always shows the full text and the buttons, because touch has no hover and an error message must not be cut. Review when Shell changes this behaviour.
- **Buttons:** The buttons of the message sit in rows under the body, three to a row, of equal widths in each row, bold, with `6px 12px` padding, the Control radius and a fill of the ink at 10%. The row has `4px` padding, and buttons and rows are `8px` apart (Shell's `4px` margin at each side of a button, none at the ends of the row). These are drawn sizes; the targets keep the floors of Layout. Deviation: GNOME Shell's button radius is `8px`; SillyBunny uses the Control radius (`9px`), because that token is reused. Review when Shell changes the button radius or the Control radius changes. Deviation: GNOME Shell shows three buttons at most and drops the rest; SillyBunny starts a second row with the fourth button, because dropping a button that an extension adds would remove what it does. Review when Shell changes this limit.
- **Dismissal:** Every in-app notification has a close button at the end of its first row, with "Dismiss" as its tooltip and accessible name. A click on the card outside a control runs the message's default action, if it has one, and dismisses the notification, as GNOME Shell does when it activates a banner. A click that ends a text selection inside the card does neither, so the text of a message that stays can be copied.
- **Position:** Top centre by default, as GNOME Shell's banner, `4px` from the window edge or from the bar it sits under (Shell's banner margin). Deviation: GNOME Shell places its banner at the top centre of the screen; SillyBunny lets the user choose one of six positions, as for toasts, because the user can move it to their liking, as upstream SillyTavern's position setting has always allowed. Review when Shell lets the user place its banners. An in-app notification keeps its position in the window while a dialog is open.
- **Title capitalisation:** The informal heading style of a toast's label, in sentence capitalisation (see the Capitalisation Rule). Deviation: the HIG asks for header capitalisation in a notification's title; an in-app notification follows the toast, because its text is a toast's and only its layout follows GNOME Shell. Review when the HIG describes an in-app notification.
- **Timing and queue:** GNOME Shell's urgency: an error or a warning stays until it is dismissed, as Shell keeps a banner of critical urgency, and an info or success message leaves after 4 seconds, Shell's timeout for a banner of normal urgency (`NOTIFICATION_TIMEOUT`). A timeout that the message sets itself replaces these defaults. A notification that times out does not disappear while it is hovered, pressed (on touch) or has keyboard focus inside it, as a toast. Up to three in-app notifications show at once, the newest nearest the edge they sit at, each with its `4px` margin; the others wait in a queue of their own and show as one is dismissed, and a repeated message collapses into the one on screen. A message that the app keeps on screen until its work ends, such as a progress state, shows at once and takes none of the three places, so it never holds another message back. A toast and an in-app notification can show at the same time; when both are set to the same position they share one stack, with the toast at the edge. Deviation: GNOME Shell shows one banner at a time and keeps every banner in its message list once it leaves; SillyBunny shows up to three at once, because errors and warnings stay until they are dismissed and SillyBunny has no message list yet, so a notification waiting behind one that stays would be held back. Review when SillyBunny gains a notification centre.

#### Banners, Status Pages, and Progress
- **Banners (HIG Banners):** For persistent states only, never for events or short-lived states. One short title written as an informal heading, and at most one button. A persistent state, including an error that one action resolves, shows in a banner whose button is that action.
- **Banner placement and metrics (`AdwBanner`):** A banner is a strip across the top of a view, under that view's header bar and above its content, at the view's full width. It is hidden until the state it reports applies, and it reveals and hides with the reveal transition. It has `6px` padding and the Window ink. Its fill is a neutral step over the Window colour. Deviation: libadwaita's banner fill is a fixed grey (`#7d7d83`) at 30% over the Window colour; SillyBunny mixes the theme's body colour into the Window colour instead, because a fixed colour bypasses user themes (The Theme Alias Rule). Review when libadwaita changes this value. The title is centred or starts at the start edge, depending on the space; parts are `6px` apart, `36px` when centred, and `9px` apart when the button is stacked below the title. The button is at least `84px` wide beside the title and `160px` wide below it, in the default or the suggested style; it runs the action that resolves the state. A banner is a polite status region (`role="status"`) that is read out when it appears. Deviation: libadwaita's banner is a group labelled by its title and announces nothing; SillyBunny announces it, because WCAG 2.2 success criterion 4.1.3 (Status Messages) asks that a status message reach assistive technology without taking focus. Review when libadwaita changes this behaviour.
- **Status pages (HIG Placeholder Pages, `AdwStatusPage`):** Empty views, empty search results, and unavailable states show a symbolic icon, a heading that names the state, an optional line of guidance, and an optional action. Symbolic placeholders stay neutral in colour and tone. Deviation: the HIG gives a placeholder page a heading that names the state; an empty view whose heading upstream SillyTavern picks from a set of playful headings keeps them, with a description that names the state, because playfulness is part of SillyBunny's character (see Overview). Review when upstream drops the headings.
- **Metrics:** The default set is a `128px` icon, the title in the Display role, `36px` between icon and text, `36px` above and below the page and `12px` at its sides, `12px` between title and description; the description is Body. The compact set, for a sidebar, a popover or a pane and the default for an empty sidebar, is a `96px` icon, the title in the Headline role, and `24px` gaps and margins. The icon is dimmed (and fades to the disabled strength when the page is disabled) and is drawn with the heavier stroke (weight `134`). The text is clamped to `600px`, centred, and wraps. The page is labelled by its title and described by its description, and its icon is hidden from assistive technology. Illustrations in colour belong to the first view of an application only (HIG Placeholder Pages).
- **Inline hint:** An empty part inside a section, card, popover or pane, such as a list with no items yet, shows a one-line hint instead of a status page: a single centred line in the Caption role and the dimmed foreground, with the section's padding and no icon, title or action. A status page is for a whole view or region; in a small surface its icon and title would crowd out the content around it.
- **Loading state:** A view or region that waits for its content shows one form: a status page in the spinner form, which is the compact set with a spinner in place of the icon. The spinner is `64px` high with a thinner stroke (`6px` at that size), the title is in the Headline role, and gaps and margins are `24px` (libadwaita `.spinner` status page). The spinner is the shared spinner, never a symbolic icon, an hourglass or a font glyph that spins. The title names what is loading, in header capitalisation and without an ellipsis, such as "Loading Documents"; a description and an action appear only when they help, such as Cancel for a load the user can stop. The page takes the place of the region that is loading. It appears only after a short delay, so a quick load shows nothing, and it goes as soon as the content is ready. The region is marked busy (`aria-busy`), and the page is its label. A load that is expected to take longer than about thirty seconds, or that knows its proportion, shows a progress bar; a load inside a control shows a spinner beside it (see Progress). Deviation: libadwaita's spinner keeps turning when animations are off; SillyBunny stops it under reduced motion and shows its still arc, because the Reduced Motion Rule removes movement and the title carries the state. Review when libadwaita changes this behaviour. Existing loading views move to this form as each surface is rebuilt.
- **Progress (HIG Spinners, Progress Bars):** Show progress for any operation that takes more than about three seconds. A spinner for operations up to about thirty seconds, placed in or next to the control it relates to, shown only after a short delay, and one at a time. A progress bar with text for longer tasks, inline with the content it tracks.
- **Spinner (`AdwSpinner`, HIG Spinners):** A label beside the spinner can name the task, and a long wait can add progress to the label: a percentage, time left, or items done. The spinner scales between `16px` and `64px` to the space it is given, turns once in 1.2 seconds on a track at 15% in the body colour, with a stroke of one eighth of its size (`2px` at `16px`), and draws a still arc when it is not moving. It is announced as a progress indicator that is busy. A spinner fades to the disabled strength when its control is disabled. Existing spinning glyphs move to the shared spinner as each surface is rebuilt.
- **Progress bar (HIG Progress Bars):** The bar shows the proportion done and the time remaining. The bar is `8px` high and at least `150px` wide, fully rounded, with an Accent fill on a trough at the trough strength; its text is smaller, dimmed and in tabular figures. A bar has text: units for a short task ("13 of 19 images rotated"), or the time left for a long one, with "About" when it is an estimate ("About 3 minutes left"). A task that overestimates pauses at 100% with "Almost done"; one that underestimates skips ahead. A bar with no known proportion (activity mode) is avoided, above all for long periods, and a bar changes mode as rarely as possible. Several simultaneous subtasks show one combined bar, unless each needs its own pause or stop. A task that is destructive or resource-heavy offers Pause and Cancel. Avoid a window that holds only a progress bar. A thin bar (`2px`, no trough, no text) attached to the bottom of the header bar suits background work.

#### Tooltips
- **Surface:** libadwaita OSD tooltip: shadow ink at 80%, white text, control radius, `1px` 10% white border. Used for hover titles and the touch press-and-hold label.
- **Metrics:** `6px 10px` padding and no shadow; the gap between an icon and text inside it is `6px`. The `1px` border of white at 10% keeps it from melting into a dark background.
- **Use (HIG Tooltips):** Every top-bar control has one. Elsewhere, use them only where they add information, and if one control in a container has a tooltip, all of them do. Tooltips never carry essential information, since touch and keyboard users may not see them. On touch, press-and-hold shows the label without triggering the action. Text is short and in header capitalisation, and does not repeat a visible label: "Back", "Search", "Main Menu".
- **Standard labels:** Back; Search (with the content type where useful: "Search Documents"); Main Menu for the primary menu; Menu for a secondary menu, naming the item where possible ("Document Menu"); New Tab; Bookmarks. Where a control has a visible label, the tooltip adds information or rephrases it ("Open…" with "Select a File"). Useful tooltips for content show the full address of a link or the message of a syntax error.

#### System notifications
- **System notifications (HIG Notifications):** A system notification tells the user about an event that matters to them while they use other applications: a long operation has finished, new content has arrived, a message was received. On the web they use the Notification API. Ask whether the user needs to be told at all, limit how often one shows (a periodic summary in place of one per message), offer a way to turn them off or reduce them, and remove a system notification once it is no longer valid. Never rely on a system notification alone: the window shows the same information. A system notification has the application's icon, a title that summarises the event and is understood alone, in header capitalisation, an optional body in sentence capitalisation, a default action when it is pressed (dismiss it and show the relevant part of the window), and up to three buttons. A button relates to the content, is often needed, does not replace a control in the window and does not repeat the default action. A message that matters only while the application is in use is a toast or an in-app notification.

### Chat Transcript

A transcript is a list of messages with its own row, action, and edit patterns.

- **Transcript:** A scrolling list of message rows on the View layer, with the composer below it. A sidebar list of transcripts stays in recency order; selecting one does not move it.
- **Message row:** A message shows its sender's name and optional avatar, then its content. A row that groups consecutive messages shows the avatar, name, and time on the first of a group only; a group breaks on a change of sender, a long gap, or a day boundary. A person's own messages may align to the end edge and others' to the start edge, with a reserved avatar slot on the start side.
- **Action row:** Actions sit in the message name row at the inline end; the name truncates before they move. A row that does not fit beside the name moves below it, and section dividers hide once it wraps. Targets use `--sb-message-hit-size`, icons `--sb-message-glyph-size`, and swipe arrows `--sb-message-icon-size`, and follow the touch-target rule: at least `44px` on coarse pointers and `32px` on fine pointers, in compact density too. The set of actions shown follows `(pointer: coarse)`, not the viewport width: a coarse pointer shows fewer actions, then the menu button, and every other action is in the menu. The menu button is the vertical ellipsis and always last. In every layout variant the action row keeps this contract; a mirrored row anchors its actions and menu to its start edge. An action row may be an overlaid toolbar that appears on hover or `:focus-within` on fine pointers; a coarse pointer gets a menu trigger beside the corner (reporting `aria-expanded`) instead, so a hover toolbar is never the only way to reach an action on touch.
- **Action menu:** Every action not in the row is a labelled menu item with a dimmed icon. Sections are split by separators with no headings, ordered by importance: primary actions, copy, structure, tools, other items; then a destructive item alone, in Destructive Red.
- **Menu surface:** A popover anchored to the menu button, trailing-aligned, that flips above when there is no room below and stays inside the main content width. In the mobile layout it is a bottom sheet titled with the name of the item the menu belongs to, with Close, that traps focus. Focus returns to the menu button. Right-click on the name row, Shift+F10, and the Menu key open the same menu; long-press on message text does not, so text selection keeps working. It closes on action, Escape, outside tap, and when the content it belongs to changes, and the popover also on scroll. Arrow, Home, and End move between rows.
- **Edit row:** Cancel and Confirm first, then the item's edit actions in sections, with a destructive action alone and last in Destructive Red. Coarse pointers put them behind the menu button; fine pointers show them inline after a divider. At the ends of the transcript, Move up and Move down stay, disabled: the one exception to omitting items that do not apply. Edit buttons are flat circles whose text colour shows the role: success for Confirm, Destructive Red for Delete, the body colour for Cancel, and Accent otherwise. Cancel is neutral because Warning Yellow means caution, not cancel (HIG UI Styling). Hover and press use a `12%` and `20%` tint of the action's colour. Deviation: the HIG reserves strong colour for a single suggested or destructive button per view; SillyBunny colours several actions in one row, because each colour shows its action's role. Review when the HIG changes this rule.
- **Delete:** Deleting an item always confirms with the destructive alert (see Dialogs), whatever the user's confirmation setting, because it cannot be undone; Return never confirms a deletion.

## 9. Do's and Don'ts

### Do:
- **Do** keep main content uninterrupted and let configuration appear only after deliberate input.
- **Do** give every view at most one suggested or destructive button, then place powerful options behind learnable progressive disclosure.
- **Do** preserve SillyTavern-compatible settings, character data, chats, presets, extensions, and migration paths.
- **Do** use `SmartTheme*`, `sb-*`, `color-*`, spacing, and radius tokens so user themes continue to work.
- **Do** keep desktop and mobile gestures, ordering, labels, and action vocabulary consistent.
- **Do** provide visible focus, semantic labels, comfortable touch targets, resilient wrapping, and reduced-motion behavior.
- **Do** use tonal surfaces before shadows and verify text contrast before shipping.
- **Do** make every action possible with the keyboard as well as with a pointer or touch. Custom shortcuts use Ctrl with a letter, never Alt (reserved for access keys) or Super. Support the standard navigation keys on custom controls: Tab and Shift+Tab move focus, Ctrl+Tab moves it where Tab has another function (a text field), Return activates, Space toggles, F10 opens the primary or secondary menu, Menu or Shift+F10 opens the context menu for the focused item, and arrow keys move around a group of related controls. A control's label immediately precedes it in the focus order. Esc closes popovers, sheets, and dialogs (HIG Keyboard, Popovers, Windows).
- **Do** test every surface with a high-contrast or forced-colours mode, 200% text size, the keyboard alone, a screen reader, and an on-screen keyboard (HIG Accessibility). Every element has a short, descriptive accessible name.
- **Do** write UI text by the HIG Writing Style: short and neutral, familiar terms over system terms, "your" over "my" when ownership must be stated, no Latin abbreviations ("for example", not "e.g."), and no trailing period: labels, headings, and descriptions end without one, a description written as a full sentence included; periods only separate the sentences of a paragraph or end longer text of several paragraphs. An ellipsis (`…`, U+2026) ends a label only when more input or confirmation follows ("Delete…", not "Preferences…"). Never build one sentence from several strings or controls, so translations stay intact. Use typographic characters: “quotes”, ’ apostrophes, – ranges, × dimensions, a bullet `•` (U+2022) in an inline list, and a narrow no-break space (U+202F) between a number and its unit ("32 GB") (HIG Typography).
- **Do** translate each new counter or sentence as one string with placeholders, never joined fragments. Use `…`, never three periods, in new labels. Reuse existing upstream strings and keys verbatim, including trailing periods; the punctuation rule applies to new copy. Unsupplied descriptions, help, and dialog bodies use exactly `TODO(copy)`, marked with `data-sb-copy-placeholder="true"` and reported for maintainer replacement; do not draft project prose.

### Don't:
- **Don't** add configuration panels, extra toolbars, or utility panes to the main content view unless the user opens them. Navigation sidebars, split views, and utility panes follow the HIG (Navigation): each view keeps one clear subject, and panes collapse or overlay at narrow widths.
- **Don't** create a nested menu spiral: no nested submenus in menus that SillyBunny builds, and hierarchies generally one level deep below a view (HIG Menus, Navigation).
- **Don't** present configuration sprawl, bottom bar bloat, or a dense control wall by default.
- **Don't** rely on mystery meat navigation, hover-only discovery, desktop-only assumptions, tiny touch targets, or fragile iOS WebKit behavior.
- **Don't** use generic SaaS polish, sterile upstream-clone blandness, or decorative motion without navigational purpose, except an illustration moving in place (Motion).
- **Don't** use gradient text, decorative glassmorphism, backdrop blur on shell layers, ambient accent glows, repeating stripe or grid backgrounds, identical repeated card grids, or sketchy illustrations.
- **Don't** use `border-left` or `border-right` greater than `1px` as a colored accent.
- **Don't** pair a `1px` border with a shadow of `16px` blur or more on a resting surface. Overlays may keep one border and one overlay shadow.
- **Don't** use uppercase tracked kickers for group or list headings, or hover lift on buttons.
- **Don't** rely on tooltips, hover, or colour alone to carry essential information.
- **Don't** use radii above `20px` for cards or sections, or let long labels and headings overflow narrow viewports.
- **Don't** introduce new pure black or pure white surfaces, or silently overwrite compatible user configuration.
