# assets-src/branding

Tooling for the mascot, logo and card art. It is its own npm package, like `tests/`, and is not part of the root install.

```
npm ci            # in this folder; .npmrc keeps ignore-scripts and min-release-age=7
npm test          # node --test, no network
```

Paths below are relative to this folder. Input files are looked up from the working directory first, then from this folder.

## Keys and endpoints

Only four names are read, from the environment or from `.env` (git-ignored; the environment wins). Nothing else in either place is read.

| Name | Use |
|---|---|
| `OPENAI_API_KEY` | OpenAI adapter |
| `GEMINI_API_KEY` | Gemini adapter |
| `OPENAI_BASE_URL` | default `https://api.linkapi.ai/v1` |
| `GEMINI_BASE_URL` | default `https://api.linkapi.ai` |

Base URLs must be https (plain http only for localhost). Keys never reach a log line, the console or an error message: headers named `Authorization` and `x-goog-api-key` and any `key=` query are redacted, every printed line and error is also scrubbed for the literal key values, and the `.jsonl` log stores references only as sha256. `test/redact.test.mjs` and `test/providers.test.mjs` cover this.

Official endpoints are a configuration change: set the two base URLs.

## Commands

```
node scripts/generate.mjs --template <name> [--vars k=v ...] [--characters reisen,tewi] [--refs a.png,b.png]
    [--model <id>] [--provider openai|gemini] [--size <size>] [--aspect <ratio>] [--n 1]
    --out raw/<stage>/ [--stage <name>] [--quality q] [--background transparent|opaque|auto]
    [--dry-run] [--yes] [--allow-stub] [--balance]

node scripts/edit.mjs --image <file> --instruction "<what to change>" [same options, no --template/--vars]
node scripts/contact-sheet.mjs [--out out/contact-sheet.png] [--cols 4] [--cell 384] [--cell-width N] [--cell-height N]
    [--labels a,b] [--nearest] <image>...
node scripts/key-bg.mjs [--out-dir out/keyed] [--key #00FF00] [--tolerance 80] [--softness 40] <image>...
node scripts/approve.mjs [--ref] [--dry-run] <file-or-sha256>...
node scripts/notice.mjs
```

- `--model` falls back to `lockedModel` in `config.json`; the provider is taken from the model's entry.
- `--size`: OpenAI takes `WIDTHxHEIGHT` (multiples of 16, edges up to 3840) and defaults to `1024x1024`. Gemini takes `512`, `1K`, `2K` or `4K` plus `--aspect` such as `2:3`, and defaults to `1K`.
- `--vars` repeats. Variables a template does not declare are an error. `name` is declared by the templates and stays empty unless a stage sets it.
- `--out` must resolve inside `raw/` or `out/`, which are git-ignored.
- Gemini returns JPEG. Files are saved with the extension of the bytes they hold (`.jpg`).
- Every real run prints `count x price`, refuses to start if the logged total plus the batch would pass `costCapUsd`, then asks `[y/N]`. `--yes` skips only the question; the cap check always runs. Without a terminal and without `--yes` the run stops.
- `--dry-run` prints the composed prompt, the references (name, size, sha256 prefix), the redacted request and the estimate. It sends, saves and logs nothing and needs no key.
- `--balance` reads the relay's `GET /api/usage/token/` before and after the run and prints `total_used` and the charge for the run from its change (500,000 quota units per dollar). The account balance in dollars is shown only when the token reports `data.user_quota`; the Gemini token does not. With `--balance`, the charge is also written to the log line as `chargedUsd`. It is the change in `total_used`, so it is only right when nothing else spends from the same token during the run; if either balance read fails, the field is left out.
- A template with `status: stub` is refused for real runs unless `--allow-stub` is passed.
- Both adapters make one image per request, one request at a time, because the relay has returned fewer images than `n` and still charged for `n`. The first failure stops the batch; images already made are saved, logged and charged, and the exit code is 1.
- A non-2xx reply whose body says `error.type: "upstream_error"` (a failed relay channel, not charged) is retried once after 3 seconds and the retry is printed. Nothing else is retried: not a 2xx reply, and not a request that threw, such as a timeout, because the relay may already be working on it.
- Edits put the edited image first among the references and use the `edit` template.

## Contact sheets, keying, approval

- `contact-sheet.mjs` scales each image to fit inside the cell box at its own aspect ratio, so mixed 3:2 and 2:3 images leave no grey bars. `--cell` sets a square box; `--cell-width` and `--cell-height` bound each side separately. Rows are as tall as their tallest image.
- `key-bg.mjs` reads PNG, JPEG or WebP and writes PNG. Pixels within `--tolerance` (RGB distance, default 80) of the key become transparent, the next `--softness` (default 40) are feathered, and the key's dominant channel is clamped on what remains to remove the green fringe. A test keys a blurred figure on a green field saved as JPEG at qualities 90, 75 and 50; the defaults hold at all three, so they were not changed. Every pixel near the key colour is keyed, so a figure must not contain it.
- `contact-sheet.mjs --scales 1,4` shows every image at each whole-number scale, at exactly width x scale, with nearest-neighbour resizing, one row per image. Use it for pixel art.
- `approve.mjs` takes log output files (path or sha256, full or a prefix of at least 8 digits), checks that each file's sha256 is the logged one, then sets `approved: true` on the output and its entry, copies the file to `approved/` and, with `--ref`, also to `refs/`. It checks everything before it writes anything and refuses a mismatching file or a different file already in the way. `approve.mjs --supersede <old> --by <new>` replaces an approved output with a newer approved one: the old output stays in the log with `superseded: <new sha256>`, its copies leave `approved/` and `refs/`, and it can no longer be approved. It refuses when the new output is not approved yet, when the old one is not approved, or when a copy in `approved/` or `refs/` is not the logged file. `NOTICE.md` lists only current approvals and gives superseded ones one history line. `approve.mjs --supersede <old> --by <new> --in-place` is for a slot master that other files point at by its approved name (for example `approved/gs-reisen-done.png`): it approves `<new>` first if it is not approved yet (same checks as a normal approval), supersedes `<old>`, and writes `<new>`'s bytes under `<old>`'s names in `approved/` (and in `refs/` when `<old>` has a copy there) instead of under its own timestamped name. The output in the log gets `approvedAs: "<that name>"`, and a later `approve.mjs` check, a later supersede and `NOTICE.md` use that name. It refuses when `<old>` is not approved, when its copy in `approved/` is missing or not the logged file (so is a copy in `refs/`), or when `<new>` is already approved under another name, before changing anything. `--dry-run` prints the plan. `approve.mjs --revert <new>` undoes a supersede: the one output that `<new>` superseded is approved again (it must still be on disk with its logged sha256), `<new>` is marked superseded by it and stays in the log as history, and the old bytes go back under the approved name in every folder where `<new>` has a copy, replacing `<new>`'s bytes after an in-place supersede, or after a plain one removing `<new>`'s copies. It refuses, before changing anything, when `<new>` is not a current approval, when nothing or more than one output was superseded by it (after a chain of supersedes on one slot, `--to <old-file-or-sha256>` picks which of them to restore, and must be one of them; the others keep their `superseded` as history), or when its copies are not its logged bytes; a second revert is refused for that reason, and `<new>` cannot be approved again afterwards. `NOTICE.md` then lists the old output as current and gives `<new>` a history line. `--dry-run` prints the plan.

## Local patches

Whole-image edits cannot fix details a few pixels wide. `patch.mjs` edits one crop at a time and puts only the chosen rects back, so nothing else in the picture changes.

```
patch.mjs --image <png> --spec <patches.json> [--instruction "..."] [--n 1] [--feather 6] --stage <s> --out raw/<stage>/ [--dry-run] [--yes] [--balance]
```

`patches.json` is a list of `{ "crop": [x, y, w, h], "composite": [[x, y, w, h], ...], "instruction": "optional" }`, all in the source image's pixels. A patch without `composite` composites its whole crop; composite rects must lie inside their crop.

- Each crop is magnified with Lanczos into whichever of 1024x1024, 1536x1024 or 1024x1536 magnifies it most, centred on a canvas padded with the median colour of the crop's border (never stretched), and sent to `/images/edits` with the `patch-edit` template. That template says the image is a close-up crop of a larger image and carries the `no-human-ears-edit` constraint.
- The result is scaled back to the crop's exact size, and only the composite rects are blended into the source, with a soft edge `--feather` pixels wide (default 6; 0 is a hard edge). Pixels outside the rects stay byte-identical to the source.
- Each call prints the mean colour difference inside and outside the composite rects. A large difference outside means the model redrew more than asked (warning above 10).
- Outputs in `--out`: the raw result of each call, the padded request image and prompt of each patch, the full-size picture (`...-patch-<variant>.png`) and a before and after sheet at 2x (`...-patch-<variant>-compare.png`). `--n` makes that many variants; variant k combines the k-th result of every patch.
- One log line per call (`template: patch-edit`, `refs` the source file's sha256, `vars` with `crop`, `composite`, `patch`, `variant`, `feather`, `chargedUsd` under `--balance`), plus one line per full-size picture (`template: patch-composite`, no cost) so `approve.mjs` can approve it. A failed call stops the run, keeps what was made and builds no picture for an incomplete variant.
- Only the OpenAI provider is supported.
- `--keep-alpha` (with a normal run or `--reuse`) keeps the source's alpha channel inside the composite rects: a pixel with alpha under 250 (transparent, or the antialiased edge of the sticker; the masters' solid pixels sit around 253, not 255) keeps its four bytes, and a solid one takes the result's colour and keeps its alpha, so a background the model drew in transparent space (it shows as a box around a sticker) never gets in. Without the flag, every variant prints how many pixels inside the rects were fully transparent in the source and are not now, warns when it is above 0, and logs it as `newlyOpaque` in the `patch-composite` line (with `keepAlpha: true` when set); the feathered edge never fades a solid pixel either way.
- `patch.mjs --image <same png> --spec <fixed.json> --reuse raw/<stage>/.../<stamp>-<model>-patch --out raw/<stage>/fix/ [--feather N] [--dry-run]` composites the saved model results of an earlier run again, with the new spec's `composite` rects and `--feather`, and makes no model call. The spec's crops must equal the reused run's crops, patch by patch, and the image must be the same file (sha256 of the logged `refs`); every reused result file must still have its logged sha256. It refuses on any mismatch, a missing result or a different number of patches, before writing anything. The variants come from the reused run, so `--n`, `--model`, `--instruction`, `--balance` and `--allow-unlocked` are refused with `--reuse`. Pictures and sheets are written as in a normal run; each picture gets a `template: patch-composite` line at cost 0 whose `refs` are the source and the reused results and whose `vars` hold `reused: <prefix>` and the new rects.

`patch-overlay.mjs --image <png> --spec <patches.json> [--scale 2] [--cols 2] [--flags <flags.json>] [--out out/patches/<spec>-overlay.png]` writes a check sheet: every crop at 2x (nearest-neighbour) with its composite rects outlined in green, so the rects can be judged by eye before any call is paid for. It reads the spec with the same checks as `patch.mjs`. With `--flags` (the file `ear-remnants.mjs` writes) the flagged pixels are tinted under the outlines, red for skin and yellow for warm lines, so every flag can be seen to be covered or deliberately left out.

`ear-remnants.mjs --image <png> --heads <heads.json> [--name <sheet>] [--out-dir out/patches] [--scale 4] [--cols 2] [--threshold 0.2] [--open-radius 7] [--min-pixels 8]` looks for what is left of a human ear beside each face. `heads.json` is a list of `{ "name", "crop": [x, y, w, h], "skin": [x, y], "ignore": [[x, y, w, h], ...], "faceless": false }`: `skin` is a point on that face's cheek (a back view, with `"faceless": true`, can use a cheek from anywhere on the sheet), and `ignore` hides rects such as a rabbit ear that hangs beside the face. Skin-like pixels (OKLab distance from the cheek colour, lightness halved, with hue and chroma checks that keep the page and the sticker white out) outside the opened face and beside its rows are flagged red; thin orange or brown lines in the hair are flagged yellow. It writes `<name>-remnants.png` (each head at 4x with the flags tinted) and `<name>-flags.json` (`[x, y, kind]`, source pixels) to `--out-dir`. It is a hint, not a verdict: temple and blush skin beside the eyes, jaw and neck bits and rabbit-ear bases are flagged too, and a person decides which flags are real and sets the rects.

`grid-image.mjs --image <png> [--step 100] [--crop x,y,w,h] [--zoom 1]` writes a copy with a labelled coordinate grid to `out/grid/`, for picking rects. With `--crop` and `--zoom` the lines and labels stay in source pixels.

## Pixel tools (S3)

The grid detector is our own (`scripts/lib/pixel-grid.mjs`). The unfake.js project is private on GitHub and is not published to npm (`unfake.js` does not exist there; the npm package `unfake` is an unrelated one), and `.npmrc` forbids git dependencies. The only dependency stays `sharp`.

- `palette-extract.mjs --in <approved sheet.png> --name reisen [--colours 28]` proposes a DRAFT palette: the sheet's colour families (weighted k-means in OKLab, skipping the page colour and transparent pixels), each as a ramp with a shadow leaning towards violet and a highlight leaning towards warm yellow, a deeper shade for the biggest families, and white plus the soft rim of the sticker look. It writes `out/palettes/<name>-draft.hex`, `.gpl` (each colour named by its role) and a `.preview.png`. 24 to 32 colours; fewer than asked for, with a warning, when the sheet has few colour families. Lock a palette by copying the `.hex` to `palettes/<name>.hex`; `--palette reisen` then finds it.
- `pixelate.mjs --in <large.png> --grid 128x128 --palette reisen [--out out/pixel/<name>.png]`:
  1. The picture is assumed to span the whole native canvas, so the expected cell is source size / grid size (a source already near native size is read one cell per pixel). The detector searches 12% either side for the cell, which may be fractional (10.24 pixels per cell), and for where the grid starts. `--cell N` fixes the cell and still finds the offset. A weak detection (strength under 0.2) is a warning.
  2. Every cell becomes one pixel. `--sample mode` (default) lets the middle 60% of the cell vote for its nearest palette colour, `centre` takes the one centre pixel. Neither averages colours.
  3. Colours are the nearest palette entry in OKLab. The palette may hold at most 32 colours (a warning below 24).
  4. Alpha is binary: a cell is opaque when at least half its voting pixels have alpha of `--alpha-threshold` (default 128) or more.
  5. Orphans (an opaque pixel with no same-colour neighbour among its 8, and a transparent pixel with 8 opaque neighbours) are reported with a suggested colour, in the output and in `<out>.report.json`, and are NOT changed. `--orphans-patch <file>` writes the suggestions as a `pixel-fix` patch for review; `--fix-orphans` applies them (repeating until none are left, at most 10 passes). Real details such as a one-pixel eye highlight look like orphans, which is why nothing is removed silently.
  The sprite touching the canvas edge is a warning. `--indexed` writes a palette PNG.
- `pixel-fix.mjs --in <native.png> --patch <patch.json> [--palette reisen] [--allow-off-palette] [--out out/pixel-fixed/<name>.png]` applies `[{ "x": 3, "y": 4, "color": "#c82832" }, { "x": 10, "y": 2, "w": 4, "h": 1, "color": "transparent" }]` in order to a copy. With `--palette`, a colour outside it is an error. It never overwrites its input.
- `snap.mjs --in approved/<id>.png --stage s5 [--figure-height 300 | --cell 3.4] [--sample median|mode] [--colours K] [--fixes <file>] [--sheet out/snap/<id>-sheet.png]` snaps a master to one square pixel grid, with no palette and no resize: it finds the offsets of a grid of the chosen cell, reads one colour per cell (the median, or with `--sample mode` the commonest 4 bit colour, of the middle 60% of the cell) and makes alpha binary. The cell is one of: `--cell N` (master pixels per art pixel), `--figure-height N` (the cell at which the opaque figure is N art pixels tall), or, with neither, the mean of the pitch found across and the pitch found down, each measured on its own from the edges between solid pixels (the run prints both, with their strength, where 1 is chance, and how well the grid fits at the chosen cell). `--colours K` reduces the picture to K colours chosen from itself and is off by default. The sticker is rebuilt on the snapped silhouette: every pixel within the master's rim width of transparent (the master's width divided by the cell, at least 1) is `#b99bf2`, and the white band is the next band width of pixels, both exact, so the rings are continuous with no gaps or isolated pixels (the run counts the pieces and the isolated pixels; `--rim`, `--band`, `--rim-width`, `--band-width` and `--no-ring-repair` override this). Islands of 6 pixels or fewer are removed and one pixel holes are filled before the rings are built. Orphans are reported as `pixelate.mjs` reports them, with a colour tolerance since there is no palette (the count with every different colour counted is printed too), and are not changed. Hand touch-ups are `pixel-fix.mjs` patches in `fixes/<id>.json` (or `--fixes`), applied after the snap, so snapping a master again gives the same file; the log records the patch's hash. A real run writes `raw/<stage>/pixel/<id>.png` and logs `template: pixel-snap`, `provider: local`, `model: pixel-snap`, the master's sha256 in `refs`, and the cell, offsets, options and fixes in `vars`; `--preview` writes `out/snap/<id>-preview.png` and logs nothing. `--sheet` writes the review sheet: master and snap at the same size, the snap at 1x and 2x, and 6x crops of both sides of each face and of the hands, taken from `review/<id>.json` (`{ "faces": [{ "name", "left": box, "right": box }], "hands": [{ "name", "box" }] }`, boxes `{ x, y, width, height }` in master pixels).
- `snap.mjs --measure [--approved approved] [--only id,id] [--figure-height 300]` prints the pitch across and down, the strength, the grid fit, and the figure height in art pixels at the detected cell, for every approved master; with `--figure-height` it adds the cell that height asks for, how far that is from the detected one, and the fit there. `snap.mjs --compare --in <master.png> --colours 24 [--sheet out/snap/<id>-sampling.png]` snaps the picture four ways on one grid (median or mode, with and without K colours) and prints orphans, colours and the error against the master for each, with a 6x crop of each. Neither logs anything.
- `snap.mjs --in approved/<id>.png --stage s5` with no size takes the body height `snap-config.json` sets for the picture's character (`{ "bodyHeights": { "tewi": 283, "reisen": 340 }, "lineupRatio": 0.8333 }`; the file is refused when the two heights drift from the ratio by more than 0.5%). The character is the one `prompts/s5-masters.json` gives the picture's id, or `--character <name>`; a picture of both characters has none and is refused. `--body-height N` sets the cell at which head top to feet, ears left out, is N art pixels tall, using the same head-top detection as `compose-scene`'s `measure: figure` (scaled to the picture's size), and it fails when no head top is found. `--detect` keeps the detected pitch instead. `snap-config.json` also sets `rings: { "rim": 2, "band": 2 }`, the width in art pixels of the lavender rim and the white band on every snapped picture, so the sticker is one width everywhere whatever its master's own rings; `--rim-width` and `--band-width` (or `rimWidth` and `bandWidth` on a batch item) override it for one picture. The run measures the rings on the finished picture and prints a `CHECK` when they are not the widths asked for. The run prints the character, the head top and feet rows and the head to feet height in art pixels, and `CHECK` lines for a head top that is missing or made of skin (a raised hand taken for the head), feet at the canvas edge, or a snapped picture that measures more than 2% off the height asked for.
- `snap.mjs --batch snap-batch.json --stage s5 [--out-dir raw/s5/pixel-body] [--sheet-dir out/snap] [--dry-run]` snaps every picture of `{ "outDir", "items": [{ "in", "id", "character", "bodyHeight" | "figureHeight" | "cell", "ringRepair" }] }` in one process: every picture is snapped, checked and sheeted in memory first, and only then are the files written and logged one after the other, so one bad picture writes nothing and two runs never append to the log together. `--dry-run` prints the table (cell, snapped size, head to feet, orphans, `CHECK` lines) and writes and logs nothing. `snap.mjs --measure [--body-sheet out/snap/body-check.png]` also prints the set body height as a cell for each master, and draws the head top (red) and feet (green) on every picture. Review boxes for the close-ups on the sheet are in `review/<id>.json` (`{ "faces": [{ "name", "left", "right" }], "hands": [{ "name", "box" }] }`, boxes `{ x, y, width, height }` in master pixels; the face boxes sit on the two sides of the head, where a human ear would show).
- `snap.mjs --in <patched.png> --grid-from <approved/pixel/<id>.png | sha256> --id <id>--<name> [--frame-region x,y,w,h] --stage s5 [--sheet out/snap/<id>--<name>-sheet.png]` snaps a frame of an idle loop (a blink, an ear twitch) on exactly the grid of its base snap, so the two line up pixel for pixel. `--in` is the base's master with the patch made (only the eyes changed). Nothing is detected: the cell, the offset, the sampling, the colours and the ring widths and colours are the ones the base's log line recorded, and `--cell`, `--body-height`, `--figure-height`, `--detect`, `--sample`, `--colours`, the ring options, `--fixes` and `--character` are refused with it. `--grid-from` takes the approved copy (`approved/pixel/<id>.png`), the `raw/` file the snap logged, or the sha256 (8 hex digits or more) of the snap; a path is matched by its name as well as its bytes, so `splash-reisen` and `splash-both-reisen`, which are the same bytes, are told apart, while a sha256 that names both is refused. A file changed since the snap, or no snap's output, is refused. The frame's id must be `<base id>--<name>` (`--id`, or the file name), so it is approved as `approved/pixel/<base id>--<name>.png` next to the base. The base's touch-ups (`fixes/<base id>.json`) are applied to the frame too, if that file is still the one the log recorded; `fixes/<frame id>.json` is refused. The log line has `refs` of the patched picture and then the base snap, `vars.cellSource: grid-from`, `vars.gridFrom: { id, sha256, file }` and `vars.frame` (see below), and the run needs `--stage` or `--preview` as any snap does.
- The frame check runs before anything is written: the frame snap is compared with the base snap, and the run prints the number of art pixels that changed and their box, in art pixels and in master pixels. A frame that changed nothing, or that snaps to another canvas size than its base, is refused. `--frame-region x,y,w,h` (master pixels) is where the patch may change things, and a frame that changed any pixel outside the cells that region touches plus a margin of 2 art pixels is refused with the box of the stray pixels, so a blink that disturbed more than the eyes is caught. Without `--frame-region` the box is only reported.
- A layout `grid` is `{ "cell": 4 }` (whole canvas pixels per art pixel) or `{ "width": 555, "height": 370 }` (the native size in art pixels, with the canvas's proportions, so the cell is the canvas divided by it and may be fractional). `compose-scene.mjs --grid` places each layer's snapped still (`pixel`) unscaled at the anchor divided by the cell. A figure layer's rings are measured as placed and printed; a grade with `keepSticker` leaves every pixel within the rim and band widths of transparent space as it was.
- `compose-scene.mjs --layout layouts/<name>.grid.json --grid --set <layer>=<frame snap> --frame-of approved/pixel/<name>.png --out raw/<stage>/pixel-body/<name>--<frame>.png` composes the frame of a grid scene: the layer's snap is swapped for its frame snap (made with `snap.mjs --grid-from`), the grade and the placement are the layout's, and the scene is checked against the base scene before anything is written. Only the pixels in which the frame snap differs from the layer's own snap (the `pixel` of the layout) may differ in the scene, wherever the layer is placed and whatever its grade, including the night grade with `keepSticker`; the run prints how many scene pixels differ and their box in art and canvas pixels. A frame snap whose figure box or size differs from the layer's snap is refused (the layer would be placed differently), and so is a swap that changes no scene pixel, a layer with no `pixel` in the layout, or a scene that differs elsewhere, which means the base scene was not composed from the other pictures as they are now. `--frame-of` needs `--grid` and at least one `--set`. The log line is a grid scene (`vars.grid`), so `approve.mjs` keeps it as `approved/pixel/<file name>`; it adds `vars.frameOf: { file, sha256 }` and `vars.frame: { changed, box, layers }`, and the base scene's sha256 joins `refs`.
- `composite-sheet.mjs --layout layouts/<name>.grid.json --smooth approved/<name>.png --grid-image raw/<stage>/pixel-body/<name>.png --out out/snap/<name>-composite-sheet.png` writes the review sheet of a grid scene: the smooth composite and the grid one at the same size, the grid one at 2x nearest, and for every box in `review/<name>-<layer id>.json` the same area of both (the grid one at 6x). The boxes are carried through each still's snap grid (its cell and offsets from the log) and its placement. Layouts for the grid scenes are `layouts/<name>.grid.json`; the smooth `layouts/<name>.json` stay as they were.
- `approve.mjs` writes an approved snap to `approved/pixel/<id>.png` (the id is in the log entry) and a grid scene to `approved/pixel/<its file name>`, recording the name as `approvedAs`, so `NOTICE.md` lists `pixel/<id>.png`. The master keeps its own file and stays approved: a snap is a new output with its own hash, and `--supersede` refuses to let pixel art replace art that is not pixel art. A newer snap of the same picture replaces the older one with `--supersede <old> --by <new> --in-place`.
- `trim-align.mjs --canvas 128x128 [--pad N] [--baseline N] [--align-x bbox|centroid] [--lock each|first] [--scale none|fit] [--nearest] [--out-dir out/aligned] <images...>` trims each image to its opaque box and places it with its feet on one baseline and its box (or the weight of the sprite) on the centre line. Pixels are copied, not resampled, unless `--scale fit` applies one common magnification (a whole number with `--nearest`). `--lock first` keeps each frame's offset from the first one, so an ear that moves between frames still moves. An image that does not fit is an error.
- `contact-sheet.mjs --scales 1,4 <images...>` shows each native sprite at 1x and 4x with nearest-neighbour resizing.
- `design-sheet-pixel` (`--vars format=sprite-128` or `format=portrait-64`) and `pixel-still` ask for a transparent background. When the template's `background` variable says "transparent", OpenAI is sent `background: transparent`; `--vars background="flat pure green #00FF00"` is the fallback, which is then keyed out with `key-bg.mjs` (Gemini cannot make transparent pictures, so it needs the fallback). A relay that returns an opaque picture to a transparent request gets a warning. `--background transparent|opaque` must agree with the prompt.

## Master art export

The approved full-size picture is the master. A build step resizes it to the exact device pixels each placement needs; there is no pixel grid or palette lock for mascot art.

- `rim-recolour.mjs --in <picture.png> --out raw/<stage>/masters/<name>.png [--target #b99bf2] [--stage s3]` gives every character the same sticker rim. It finds the model's outer lavender ring (walking in from the transparent edge through pixels that are not white, no deeper than the white band starts; the white band is looked for 16 pixels in from the edge, and only when it is not there twice as deep each time, up to 256, so a picture drawn on a coarse grid with a rim and a band 32 pixels thick works, while one whose band is within 16 pixels is read exactly as before) and moves each of its pixels by the difference between the target and the image's own median rim colour, scaled by how much of the way the pixel is from white to the rim. The move is made in OKLab, so hue and lightness change and the variation inside the rim stays, and antialiased pixels move less. Alpha, the white band and the character are never changed (a test checks they are byte for byte equal), and lavender hair behind the white band is not touched. A canvas border is a cut, not an edge. It writes the PNG, refuses to overwrite one, and logs a derived output (`template: rim-recolour`, `provider: local`, `estimatedUsd: 0`, the source's sha256 in `refs`) so `approve.mjs` can approve it. It fails when it finds no rim or no white band.
- `export-art.mjs --spec export-specs/trial.json [--out-dir out/export] [--only id,id] [--sheets]` writes `<id>@<css>x<density>.webp` for each asset and CSS size at 1x, 2x and 3x, and `manifest.json`. The spec is `{ "margin": 24, "assets": { "<id>": { "character", "master", "css": [128, 64], "fit": "contain|width|height", "square": false, "crop": [x, y, w, h], "margin", "webp", "focus": [x, y] } } }`. An asset with `"pixel": true` and a snapped still as its `master` is not resized: it is framed in art pixels (`margin` defaults to 2, `crop` is in art pixels, `css`, `fit`, `src` and `webp` are refused) and written at its own size as `<id>@native.png` or `.webp`, lossless, whichever is smaller; a master with translucent pixels is refused. The manifest entry has `"pixel": true` and `"native": { "width", "height" }`, and its one variant has no `css` or `density`, so the app picks a whole number of device pixels per art pixel. The smooth path is unchanged for every other asset.
- `frames` on a pixel asset, `"frames": [{ "id": "blink", "master": "approved/pixel/<id>--blink.png" }]`, exports the pictures of an idle animation after the base, in that order. Each is cut with the base's frame (not its own box), so the files line up pixel for pixel; it must be a snapped still of the base's size with the same opaque box, or the export is refused before anything is written. The files are native size, lossless, in the format the base got, named `<asset id>--<frame id>@native.png` or `.webp`. The manifest entry keeps every key it had and, for an asset with frames, adds `frames`: the base first and then each frame in order, each `{ id, file, format, bytes, master, masterSha256 }` (the base's id is the asset id, a frame's is `<asset id>--<frame id>`). A later export with fewer frames removes the frame files of the earlier one. The sheets show every frame. There is no animation code in the app yet; the manifest is the list it will play.
  1. The frame is the subject's box (pixels with alpha of 16 or more, or `crop`) plus `margin` source pixels on every side, made square with `square`. It can reach past the canvas; the extra is transparent, so the sticker edge never touches the edge of the file.
  2. The frame is resized with Lanczos3 on premultiplied alpha (no fringe round the edge). `fit: contain` makes the longer side the CSS size times the density, which in a square box is the box; `width` and `height` measure that side. A size the frame cannot supply without enlarging it is an error.
  3. Each asset is stored as one of three WebP encodings: `lossless`; `near-lossless` (lossless WebP after rounding low bits, no chroma subsampling); or `lossy`. Each is compared with the Lanczos resize, both composited on grey, as an OKLab distance times 100 over the pixels that show: the mean must be at most 0.4 and the 99th percentile at most 1.5 (about 2 is the smallest step an eye can tell apart). `auto` takes, among the encodings that pass for every size of the asset, the one with the fewest bytes, trying near-lossless quality 40 to 90 and lossy 70 to 95 from the lowest. `webp` can force `"lossless"` or `{ "mode": "near-lossless" | "lossy", "quality": n }`.
  `crop: "canvas"` frames the whole picture (with `margin: 0` and `fit: "width"` that keeps the model's layout and a wide placement's aspect). `src` picks the fallback file for browsers without srcset: `{ "css": 128, "density": 2 }`, by default the 2x file of the widest CSS size. The manifest names it in `src` on the asset and flags it on its variant. `export-specs/shell.json` covers every mascot placement, with masters at `approved/<id>.png`; a slot whose master is not there yet is refused by name, so export the finished ones with `--only`.
  The manifest lists, for each asset, its master and its sha256, the frame, the encoding and, for each variant, file, css, density, width, height, bytes and the bytes and figures of all three encodings. `--sheets` also writes `<character>-sheet.png` into the output folder: each variant as the browser decodes it (1:1), a 4x zoom of a window round the asset's `focus`, and the real file size in the label. An asset's old files are replaced on a new run, and other assets in the manifest are kept.

## Logo vector (S4) and scene compositor (S5)

- `vectorize.mjs --in <approved logo master.png> [--out-dir raw/s4/logo-vector] [--sheet out/s4/logo-vector.png] [--base #8b64aa] [--centre both|base|bbox] [--segment-length 8] [--k-dark px] [--k-light px] [--preview]` turns the master into flat SVGs. It first snaps the picture to its own tones (colours within 0.09 in OKLab are one tone, a pixel takes the nearest tone, pixels under half opaque are background) and sets the tone nearest `--base` to exactly that colour. Each tone is traced by itself with `vtracer` (colour mode, stacked, spline; found through `$VTRACER`, `~/.cargo/bin` or the PATH), the base tone under all the others so no gap opens between tones, and the paths are merged into one `<path>` per tone with relative coordinates at one decimal. The SVG has a `viewBox` and no width, height, transform or metadata. The trace is rendered and compared with the snapped picture, and a trace that is wrong by more than a pixel over more than 4% of the shape is refused. `base` centres the dome with the letters on the vertical axis (found as the lowest thick body, holes filled), `bbox` centres the whole box; both give equal margins above and below, and the run prints how far apart the two centres are. For each centring it writes three SVGs: `logo-<centring>.svg` (as drawn), `logo-<centring>-lines-a.svg` and `logo-<centring>-lines-b.svg`. The lines and dots are found on the snapped picture: it is opened (holes filled first) with a window 2.5% of the emblem wide, wider than a line, which leaves the ears and dome, and what the opening removes, less pieces under 200 px, is the lines with their dots. The few pixels of each line that the opening rounds back into the dome are shaded too, so the shading runs up to the dome. Shading is done on the snapped picture before tracing, in the logo's own three tones with light from above, so each file still has one path per tone. A base tone pixel in that zone is dark when the pixel `k-dark` rows below it is not drawn (the line minus the line shifted up), and, in B only, light when the pixel `k-light` rows above it is not drawn; dark wins where they meet. By default `k-dark` is a third and `k-light` a fifth of the line thickness (the most common thickness along the lines), because the lines are as thick as the dome's whole dark band, so the dome's own band widths cannot be copied. The run prints the dome and ear bands it measured. The pixel drafts (`logo-pixel-16.png`, `logo-pixel-32-sb.png`, `logo-pixel-32-solid.png`) take the ears and dome only (everything thinner than 2.5% of the emblem is dropped, the SB holes are filled), centre them on the dome and reduce by area coverage: a cell is opaque from 50% coverage, or from 40% when it touches such a cell, and takes the tone that covers most of it. The 32 px SB draft cuts the letters as 3 by 5 cell glyphs with one cell strokes, the 16 px draft has no letters. They are starting points for `pixel-fix`. The contact sheet shows the centring frames with the dome and box ticks, the shading variants beside the plain logo at 420 px with a 4x close-up of a line and dot, the small sizes at 1x and 4x, and the drafts at 1x and 8x, on `#fafafb` and `#222226`. `--preview` writes under `out/` only and logs nothing; a real run writes the files and a derived-output log line (`template: vectorize`) together or not at all.
- `logo-plates.mjs --in <approved logo master.png> [--out-dir raw/s4/logo-plates] [--sheet out/s4/logo-plates.png] [--shape squircle|circle] [--colour light|dark] [--base #8b64aa] [--k-dark px] [--k-light px] [--preview]` is the step after `vectorize.mjs` once the dome centring and the line shading (B) are chosen. It redraws the lines and dots as exact geometry instead of tracing them. Each dot is a circle fitted to the boundary of its piece (a least squares fit that drops the stretch where the line joins), and each line is a centre line of horizontal and vertical pieces found in the piece's straight runs, drawn as a stroke with square corners. All lines share one width and all dots one radius, the middle of what was measured, and the stroke's edges are whole pixels. The line runs on into the dome by 10 px under the dome's outline, and the bands stop at the dome's edge, which is fitted as a curve from the rows above and below the line. The run stops if a redrawn line is more than 3 px from the picture, and prints how far each dot and line moved. The shading follows the same rule as in `vectorize.mjs`: the dark band is the stroke less the stroke shifted up by `k-dark`, the light band the stroke less the stroke shifted down by `k-light` (a third and a fifth of the width unless set), and the dot's crescents are the circle less the circle shifted, stopping on the side the line comes from where the line's own band takes over. Bands and crescents are exact paths. The ears and dome are traced without the lines, so the logo is still three paths, one per tone. The body is no longer traced with `vtracer`. The dome's two sides are first redrawn as one degree 4 curve each (a robust fit that ignores the rows where a line was cut away), then the shape, the two bands and the letters are traced with `potrace` (found through `$POTRACE` or the PATH) from sub-pixel fields made from the master's alpha and luma, and the curves are fitted again with as few cubics as stay within 0.3 px. The bands reach 0.25 px past the shape so no rim of the base tone shows beside them. The run prints how far the letters are from the snapped picture and how well the dome fits. The emblem is put on plates: a squircle (superellipse with exponent 5) and a circle, each in a pale lavender and a deep plum made in OKLCH from the base colour's hue (lightness 0.95 and 0.22), with a lip along the bottom 3% of the plate's height in a darker shade, and the SB cut-outs show the plate colour. On the squircle the emblem's larger side is 80% of the plate; on the circle its smallest enclosing circle about the dome's axis has 94% of the plate's radius. Both are moved up by half the lip. `logo-emblem.svg` is the emblem on its own, `logo-emblem-nolines.svg` the same frame without lines, and `logo-plate-<S|C>-<L|D>[-nolines].svg` are the plates on a 1024 square, with the lines unless the name ends in `-nolines`. The outline of a plate is written once in `<defs>` and used three times (lip, raised plate cut to the outline, clip), to keep the file under 12 KB. With `--shape` and `--colour` together only that plate is made, and the files are named `logo-emblem.svg`, `logo-emblem-nolines.svg`, `logo-plate.svg` and `logo-plate-nolines.svg`; the sheet is then written only if `--sheet` is given. Every SVG must have a `viewBox`, no `width` or `height`, no metadata and be under 12,000 bytes (`scripts/lib/svg-checks.mjs`), or the run stops before writing or logging. The log line holds the shapes, the plate and lip colours, the squircle exponent, the band widths, the line width and the dot radius. The sheet shows the reference, each plate at 360 px with and without lines on a light and a dark page, and the plates without lines at 64 and 32 px with a 4x copy. The colour and placement code is in `scripts/lib/plate.mjs`, and takes the plate's size, so the full-bleed square backgrounds of the app icons can reuse it. `--preview` writes under `out/` only and logs nothing; a real run logs one derived output (`template: logo-plates`).
- `logo-final-check.mjs [--dir raw/s4/logo-final] [--sheet out/s4/logo-final-check.png]` reads the four final SVGs, runs the same checks and prints their sizes raw and gzipped, then writes a check sheet under `out/` only (it refuses to overwrite one): all four at 512 px, `logo-plate` at 128 and 64 px, and `logo-plate-nolines` at 48, 32 and 16 px at 1x and as a 4x nearest-neighbour copy, each on a light and a dark page. It writes nothing to the log.
- `logo-fix-check.mjs --master <approved logo master.png> [--old approved] [--new raw/s4/logo-final-2] [--sheet out/s4/logo-fix-check.png] [--scale 4]` checks `logo-plate-nolines.svg` and `logo-plate.svg` in both folders, prints their sizes, and writes a sheet under `out/` only (it refuses to overwrite one) with the old and new file side by side at 512 px, then the same parts of the master cut from both at `--scale` pixels to a master pixel: the two sides of the dome, the S, the B and the dome's top left. It writes nothing to the log.
- `pixel-prop` draws one object with no character (`--vars prop=moon|star`, from `prompts/pixel-props.md`) in the same pixel style and sticker edge, from `prompts/style-pixel-prop.md`; a test keeps that style file in step with `style-pixel.md`.
- `compose-scene.mjs --layout layouts/<name>.json --out raw/<stage>/masters/<name>.png [--set <layer>=<picture>]... [--preview]` composes a scene from pictures that already exist. The layout is `{ canvas: { width, height }, layers: [{ id, image, z, at, anchor, height, measure }] }`: each picture is trimmed to its alpha box (pixels fainter than 8 are ignored), scaled with Lanczos to `height` canvas pixels keeping its aspect, placed with `at` (`centre`, `bottom-centre` or `top-left`) on `anchor`, and drawn in `z` order. A layer with `repeat: [{ x, y, height }]` is drawn at each point (the stars). `height` can be `{ ratio, of: <layer id> }`. `measure: figure` sizes a character by head top to feet: the head top is the first row inside the sticker with a 40 px run of pixels that are not ear coloured (white fur, pink), so the ears and a strand of hair are left out; if there is none, the whole box is used and the run says so. A layer can have `grade: { toward: "#7d8fd6", amount: 0.14, lightness: -0.03, keepSticker: true }`, a colour grade applied to the layer after it is trimmed and scaled and before it is placed. In OKLab, each pixel that is not fully transparent moves `amount` (0 to 1, required) of the way toward the target's a and b (its hue and chroma, so white and grey pick up the tint) and its lightness changes by `lightness` (-1 to 1, default 0), kept between 0 and 1; alpha never changes. `toward` is required. With `keepSticker` (default true) the white band and the lavender rim, found by the same detection as `rim-recolour.mjs`, keep their bytes, so the shared rim colour stays the same in all art; a layer with no sticker is then refused, and `keepSticker: false` grades the whole layer. A real run logs every layer's grade, with the defaults filled in, as `vars.grades`; a scene without grades logs none. `--measure <picture>[:first-last]` prints those figures. A real run logs a derived output (`template: compose-scene`) with the hash of every input; `--preview` writes under `out/` only and logs nothing, so a placeholder passed with `--set` never reaches the log. `layouts/hero-duo-night.json` is the night banner. With `--grid` the layout is composed on its pixel grid (`"grid": { "cell": 4 }`, canvas pixels per art pixel, which must divide the canvas): the picture is the canvas divided by the cell, each layer uses its snapped still (the layer's `"pixel"` path, or `--set`), copied in unscaled, with no resampling, at an anchor of `round(anchor / cell)` art pixels, so `height` is not used to scale; the run reports the height wanted, the figure height of the still, and, for a `{ ratio, of }` height, the ratio the stills give against the one wanted, so a character's size comes from the height she was snapped at (`measure: figure` looks for the head top with a 12 pixel run and a 5 pixel sticker in art pixels). A grade is applied to the still before it is placed. A picture with translucent pixels is refused. A real grid run logs `vars.grid`; write it under `raw/<stage>/pixel/`. The scenes' grid layouts are `layouts/<scene>.grid.json`, and their snapped stills are named `<scene>-<character>` (for example `hero-duo-reisen`), so `approve.mjs` writes them to `approved/pixel/` under those names.

## Prompt kit

`prompts/` is composed in this order: style, character files, template, constraints. Template front matter holds `style`, `characters`, `constraints`, `require` and `var.<name>: <default>`. `lookup.<var>: <file>:<variable>` fills a variable from a `## key` table in `prompts/<file>.md`, keyed by another variable; `expression-face-edit` uses it to take its ear pose from `prompts/ear-poses.md` for each of the 28 expressions, and `--vars ears=...` overrides it. A line whose variable resolves to nothing is dropped. The `references`, `style-reference` and `sheet-order` constraints appear only when references are attached. Every template that draws a character carries the `no-human-ears` constraint (the `edit` and `patch-edit` templates carry `no-human-ears-edit`, which also asks to remove human ears that are already there unless the instruction says otherwise); `test/prompt-ears.test.mjs` fails for a new template that has neither, unless it is listed as drawing no character. Prompt files name no artist, studio, game or character; `test/prompt-kit.test.mjs` checks this.

## Log

`log/generations.jsonl` is committed. Each line is `{ time, stage, provider, model, template, vars, refs, size, n, outputs, estimatedUsd, [chargedUsd,] approved }`. `chargedUsd` is the relay's measured charge and is optional. The cost cap sums `chargedUsd` where a line has it and `estimatedUsd` otherwise; `notice.mjs` shows the two separately. `refs` and `outputs[].sha256` are hashes. For Gemini, `size` is `<size>/<aspect>` when an aspect is set. `n` and `estimatedUsd` count the images actually made. The composed prompt is written next to the outputs as `*.prompt.txt` (git-ignored).

`--balance` measures the change in the token's total, which counts every run on the token, so two runs at once would each record both. Every real run therefore leaves a record in `log/.runs/` (git-ignored: provider, pid, start, end; no key). When another run's record overlaps this one, `--balance` records no `chargedUsd` and prints a warning, and the estimate stands. `fix-charged.mjs --from <time> [--write]` lowers a `chargedUsd` above the price times the images, from that time on, to that figure, changing nothing else in the line; it refuses to write while a run is going. It was used once, from 2026-11-01T09:10:00Z, for edit lines measured while the S5 masters run was spending on the same token.

## Request shapes and sources

Checked on 2026-11-01.

**OpenAI** (`openai` adapter)
- Text only: `POST {OPENAI_BASE_URL}/images/generations`, JSON `{ model, prompt, n, size }` plus `quality` and `background` when given, `Authorization: Bearer`. Response `data[].b64_json`; `usage` is printed.
- With references: `POST {OPENAI_BASE_URL}/images/edits`, multipart with `model`, `prompt`, `n`, `size` and one `image[]` file part per reference (up to 16).
- GPT Image models always return base64; the adapter also accepts a `url` item (https only, no credentials sent, size and time capped) and a `data:` URL, because a relay may differ.
- Sources: https://developers.openai.com/api/docs/guides/image-generation, https://developers.openai.com/api/reference/resources/images/methods/generate, https://developers.openai.com/api/reference/resources/images/methods/edit
- The edit reference also lists a JSON form (`images: [{ image_url }]`). The adapter uses the guide's multipart `image[]` form; the relay has not been tried with edits.

**Gemini** (`gemini` adapter)
- `POST {GEMINI_BASE_URL}/v1beta/models/{model}:generateContent`, header `x-goog-api-key`, JSON `{ contents: [{ role: 'user', parts: [{ text }, { inlineData: { mimeType, data } }, ...] }], generationConfig: { responseModalities: ['IMAGE'], imageConfig: { imageSize, aspectRatio } } }`.
- Response `candidates[0].content.parts[]` with `inlineData` (also read as `inline_data`) or `fileData.fileUri`; `usageMetadata` is printed. A reply with no image is reported with its `finishReason`, `promptFeedback.blockReason` and any text.
- Up to 14 reference images (Nano Banana 2.1: 10 object and 4 character images).
- Output format: neither API documents a PNG option. In `generateContent`, `generationConfig.responseFormat.image.mimeType` has one value, `IMAGE_JPEG`; the Interactions API reference lists only `image/jpeg` for `response_format.mime_type`. There is no flag for it, and Gemini output is JPEG. Checked on 2026-11-01: https://ai.google.dev/api/generate-content (ImageResponseFormat), https://ai.google.dev/api/interactions.
- Sources: https://ai.google.dev/api/generate-content (`GenerationConfig.responseModalities`, `ImageConfig`), https://ai.google.dev/gemini-api/docs/image-generation (sizes, token counts, reference limits).
- Google's image guide now shows the Interactions API (`/v1beta/interactions`) as its main path. The relay lists `generateContent` as its Gemini endpoint, so that is what this adapter uses.
