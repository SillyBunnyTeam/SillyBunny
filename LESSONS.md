### Scroll, streaming and cancellation

- **Breaks:** rendering or resizing moves the reader's position; cancelling leaves stream state behind.
- **Files:** `public/script.js`, `public/scripts/chat-render-lifecycle/`, `public/scripts/chats.js`, `src/request-cancellation.js`.
- **Guards:** `chat-render-lifecycle/scroll-intent.js` decides when to follow the newest message, `resize-observer.js` handles content that resizes after render, and `mobile-viewport.js` handles mobile viewport changes.
- **Guards:** a page hands its chat replies to the server and stops its stream on `pagehide`, not `beforeunload` (`public/scripts/resumable-generation.js`, `public/script.js`). A leave-site prompt can cancel `beforeunload`, and the page then stays with replies the server still writes into the chat (PR #877 review). Test: `tests/resumable-generation-frontend.test.js`.
- **Guards:** Stop cancels the run, so `Generate()` never reaches its finish path for the stopped reply. `stopGeneration()` calls `StreamingProcessor.finalizeStoppedMessage()`, which ends the reasoning with all reasoning that arrived, records `extra.reasoning_duration`, removes `extra.server_generation_placeholder` and saves the chat. Without it, a reply stopped during reasoning kept "Thinking..." and a null duration, and no save followed Stop, so a chat reload right after Stop dropped the reply (10f2b91e4 set `isStopped` in `onStopStreaming()`; 0167ddc2a made Stop a cancellation that clears the streaming processor). Tests: `tests/story-mode-request-controls.test.js`, `tests/server-generation-commit.e2e.js`.
- **Guards:** a Gemini reply that stops early can look finished or blank, because thinking counts against the output limit and a single request has a token cap. `CONTINUATION` and `MAX_TOKENS` from generateContent and `requires_continuation` and `incomplete` from Interactions reach the client as a length finish, and the direct Gemini sources then show a warning (`warnsOnGenerationLengthFinish()` in `public/scripts/generation-request-controls.js`, `src/endpoints/backends/chat-completions.js`). `StreamingProcessor.providerLengthFinish` is separate from `finishReason`, which records the provider's finish only with a prose cap and also covers the local cap. A chunk with a `continuationToken` and no `finishReason` is a checkpoint, not a finish. Tests: `tests/story-mode-request-controls.test.js`, `tests/google-model-request.test.js`, `tests/gemini-interactions.test.js`.
- **Guards:** `src/gemini-long-decode.js` continues a Gemini reply across requests while Google answers `CONTINUATION` or `requires_continuation`, so those finishes reach the client only when long decode could not go on. Every request repeats the same body with the newest token. Google counts `maxOutputTokens` across requests and answers 400 once a request's limit is spent, so later requests send the full limit. The stream removes the `CONTINUATION` finish and every token before forwarding, because `public/scripts/openai.js` keeps a length finish once it sees one. A `CONTINUATION` finish continues from the newest token whatever went out after that token, as Google's js-genai SDK does. A stream that stops with no finish resumes from its token only when nothing visible went out after that token, because the next request repeats that content and the client cannot take it back; otherwise the stream ends with a cut-off finish. A token the request already has marks nothing new, so content beside it counts as content after the token. A new token covers the text on its own event: live streams carried one on every event from about 32K tokens on, and resuming from such a token on 2026-11-05 repeated nothing. A request that stops with no new token and no content goes out again up to 3 times. An HTTP error status, a blocked prompt, an error event with no new token and a status that asks for the next request with the same token all end the reply instead. A non-streaming request's text joins parts with a separator and joins requests with none, because a request boundary can fall inside a word. The first non-streaming Gemini 4 request above 32,768 tokens goes out capped, and only that request continues past `MAX_TOKENS`. Vertex uses `v1beta1` for the same Gemini 4 limits and `v1` for everything else. Each later request calls `extendLifetime()` on the resumable generation, because one reply can outlast the sweep's lifetime limit while no single request can. `readRawEvents()` keeps an event in pieces and scans only the new text, because a regex flattens a concatenated string on every read and that cost grows with the square of an inline image's size. Tests: `tests/gemini-long-decode.test.js`, `tests/google-model-request.test.js`, `tests/gemini-interactions.test.js`, `tests/resumable-generations.test.js`.
- **Guards:** `getGemini3ThinkingLevel()` in `src/prompt-converters.js` sends `high` for `xhigh` and `max` on Gemini 4, because its documentation names no higher level. Gemini 3 models still receive the picked rung. Test: `tests/prompt-converters.test.js`.
- **Tests:** `tests/chat-render-lifecycle-script-wiring.test.js`, `tests/chat-scroll-regressions.e2e.js`, `tests/request-cancellation.test.js`, `tests/in-chat-agents-companion-panel.test.js`, `tests/sse-stream.test.js`, `tests/frontend/SseStream.e2e.js`.
- **Fixes:** #271 (stabilise chat scrolling), #314 (cancel when a stream disconnects), #771 (resize and load lock work against each other), #783 (streaming moves the screen).

### Chat writes, reloads and backups

- **Breaks:** an old queued write replaces a newer chat; backups push each other out of the backup ring.
- **Files:** `public/scripts/chat-save-guard.js`, `public/scripts/chat-reload-guard.js`, `src/endpoints/chats.js`, `src/generation-commit.js`, `public/scripts/server-generations.js`.
- **Guards:**
  - The server writes a reply over an existing message only when that message carries `extra.server_generation_placeholder` with the generation's start time. The browser removes the mark when the reply is finished or stopped, so a reply the page saved itself, and later edits to it, are not overwritten (`src/generation-commit.js`).
  - `Generate()` awaits `settleGenerationCommit()` before it saves a finished reply. If the server answers `committed`, the page reloads the chat and does not save its own copy, which would fail the integrity check. Stream readers return at `[DONE]`, which can come before the body ends and claims on its own (PR #877 review).
  - A tab keeps its server event stream (`public/scripts/server-generations.js`) only while it is visible or reads a reply of its own. Over HTTP/1.1 a browser opens about 6 connections per server for all its tabs; with a stream in every tab, a seventh tab never loads (PR #877 review). Tests: `tests/server-generations-frontend.test.js`, `tests/server-generation-commit.e2e.js`.
  - A tab that reloaded once for a server-written reply and still finds no mark for it acknowledges it. Otherwise each reload reconnects, hears of the reply again and reloads again until the server forgets it.
  - `reloadCurrentChat()` removes an open message editor but leaves `this_edit_mes_id` set. A reload for a server-written reply reopens the edit with its unsaved text through `messageEdit()`, unless the reply changed that message, and clears the id with `setEditedMessageId()` (`restoreOpenEdit()` in `public/scripts/server-generations.js`). Waiting with the reload does not help: once the server has written the chat, saving the edit fails the integrity check. Tests: `tests/server-generations-frontend.test.js`, `tests/server-generation-commit.e2e.js`.
- **Tests:** `tests/chat-cloning-lifecycle.test.js`, `tests/chat-save-guard.test.js`, `tests/chat-save-queue-runtime.test.js`, `tests/chat-integrity-rotation.test.js`, `tests/reload-chat-safeguard.test.js`, `tests/prove-368-differential.test.js`, `tests/server-generation-commit.test.js`, `tests/resumable-generation-frontend.test.js`, `tests/story-mode-request-controls.test.js`.

### Chat, group, file, vector and asset route input

- **Breaks:** a request field, a stored group chat ID, a line in a chat file or a failed download makes a route use a path outside its folder, or makes the route throw outside its error handling.
- **Cause:** a rejection from an async route reaches `handleRouteError()` in `src/route-errors.js`, which answers 500 without saying what was wrong, and a throw in a stream or readline event crashes the server, which the supervisor then restarts. So that code must answer its own errors. A JSON body or an extended query string can send an object whose `toString` is not a function, and loose equality, `String()`, template literals and `toString()` throw for it. `pipe()` leaves an error from its source stream unhandled. Paths were checked with a string prefix or not at all, and `sanitize()` (sanitize-filename 1.6.3) turns `.`, `..` and Windows device names into an empty name, which makes the joined path name the folder itself.
- **Files:** `src/endpoints/files.js`, `src/endpoints/chats.js`, `src/endpoints/groups.js`, `src/endpoints/vectors.js`, `src/endpoints/assets.js`.
- **Guards:**
  - `/api/files/delete` and `/verify` accept a path only inside the files folder (`isPathUnderParent()`). A string prefix also accepts sibling folders whose names start with the files folder name.
  - `getGroupChatPath()` in `src/endpoints/chats.js` joins a stored group chat ID only when it is a string or a number and its path stays inside the group chats folder. Chat search and recent chats skip any other ID, and group create and edit answer 400 for a chat list that holds one. A slash inside the folder, as in a checkpoint name, and numeric IDs from older groups still pass.
  - Chat export runs inside one `try` block and answers 400 for a `file` that is not a string or that sanitizes to an empty name. It waits for its read stream through a promise with `error` listeners on the stream and on readline, because readline re-emits input stream errors and an `error` event without a listener throws. It skips a line that is not a chat message, such as an empty line in an older chat file.
  - `getChatInfo()`, which chat search, recent chats and group chat info read through, counts and matches `mes` only when it is a string, because nothing catches a throw in its readline event.
  - Group delete answers 400 for an `id` that is not a string or a number.
  - The vector routes return `regenerateCorruptedIndexErrorHandler()` from their catch blocks, so it catches errors from its own regeneration and answers 500.
  - `getIndex()` refuses a vector source or collection ID that sanitizes to an empty name, and the routes answer 400. Vector purge answers 400 for such a collection ID, so each purge path is one collection folder inside its source folder.
  - `validateAssetFileName()` in `src/endpoints/assets.js` refuses a file name that is not a string, so asset delete, asset download and Data Bank upload answer 400 for one. The asset routes compare the category with `===`, and the character asset list answers 400 for a `name` that is not a string.
  - Asset download writes the body through `pipeline()`, so an error in the download body answers 500. With `pipe()`, the request never got an answer under Node.js, and Bun raised the error as uncaught. Its catch block answers only when nothing was sent, because the character branch answers before it removes the temp file.
- **Tests:** `tests/route-guards-scenarios.test.js`, `tests/route-guards-rows.test.js` (rows on the hostile file name harness, `tests/util/hostile-file-names-*.js`). `tests/hostile-file-names-storage.test.js` requires 400 from the vector routes for every source and collection ID that sanitizes to nothing, except an empty source, which the routes replace with `transformers`.
- **Fixes:** `8bd570ff8` (files folder), `7c1cb041b` (group chat IDs), `5f40fd1cb` (chat export and chat info), `cab2e7be3` (group delete id), `3819943a4` (vector index regeneration), `5c194ad04` (vector folder names), `42e7698e4` (asset routes).

### Route errors and crashes

- **Breaks:** one request that fails outside its route's error handling ends the server, and the server stays down.
- **Cause:** Express 4 ignores the promise that a route handler or middleware returns, so a rejected async route got no answer and reached the `unhandledRejection` handler in `src/server-main.js`. That handler and the `uncaughtException` handler exited with code 0, which the supervisor passes on as a stop. A throw in a stream, readline or timer callback still reaches `uncaughtException`, because no route is on the stack there.
- **Breaks:** the client's CSRF retry (#475) never runs.
- **Cause:** `fetchWithCsrfRetry()` in `public/scripts/csrf-token-refresh.js` refreshes the token and repeats the request only for a 403 whose body contains `Invalid CSRF token`. Express's default error handler sends only the status text in production, and `server.js` defaults `NODE_ENV` to production, as `Start.bat`, `Start-Node.bat`, `start.sh`, the `Dockerfile` and `docker/docker-compose.yml` set it, so the 403 said only `Forbidden`.
- **Files:** `src/route-errors.js`, `src/server-main.js`, `src/server-supervisor.js`.
- **Guards:**
  - `forwardAsyncRouteErrors()` in `src/route-errors.js` replaces `handle_request()` and `handle_error()` on the Express 4 `Layer` prototype, so a rejected promise from a handler or an error handler goes to `next()`, as the Express 5 router does. It covers every app, router and route made from the server's copy of Express, including the routers that server plugins get. It does not cover a router made from another copy of Express or code that runs outside a route. A falsy rejection reason becomes `Error('Rejected promise')`, because `next()` with a falsy value goes on to the next route. Express 5 does this itself, so the module goes with an upgrade to Express 5.
  - `handleRouteError()` is registered after the not-found handler, before the server listens. Express calls a four-parameter middleware only for errors and skips the not-found handler for them, so both only have to come after every route, plugin routes included. It logs the error as Express's default handler did, and a client disconnect as the same warning as the process handlers. It answers with the error's own 4xx or 5xx status (400 or 413 from the body parser, 403 for a CSRF token) or 500, with only the status text as the body in every `NODE_ENV`; Express's default handler sent the stack trace outside production. It does not answer a response that has started: it destroys the socket of an unfinished one and leaves a finished one alone.
  - The CSRF refusal is the one error answered with its own message. csrf-sync 4.2.1 makes one `invalidCsrfTokenError` per protection object and passes that object to `next()` for every refused request. `src/server-main.js` sets its message and passes it to `answerWithErrorMessage()`, so `handleRouteError()` answers it with 403 and that message as `text/plain`, without the chalk color codes, which `stripVTControlCharacters()` from `node:util` removes under Bun and Node.js. The match is the object itself, not the `EBADCSRFTOKEN` code that other CSRF libraries also use, so another error with that code keeps the status text.
  - The `uncaughtException` and `unhandledRejection` handlers exit with `SERVER_CRASH_EXIT_CODE` (1) after the usual cleanup, or after `SUPERVISOR_FORCE_KILL_TIMEOUT_MS` when a cleanup step fails or does not finish.
  - `runSupervisor()` relaunches a child that reported startup (`SERVER_STARTUP_READY_MESSAGE`) and then exits with a non-zero code or a signal while no stop was requested. It waits `SUPERVISOR_CRASH_RESTART_DELAY_MS` (1 s), doubled for each crash restart within `SUPERVISOR_CRASH_WINDOW_MS` (10 minutes), and a crash after `SUPERVISOR_CRASH_RESTART_LIMIT` (5) such restarts ends the supervisor with the child's exit code. A stop request ends the wait at once. A failure before startup, exit code 0, the restart, plugin update and supervisor reload codes and a requested stop behave as before. The launchers loop only on exit code 75, and Docker's `restart: unless-stopped` restarts on any exit, so they need no change.
- **Limit:** a crash restart loses what the server process holds in memory, such as session-auth sessions and server-side generations that were running.
- **Tests:** `tests/route-errors.test.js`, `tests/server-supervisor-crash-restart.test.js`, `tests/csrf-refusal-retry.test.js` (the csrf-sync setup of `src/server-main.js` with a colored message, and `fetchWithCsrfRetry()` against its real answers).
- **Fixes:** `ae27417cc` (async route errors), `120fa5fbf` (crash restarts), `a41adfe62` (crash exit code), `b0735ddab` (CSRF refusal text).

### Runtimes, Termux, launchers and updates

- **Breaks:** the wrong runtime or shell behaviour on one platform.
- **Files:** `Start-Node.bat`, `scripts/`, `src/npm-launcher.js`, `src/endpoints/server-admin.js`.
- **Guards:** `server.js` runs under `src/server-supervisor.js`. It loads `src/server-log-buffer.js` first and imports `src/server-main.js` last. Do not change this import order.
- **Bun and disconnects:** under Bun 1.3.12 and 1.3.14 an Express response emits no `close` when the client disconnects; the request and its socket do. Node emits all three, and emits the response's `close` from inside the socket's. The streamed routes in `src/resumable-generations.js` use `whenClientGone()`, which watches both and runs once (test: `tests/server-generation-commit.test.js`). Still on the response's `close`: `src/endpoints/backends/chat-completions.js`, `src/endpoints/server-admin.js`, `src/endpoints/chat-archive.js`, `src/server-listen.js`.
- **Bun and transformers.js images:** sillytavern-transformers takes its browser code path when `self` is defined, and Bun defines it. On that path `RawImage.fromBlob()` needs `createImageBitmap()` and `RawImage.resize()` needs `OffscreenCanvas`. Bun has neither, so local captioning failed for every image. `decodeRawImage()` in `src/transformers-image.js` decodes with the server's jimp and returns a `RawImage` subclass whose `resize()` also uses jimp (test: `tests/transformers-image.test.js`, which defines `self` so that Node.js takes the Bun code path). `crop()` and `center_crop()` still need a canvas under Bun; the default captioning model does not call them.
- **Bun and the listen port:** before Bun 1.4.0, sockets on Windows are inheritable (oven-sh/bun#36936, fixed by oven-sh/bun#36938). A process that the server starts, such as git during an update, can keep the port bound after the server exits. `engines.bun` still allows 1.3.14. The listen retry window in `src/server-listen.js` and `GIT_OPTIONS` in `src/endpoints/server-admin.js` (no background git maintenance during updates) guard against it. `hasBunSocketInheritBug()` limits the port-conflict hint and the dead-holder diagnostic to Bun before 1.4.0 on Windows (test: `tests/server-listen.test.js`). Before Bun 1.4.3, `closeAllConnections()` does nothing once `close()` has run (oven-sh/bun#43557), so `closeListeningServers()` also destroys the tracked sockets.
- **Bun and fetch idle timeouts:** under Bun 1.4.4, `fetch` ends a request with `TimeoutError: The operation timed out.` after 360 seconds with no bytes, including a gap in the middle of a stream. Node.js 24.22.1 does not. `timeout: 0` turns this off under Bun, and `node-fetch` 3 ignores the option. In `src/endpoints/backends/chat-completions.js` only the Mistral, Cohere, generateContent and Interactions requests pass it (tests: `tests/google-model-request.test.js`, `tests/gemini-interactions.test.js`).
- **Git child processes:** simple-git 4 removes every `GIT_*` variable and `EDITOR`, `VISUAL`, `PAGER`, `PREFIX` and `SSH_ASKPASS` from the environment of the git processes it starts, unless the `allowEnvironment` option names them. SillyBunny sets no `allowEnvironment`, so a user's `GIT_SSH_COMMAND`, `GIT_ASKPASS` or `GIT_CONFIG_GLOBAL` does not reach git during server updates, server plugin updates, or extension installs and updates. simple-git 4 also sets `GIT_TEST_DISALLOW_ABBREVIATED_OPTIONS`, so git stops on an abbreviated long option such as `--dep` for `--depth`; write options in full. It refuses a `-c` key that it treats as unsafe, such as `core.sshCommand`; `GIT_OPTIONS` sets only `gc.auto` and `maintenance.auto`.

### Character import and upload files

- **Breaks:** data in an imported card or archive, in an uploaded sprite or sprite pack, or in a create request decides which folder the server writes to, which file type it stores, or how long the card parser runs.
- **Cause:** the import and upload code takes names, extensions and chunk lengths from the data it receives. A name that sanitizes to nothing makes the parent folder the target folder, an archive or uploaded file keeps its own extension, `sanitize-filename` keeps only the first 255 bytes of a name and so can cut off an extension at its end, and `png-chunks-extract` allocates, copies and checksums the length that a chunk declares before it finds that the file is shorter.
- **Files:** `src/endpoints/characters.js`, `src/endpoints/sprites.js`, `src/image-file-type.js`, `src/character-card-parser.js`, `src/png/extract.js`, `src/charx.js`, `src/byaf.js`.
- **Guards:**
  - `getCardAssetFolder()` in `src/endpoints/characters.js` names the asset folder of a CHARX or BYAF card after the sanitized card name, or after the card's file name when the name sanitizes to nothing. A CHARX import skips its assets when that name is not a folder directly inside the characters and user images folders. A preserved name such as `...png` gives that on POSIX systems, where `getPreservedName()` does not sanitize.
  - `isImageFile()` in `src/image-file-type.js` accepts a file only when its extension is png, apng, jpg, jpeg, jfif, gif, webp, avif or bmp and its leading bytes are an image of that type. A BYAF import stores a background or an alternate icon, and a CHARX import an asset, only when it passes; `isArchiveImage()` in `characters.js` logs the others. The stored bytes are the archive's bytes. A BYAF chat names only the backgrounds that were stored.
  - `POST /api/sprites/upload-zip` stores a pack entry only when its sanitized name passes `isImageFile()`. `POST /api/sprites/upload` keeps the uploaded extension when that passes, takes the extension of the image type that the bytes are (`getImageExtension()`) when it does not, and answers 400 when the sanitized name still fails, before it replaces an existing sprite. A sprite uploaded from a URL arrives as `image.png` whatever its type, so a wrong image extension is replaced and not refused. `readImageSignature()` reads only the leading bytes of the upload.
  - `POST /api/characters/import` takes the import function only when `Object.hasOwn(formatImportFunctions, format)`, so every other file type gets the unsupported format answer.
  - `POST /api/characters/create` answers 400 to a `file_name` that sanitizes to nothing, such as `.` or `..`, because the same name also names the card's chats folder.
  - `src/png/extract.js` walks the chunk headers up to IEND before `png-chunks-extract` runs, and throws `PNG chunk at byte <n> runs past the end of the file` when a chunk header or the data length it declares does not fit in the file. `read()` and `write()` in `src/character-card-parser.js` use it. A file that ends inside the CRC of a chunk still gets the CRC error, and a file that ends inside the CRC of IEND still imports.
- **Tests:** `tests/character-archive-assets.test.js`, `tests/character-route-names.test.js`, `tests/png-chunk-bounds.test.js`, `tests/png-chunk-fuzz.test.js` (chunk lengths past the end of the file and files cut inside a chunk), `tests/card-import-corpus.test.js` (import, export and import again for each card and chat format), `tests/sprite-upload-images.test.js`.

### Security and credentials

- **Breaks:** untrusted card scripts reach remote resources; secrets cross scopes.

### Accounts and session login

- **Breaks:** an account or session route reads a request field, a handle or a server path that it has not checked, or answers before the checks that guard the other routes.
- **Cause:** Express 4 does not catch a rejection from an async route or middleware, so that code must answer its own errors. `toKey()` reads an array as the handle in it, and `getUserDirectories()` joins a handle into a path as it is.
- **Files:** `src/middleware/sessionAuth.js`, `src/server-main.js`, `src/users.js`, `src/endpoints/users-public.js`, `src/endpoints/users-private.js`, `src/endpoints/users-admin.js`, `public/scripts/sillybunny-tabs.js`.

An error with a syscall answers 500 with the generic message; an archive error answers 400 with its message (`2d093e8af`).

### Dependencies and lockfiles

- **Breaks:** `package-lock.json` and `bun.lock` drift apart, or Bun cannot read `bun.lock` and resolves again from the registry without the release-age gate.
- **Files:** `package-lock.json`, `bun.lock`, `tests/package-lock.json`, `.npmrc`, `Dockerfile`, `start.sh`, `Start.bat`, `Start-Node.bat`.
- **Guards:**
  - Both lockfiles ship. The Bun launchers install from `bun.lock` with `--frozen-lockfile` (`start.sh:250`, `Start.bat:141-145`), and so does the Docker image (`Dockerfile:24`). `Start-Node.bat` and CI's `npm ci` use `package-lock.json`. The launchers restore the tracked lockfiles after an install (`start.sh:306-313`, `Start.bat:168-174`).
  - When every change in the checkout is to `bun.lock`, `package-lock.json` or `package.json`, `getRepositoryStatus()` in `src/endpoints/server-admin.js` restores them with `git restore --staged --worktree`. `POST /api/server-admin/status` and `POST /api/server-admin/update` call it, so either request discards uncommitted dependency edits in the checkout that the server runs from. Commit those edits before you start a server there.
  - When a frozen Bun install fails, the launchers retry without `--frozen-lockfile` (`start.sh:275-288`, `Start.bat:162-165`). The retry resolves from the registry and does not use the committed `bun.lock`.
  - `npm audit` reads only `package-lock.json`. Check `bun.lock` with `bun audit`.
  - `min-release-age=7` in `.npmrc` applies to npm only. Bun 1.4.4 ignores it and chose an `electron-to-chromium` release from the day before. Bun reads `--minimum-release-age=<seconds>` or `minimumReleaseAge` in `bunfig.toml`. To keep the gate, update `package-lock.json` with npm, move `bun.lock` aside and run `bun pm migrate`. Without a `bun.lock`, `bun install` also migrates from `package-lock.json`.
  - Bun 1.4 writes `"lockfileVersion": 2` for a new or migrated lockfile (oven-sh/bun#31539). Bun 1.3.14, which `engines.bun` still allows, stops with `Unknown lockfile version`. Version 2 adds only parse-time checks, and Bun 1.4 keeps an existing version 1 lockfile at version 1 (oven-sh/bun#31602). After a migration, set the version back to 1 and check that frozen installs on Bun 1.4.4 and 1.3.14 leave `bun.lock` byte-identical.
  - After a change to `overrides`, Bun 1.4.4 fails a frozen install with `overrides in package.json changed since bun.lock was saved`, and the launcher retry then resolves without the gate. Regenerate both lockfiles after an `overrides` edit.

With a nested override such as `"vectra": { "uuid": "^11.1.1" }`, Bun 1.4.4 writes `"lockfileVersion": 3` instead of 2 (checked with `bun install --lockfile-only`), and the reset to version 1 above does not cover it.   - The server never loads the installed `protobufjs`. The Node.js entry of onnxruntime-web, `dist/ort-web.node.js`, requires only Node.js built-ins and `onnxruntime-common`. Only `onnxruntime-web/lib/onnxjs/` requires `onnx-proto`, and nothing imports it.
  - The browser bundle never uses the installed `lodash-es`. `webpack.config.js` aliases `chevrotain` to its prebuilt `lib/chevrotain.mjs`, which carries its own copy of the lodash functions it uses. That copy has neither `_.template` (GHSA-r5fr-rjxr-66jc) nor `_.unset` and `_.omit` (GHSA-f23m-r3pf-42rh). Outside `tests/`, only `public/lib.js` imports chevrotain.

  - `tests/` has its own `package.json`, and npm reads only the `.npmrc` next to the nearest `package.json`. ### Macro whitespace

- **Breaks:** a trim in the macro engine removes whitespace that a template asks for with `{{newline}}`, `{{space}}` or `{{noop}}` (SillyTavern/SillyTavern#5673 and SillyTavern/SillyTavern#5674).
- **Cause:** the engine trims text after it resolves the macros in it. `{{if}}` trims its resolved branch, scoped macros trim their content, and variable shorthand values (`{{.x = ...}}`) are trimmed. The legacy `{{trim}}` post-processor runs after `{{noop}}` is already an empty string, so `{{noop}}` does not stop it as it did in the legacy engine (`public/scripts/macros.js`).
- **Files:** `public/scripts/macros/engine/MacroCstWalker.js`, `public/scripts/macros/engine/MacroEngine.js`, `public/scripts/macros/definitions/core-macros.js`.
- **Guards:** `public/scripts/macros/sillybunny-whitespace-markers.js`. The walker wraps `{{newline}}` and `{{space}}` output in U+FDD0 and `{{noop}}` output in U+FDD1, and removes them after each trim. `MacroEngine.evaluate()` removes them before it returns, except for the `{{if}}` branch, which `resolve(text, { keepWhitespaceMarkers: true })` returns with markers for the trim in the `{{if}}` handler. Only the `core:` post-processors see the markers.
- **Tests:** `tests/sillybunny-macro-whitespace.test.js` (runs the real engine in Jest), `tests/frontend/sillybunny-macro-whitespace.e2e.js`.
- **Limit:** `{{trim}}` still removes `{{newline}}` output next to it, as the legacy engine did. Put `{{noop}}` between them to keep the newline.
- **Limit:** prompt text that already contains U+FDD0 or U+FDD1 loses those characters.

### Client addresses behind proxies

- **Breaks:** the whitelist, a rate limit or `requireHttps` decides on a forwarded value that no trusted proxy set.
- **Cause:** a reverse proxy adds the address it received the request from at the right end of `X-Forwarded-For`, and it can pass the other forwarded headers on from the client unchanged. The server cannot tell which headers its proxy set.
- **Files:** `src/express-common.js`, `src/middleware/whitelist.js`, `src/middleware/requireHttps.js`, `src/middleware/basicAuth.js`, `src/middleware/hostWhitelist.js`.
- **Guards:**
  - The trusted hops are the valid entries of the `whitelist` setting (`getTrustedProxies()` in `src/express-common.js`). `whitelist.txt` and the Docker host addresses do not count. `getForwardedIps()` returns the address in each enabled forwarded header and reads `X-Forwarded-For` from the right: it skips trusted hops, and the first other entry is the client.
  - With `enableForwardedWhitelist` on, the whitelist blocks a request unless every address that `getForwardedIps()` returns is listed, and it names the first unlisted one.
  - `getIpAddress()` adds a forwarded address only when the socket address is a trusted hop and every enabled header names the same valid address. Otherwise it returns the socket address. The basic auth, account login, account recovery, password reset and conversation message limiters and the access log read their address through it.
  - `isIpInPatterns()` parses addresses strictly and treats a value that is not an IP address as unlisted, so a malformed forwarded value or a socket without an address gets 403, not 500. An IPv4-mapped value matches its IPv4 entry.
  - `requireHttps` lets plain HTTP through only from a loopback socket address without forwarding headers, whatever the `Host` header says. It reads the first `X-Forwarded-Proto` value, and only from a trusted hop.
  - Basic auth matches no request when the configured username or password is empty or is not a string, and it compares the configured user with `crypto.timingSafeEqual()` over SHA-256 digests.
  - `hostWhitelist.enabled` goes through the `'boolean'` converter, so `SILLYTAVERN_HOSTWHITELIST_ENABLED=false` turns the host check off.
- **Tests:** `tests/forwarded-client-address.test.js`, `tests/require-https-client-address.test.js`, `tests/basic-auth-configured-credentials.test.js`, `tests/host-whitelist-enabled-switch.test.js`, `tests/middleware-whitelist.test.js`, `tests/middleware-host-whitelist.test.js`, `tests/middleware-basic-auth.test.js`, `tests/middleware-require-https.test.js`.
- **Fixes:** `1b127a865` (whitelist), `06dc7a6e0` (rate-limit keys), `e059e5d23` (`requireHttps`), `0a836ed40` (basic auth credentials), `30ecce06d` (host whitelist switch).

### Slash commands and STscript

- **Breaks:** the STscript parser reads a script differently from how it is written. A closing mark, a pipe or an escaped character is skipped or taken twice, so a command ends up in another command's value, a value gains text such as `undefined` or `[Closure]`, or the parser throws a `TypeError` instead of a parser error.
- **Cause:** the parser moves one index through the text. Branches that return from a nested parse (a nested block comment, the quoted rest of a split-count command, an unclosed quote in lenient parsing) took one more character. Positions were counted back from an index that had already moved past whitespace or a closing quote. The split branches lost an escaped first character, because the parser took it before it started to split.
- **Files:** `public/scripts/slash-commands/SlashCommandParser.js`, `public/scripts/slash-commands/SlashCommandParserError.js`.
- **Guards:** every `SlashCommandParserError` carries the text and the index. The error handler of `executeSlashCommandsWithOptions()` reads its line, column and hint, and without them it throws a `TypeError` instead of showing the parser error.
- **Tests:** `tests/frontend/StscriptParserFixes.e2e.js` (one test or more for each fix, through `tests/frontend/stscript-parser-harness.js`).
- **Limit:** macro positions are still counted back from the end of a value, so a macro is indexed one character late for each escape that follows it in the value. With `REPLACE_GETVAR`, the macro index describes the replaced text, not the source.
- **Open:** `SlashCommandExecutionError.hint` slices its source as the parser error did, so an execution error on a line that another line follows shows the line without its last character (`/let x 1 | /let x 2` followed by a new line shows `/let x `).
- **Fixes:** `15b28ab1b` (nested block comments), `cebf47278` (`/let` with an empty `key=`), `627eb8cc8` (split argument error without text), `aa6f61ce1` (escaped first split value), `b420e832d` (`/parser-flag` without a name), `996ce24cf` (quote flags for closures), `f3e74ca1d` (quoted split-count rest), `87bd300e0` (closure in a joined rest), `cfc4fcf73` (macro positions in quoted values), `5e17bdc22` (unclosed quote in lenient parsing), `039e44a8e` (unknown command position), `643ad824a` (error hint line).
