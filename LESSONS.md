This file lists the bugs that recur in SillyBunny, where they happen, and what guards against them. Read the section for the area you change before you fix a bug or make a non-trivial change.

## Recurring bugs

The sections go from the most fixes to the fewest. "No test" lists fixes that shipped without a test that guards them.

### Mobile, viewport and WebKit

This is the largest class by a wide margin.

- **Breaks:** viewport or virtual keyboard changes hide the composer or detach the shell.
- **Files:** `public/css/sillybunny-mobile-shell.css`, `public/css/sillybunny-tabs.css`, `public/style.css`, `public/scripts/sillybunny-tabs.js`.
- **Tests:** `tests/mobile-keyboard-focused-input-scroll.test.js`, `tests/mobile-shell-lifecycle-wiring.test.js`, `tests/expanded-editor-touch.e2e.js`, `tests/openrouter-picker-touch.e2e.js`, `tests/webkit-prefix-companions.test.js` (WebKit prefix parity, #562).
- **Limit:** `tests/mobile-ios26-keyboard-layout.e2e.js` simulates `visualViewport` in Chromium. It does not test real Safari.
- **Limit:** `tests/webkit-prefix-companions.test.js` checks `backdrop-filter` and `user-select` in fork `.css`, inline CSS in JavaScript and HTML, and bundled agent templates. It skips the upstream-origin files in `tests/fixtures/upstream-origin-public-files.json` and does not check camelCase style properties such as `style.backdropFilter`. It uses its own brace scanner because `@adobe/css-tools` 4.4.4 does not parse CSS nesting and drops rules in `public/style.css`.
- **Side-panel sheets:** adopted upstream panel sources can retain mobile `100dvw` sizing; constrain the source and its descendants to the panel. Size sheets from available space, not their intrinsic height: a flex child with percentage sizing can otherwise collapse the source and its nested scroller to zero. Keep same-side docked panels split across the measured chat-shell height. Tests: `tests/side-panel-adapters.e2e.js` (390×844, 360×740, 1440×900, split panels) and `tests/mobile-shell-smoke.e2e.js` (MovingUI containment).
- **Lazy images in a closed `<details>`:** Chromium still fetches an `<img loading="lazy">` inside a closed `<details>`, so a large image in a collapsed expander must get its `src` only when the expander first opens. Found with the former Home "More Assistants" expander (`342c557dd`), which the one-column Home removed; no current code depends on it.
- **Closed menus stay in the DOM:** every registered side panel keeps its `role="menu"` element (`public/scripts/sillybunny-editor/side-panel.js:268–269`) while closed, so "is a menu open?" must test for a visible box, not for a `[role=menu]` match. A plain match made the former Bundled Extras page inside Home (`342c557dd`) ignore Escape forever; that page is now a window, whose dialog frame handles Escape, so no current code depends on this.
- **Side-panel sheets without a composer:** a phone side-panel sheet sits above `#form_sheld`, and Home hides the composer (`#sheld[data-sb-home='on'] > #form_sheld { display: none }`, `public/css/sillybunny-home.css`). A `display: none` composer has an all-zero rect, so a sheet anchored to its top got zero height. `getSheetAnchorTop()` in `public/scripts/sillybunny-editor/side-panel.js` uses the bottom of `#sheld` when the composer has no layout box. Tests: `tests/unit/side-panel.test.js`, `tests/home-state.e2e.js` (a sheet opened on Home is taller than 100px and stays inside `#sheld`).
- **Docked side-panel bounds:** side panels also carry `.sb-dialog--window`, so the Window's `max-height: 90dvh` can clip a panel below the chat shell. Remove that cap from docked panels; `tests/side-panel-adapters.e2e.js` checks the panel against `#sheld` at 1440×900. Introduced by `70801186d`.
- **Detached modal content:** moving mobile chat tools into a shared dialog without hiding the source fragment leaves its search field painted in the document. This was introduced by `aa19e952a` and affected the Characters mobile opening path as well as Toggle Panels. Keep detached dialog content hidden and inert until the frame owns it, then hide it again after disposal. Test: `tests/mobile-character-toggle-and-panels.e2e.js`.
- **Mounted list spacing:** legacy tag controls carry a top margin, and the mobile drawer can apply a more specific margin on top. Reset that margin only inside the mounted Characters/Groups filter row; keep its 40px desktop and 44px mobile target. Test: `tests/character-list.e2e.js` (`Groups filter toolbar avoids extra vertical padding`).
- **Mobile editor labels:** a select that should sit below its label needs the shared combo row's `wide: true` mode. Otherwise its intrinsic-width suffix can squeeze labels such as Group Folder into multiple lines. Test: `tests/group-editor-member-lists.e2e.js` (`group folder label stays on one line on mobile`).
- **Popup scroll:** upstream `popup.css` sets `min-height: fit-content` and hides overflow on tall desktop popups, which clips the final rows. The tier frame fixes this; `tests/popup-scroll.e2e.js` checks the last row and visible response. Characterized by `e78207e03`, framed by `5d0d2dd9b`.
- **No test:** #438 (iOS overscroll blanks the page, keyboard moves the composer).
- **Fixes:** #658 (composer stays above the iOS keyboard), #840 (touch scroll in expanded mobile editors), #914 (pickers open during scroll).
- **Labels that may not fit:** a width breakpoint cannot decide whether a text label fits, because the label's width depends on the user's font size (`--fontScale`, the Global Font Size slider) and on the translation. The Home assistant card footers first used fixed container-query widths; at a 20px font or with the French "Start new chat", the ⋮ button sat up to 135px outside the card. `public/scripts/sillybunny-home/footer-fit.js` measures each footer with both labels shown (one read pass, one write pass, in an animation frame so the write cannot loop the `ResizeObserver`) and sets `data-sb-footer-compact` so both labels hide together; a CSS safety net (`min-width: 0`, ellipsis) keeps a miss inside the card. `scrollWidth` alone missed buttons that spilled into the footer's end padding, so the check compares the buttons' span with the content box. Tests: `tests/unit/sillybunny-home-footer-fit.test.js`, `tests/home-layout.e2e.js` (20px font, long labels, every card width).
- **Measure the placement you are testing for:** `header-fit.js` (`public/scripts/sillybunny-home/`) keeps the Home title centred on the column and moves the version below it when the version beside the title would touch the main menu button. Each pass removes `data-sb-version-below` first and measures the beside placement, so the answer depends only on current widths and cannot oscillate; below the title the version has zero inline size, so a text change resizes nothing, and a `MutationObserver` on the version triggers a pass. A test helper that measured the version in its current placement never found the switch point at 390 and 360. Tests: `tests/unit/sillybunny-home-header-fit.test.js`, `tests/home-layout.e2e.js` (title centred at every width and at 20px text, version below on narrow phones).
- **Popovers and the visual viewport:** a fixed popover is placed in layout-viewport coordinates, but the user sees only the visual viewport, which is smaller while zoomed in or while an on-screen keyboard is open. `getVisibleViewport()` (`public/scripts/sillybunny-action-menu.js`) clips `bounds` to the visual viewport's own rectangle: WebKit reports `innerWidth` and `innerHeight` as the visual size while pinch-zoomed, so clipping by them as well collapses a panned viewport to nothing. An open popover places itself again on `visualViewport` `resize` and `scroll`, once per frame, because an iOS pan and Chrome's resizes-visual keyboard fire neither a window resize nor a document scroll. A menu button at the end of a card inside much wider `bounds` passes `alignment: 'end'`; the automatic rule (a trigger in the start half of `bounds` aligns to its start) opened Home's Assistant Menu over the next card. Tests: `tests/unit/sillybunny-action-menu.test.js`, `tests/action-menu-viewport.e2e.js`.
- **`rem` does not follow the font slider:** the Global Font Size slider sets `--fontScale`, and `--mainFontSize` and every `--sb-type-*` token scale with it, but the root font size stays 16px, so a width in `rem` does not grow with the text. The art-and-text intro first stacked its line below the art at a `13rem` basis, which left about 18 characters per line beside 128px art at 20px text. `.sbArtIntro > p` uses `flex: 1 1 14em` in the line's own size (`public/css/sillybunny-windows.css`). Test: `tests/home-windows.e2e.js` (Shortcuts at 360×640 stacks at 20px text and sits beside its art at the default size).
- **Touch size follows the pointer, not the width:** the settings page's Back and Close (`.sb-settings-back-button`, `.sb-settings-close-button` in `public/css/sillybunny-tabs.css`) are 36px squares by default.
  - **Breaks:** with touch emulation, both measured 36×44px at 390×844 and 360×780, below the 44×44px that DESIGN.md (Touch targets) asks for on coarse pointers. At 820×1180 with touch, where the settings page has two columns, Close measured 36×36px.
  - **Cause:** `public/css/mobile-styles.css` loads only up to 768px wide (`media="(max-width: 768px)"` in `public/index.html`) and gives every `button` `min-height: var(--sb-mobile-touch-target, 44px)`. Phones got the height but not the width, and a touch screen wider than 768px got neither.
  - **Guard:** a `(pointer: coarse)` block after each base rule sets the width and height to `var(--sb-mobile-touch-target, 44px)`. It gives `.sb-settings-header-spacer` the same width, because the spacer balances Close and keeps the title centred in the two-column layout.
  - **Tests:** `tests/mobile-shell-smoke.e2e.js` (`settings Back and Close are at least 44px touch targets at 390 and 360 wide`). Before the fix it failed on the width of both buttons at both sizes.
  - **Limits:** the compact-mode rule (`:root[data-sb-compact-mode='true'] .sb-settings-close-button`, 28px) is more specific, so in compact mode Close stays 28px wide on a coarse pointer, and the 44px spacer puts the two-column title 8px right of centre. The test does not turn compact mode on.

### Scroll, streaming and cancellation

- **Breaks:** rendering or resizing moves the reader's position; cancelling leaves stream state behind.
- **Files:** `public/script.js`, `public/scripts/chat-render-lifecycle/`, `public/scripts/chats.js`, `src/request-cancellation.js`.
- **Guards:** `chat-render-lifecycle/scroll-intent.js` decides when to follow the newest message, `resize-observer.js` handles content that resizes after render, and `mobile-viewport.js` handles mobile viewport changes.
- **Guards:** a page hands its chat replies to the server and stops its stream on `pagehide`, not `beforeunload` (`public/scripts/resumable-generation.js`, `public/script.js`). A leave-site prompt can cancel `beforeunload`, and the page then stays with replies the server still writes into the chat (PR #877 review). Test: `tests/resumable-generation-frontend.test.js`.
- **Guards:** a freshly opened, greeting-only Reisen or Tewi chat stays at its top so the greeting picture is in view. The hold sits in the one bottom-scroll sink, `scrollChatElementToBottom`, through `shouldHoldChatAtTop()` (`public/scripts/sillybunny-home/greeting-art-opening.js`), and is not skipped for `force`, because the pins of a chat load are themselves forced. The resize compensation in `RossAscends-mods.js` writes `scrollTop` outside that sink, so it is guarded too: without it, the Temporary Chat banner moves the chat 46 px and ends the hold. A first version shadowed `#chat.scrollTop` with an own accessor; review found it swallowed the Go to bottom button and could snap back a scrollbar drag, so the sink guard replaced it. The hold must outlast the load lock (`script.js` 2400 + 250 ms); a unit test reads both. Tests: `tests/unit/sillybunny-greeting-art-opening.test.js`, `tests/greeting-art.e2e.js`.
- **Guards:** Stop cancels the run, so `Generate()` never reaches its finish path for the stopped reply. `stopGeneration()` calls `StreamingProcessor.finalizeStoppedMessage()`, which ends the reasoning with all reasoning that arrived, records `extra.reasoning_duration`, removes `extra.server_generation_placeholder` and saves the chat. Without it, a reply stopped during reasoning kept "Thinking..." and a null duration, and no save followed Stop, so a chat reload right after Stop dropped the reply (10f2b91e4 set `isStopped` in `onStopStreaming()`; 0167ddc2a made Stop a cancellation that clears the streaming processor). Tests: `tests/story-mode-request-controls.test.js`, `tests/server-generation-commit.e2e.js`.
- **Guards:** a Gemini reply that stops early can look finished or blank, because thinking counts against the output limit and a single request has a token cap. `CONTINUATION` and `MAX_TOKENS` from generateContent and `requires_continuation` and `incomplete` from Interactions reach the client as a length finish, and the direct Gemini sources then show a warning (`warnsOnGenerationLengthFinish()` in `public/scripts/generation-request-controls.js`, `src/endpoints/backends/chat-completions.js`). `StreamingProcessor.providerLengthFinish` is separate from `finishReason`, which records the provider's finish only with a prose cap and also covers the local cap. A chunk with a `continuationToken` and no `finishReason` is a checkpoint, not a finish. Tests: `tests/story-mode-request-controls.test.js`, `tests/google-model-request.test.js`, `tests/gemini-interactions.test.js`.
- **Guards:** `src/gemini-long-decode.js` continues a Gemini reply across requests while Google answers `CONTINUATION` or `requires_continuation`, so those finishes reach the client only when long decode could not go on. Every request repeats the same body with the newest token. Google counts `maxOutputTokens` across requests and answers 400 once a request's limit is spent, so later requests send the full limit. The stream removes the `CONTINUATION` finish and every token before forwarding, because `public/scripts/openai.js` keeps a length finish once it sees one. A `CONTINUATION` finish continues from the newest token whatever went out after that token, as Google's js-genai SDK does. A stream that stops with no finish resumes from its token only when nothing visible went out after that token, because the next request repeats that content and the client cannot take it back; otherwise the stream ends with a cut-off finish. A token the request already has marks nothing new, so content beside it counts as content after the token. A new token covers the text on its own event: live streams carried one on every event from about 32K tokens on, and resuming from such a token on 2026-11-05 repeated nothing. A request that stops with no new token and no content goes out again up to 3 times. An HTTP error status, a blocked prompt, an error event with no new token and a status that asks for the next request with the same token all end the reply instead. A non-streaming request's text joins parts with a separator and joins requests with none, because a request boundary can fall inside a word. The first non-streaming Gemini 4 request above 32,768 tokens goes out capped, and only that request continues past `MAX_TOKENS`. Vertex uses `v1beta1` for the same Gemini 4 limits and `v1` for everything else. Each later request calls `extendLifetime()` on the resumable generation, because one reply can outlast the sweep's lifetime limit while no single request can. `readRawEvents()` keeps an event in pieces and scans only the new text, because a regex flattens a concatenated string on every read and that cost grows with the square of an inline image's size. Tests: `tests/gemini-long-decode.test.js`, `tests/google-model-request.test.js`, `tests/gemini-interactions.test.js`, `tests/resumable-generations.test.js`.
- **Guards:** `getGemini3ThinkingLevel()` in `src/prompt-converters.js` sends `high` for `xhigh` and `max` on Gemini 4, because its documentation names no higher level. Gemini 3 models still receive the picked rung. Test: `tests/prompt-converters.test.js`.
- **Tests:** `tests/chat-render-lifecycle-script-wiring.test.js`, `tests/chat-scroll-regressions.e2e.js`, `tests/request-cancellation.test.js`, `tests/in-chat-agents-companion-panel.test.js`, `tests/sse-stream.test.js`, `tests/frontend/SseStream.e2e.js`.
- **Fixes:** #271 (stabilise chat scrolling), #314 (cancel when a stream disconnects), #771 (resize and load lock work against each other), #783 (streaming moves the screen).

### Bundled defaults, templates and user state

- **Breaks:** a refresh, reset or update overwrites user themes or templates, or brings back deleted defaults.
- **Files:** `default/`, `public/scripts/preset-manager.js`, `public/scripts/extensions/in-chat-agents/agent-store.js`, theme endpoints and theme CSS.
- **Guards:**
  - `src/endpoints/content-manager.js` does not overwrite a seeded file that already exists.
  - "Restore default presets" (`restoreDefaultPresetFiles`, `src/endpoints/content-manager.js`) used `cpSync(..., { force: true })` over every bundled preset, so it reset bundled presets the user had edited while its confirm text promised only that deleted ones come back. It now copies with `COPYFILE_EXCL` and skips a file that exists, edited or not, including one that appears during the restore (`tests/default-preset-deletions.test.js`). Bundled Extras restores one preset through `/api/presets/restore` and `/api/presets/save` instead (`public/scripts/sillybunny-home/bundled-extras-presets.js`).
  - `reconcileManagedBundledQuickReplies()` removes a bundled Quick Reply only when its hash matches a known stale version. It does not touch user-edited files.
  - Bundled agent template updates match by template `id` (`scripts/bump-agent-template-versions.js`). An update keeps the agent's enabled state, quick-toggle pin, order and profile overrides.
  - `✅ Run Unit Tests on PR` fails when an existing bundled agent template or `index.json` entry changes without a version bump. It runs `scripts/bump-agent-template-versions.js --check` against the PR's merge ref. After a commit, bump with `npm run agents:bump-template-versions -- --base origin/staging`; without `--base` the script compares only uncommitted changes against `HEAD`.
- **Tests:** `tests/preset-save-deleted-default.test.js`, `tests/create-only-installs.test.js`, `tests/sillybunny-theme-css.test.js`, `tests/theme-custom-css-import.test.js`, `tests/in-chat-agents-templates.test.js`, `tests/bump-agent-template-versions.test.js`, `tests/user-data-migrations.test.js`, `tests/startup-data-migrations.test.js`, `tests/config-key-migration.test.js`, `tests/bundled-default-validators.test.js`.
- **No test:** `a354f263d` (#753, redundant bundled-agent updates).
- **Fixes:** #687 (saving a preset over a deleted bundled default's name), #834 (an external theme pack wipes saved themes), #919 (theme data lost on update, export or reset; Custom CSS overwritten).
- **A bundled theme revision reaches users three ways:** new installs seed `default/content/themes/*.json` through `default/content/index.json` and take their applied palette from `default/content/settings.json`, which must match the default theme's file (`tests/libadwaita-theme-migration.test.js`). Existing installs keep their own copy, which `reconcileManagedBundledThemes()` (`src/endpoints/content-manager.js`) replaces only when its SHA-256 equals a previous bundled file (`MANAGED_BUNDLED_THEMES`, `CONTRAST_REVISED_THEME_HASHES`), so edited and deleted copies stay as they are. The colours a user has applied live in their own `settings.json`, which only a startup repair changes: `planThemeTextRepair()` (`public/scripts/sillybunny-theme-revisions.js`), run once from `public/scripts/power-user.js` behind `power_user.sb_theme_text_revision`, acts only when the saved theme name and all ten colour keys equal a previous bundled version, and replaces the CSS only when it is the previous bundled CSS. Without that repair a user keeps the old colours, and switching themes later shows the prompt for CSS no theme stores. Tests: `tests/bundled-theme-reconcile.test.js`, `tests/sillybunny-theme-revisions.test.js`, `tests/sillybunny-theme-text-repair.e2e.js`, `tests/bundled-theme-text-contrast.test.js` (every bundled theme's text roles reach 4.5:1).
- **Bundled extensions open their own first-run dialogs:** Quick Image Gen opens its setup wizard whenever its saved settings are missing or empty (`public/scripts/extensions/quick-image-gen/index.js`), which happens on a new install, after a settings reset and after an import without its settings. On a first run the wizard sat under the modal onboarding dialog, where its Skip button could not be pressed, and `waitForAppReady()` (`tests/frontend/frontent-test-utils.js`) needed a locator handler to close it. `seedQuickImageGenFirstRun()` (`public/scripts/sillybunny-first-run-defaults.js`), called once before `loadExtensionSettings()` in `public/script.js`, seeds `{ setupWizardSeen: true, starterPresetsSeeded: false }`: QIG treats any non-empty saved object as an existing install, so `starterPresetsSeeded` must be an explicit `false` or the starter presets are skipped too. The vendored files are unchanged. Tests: `tests/unit/sillybunny-first-run-defaults.test.js`, `tests/quick-image-gen-first-run.e2e.js` (with the seam disabled, the no-wizard and reset tests fail; without the explicit `false`, the starter-presets test fails).
- **What the app rewrites when a card is saved:** the character editor posts `FormData`, and the browser sends its multi-line text with CRLF line breaks; `charaFormatData` (`src/endpoints/characters.js`) writes an `extensions.depth_prompt` with an empty prompt into every card it saves, and the editor embeds the linked world as `data.character_book` under the world's name. A fingerprint of a card's text must normalise all three, or saving a bundled card without a change makes it look edited. `src/sillybunny-managed-content.js` normalises line breaks, treats an empty depth prompt and a book named after a manifest world as none, and pins literal hashes so the algorithm cannot drift without a failing test (`tests/managed-content-app-roundtrip.test.js` posts real CRLF multipart through `/edit`).
- **Managed bundled content never overwrites what it does not recognise:** reconcile replaces a card, sprite file or world only when its fingerprint is a known earlier release; anything else (a user edit, a malformed or unsafe file) is `modified` and left alone, and only an explicit apply or restore writes it, after a backup that aborts the write when it fails. A world's root `extensions` count, because the app copies them into embedded books. Renaming a managed card moves its file, so it shows as `deleted` and Restore adds a second card (`tests/managed-content-app-roundtrip.test.js`).
- **A bundled card or world that changes before release still needs its old fingerprints in `previousFingerprints`:** testers' servers hold the version they were seeded with, and reconcile replaces a file only when its fingerprint is a listed earlier one, so a manifest rebuilt at version 1 with no history left a tester's older Reisen, Tewi or SillyBunny Lexicon `modified`, and Home showed Reisen framed to the waist beside the current Tewi. Rebuilding the manifest at version 1 with no history was the earlier practice for content that had not shipped. The two assistant cards list their two pre-release versions and the Lexicon its seven pre-release ones (2 to 7 November), newest first, and `tests/unit/sillybunny-shipped-managed-content.test.js` pins them as literals at the end of the list ("stay at the end of the earlier fingerprints, newest first, so an unedited copy of a pre-release card is updated at start", and the Lexicon's twin), because a later rebuild adds fingerprints in front of them. `buildManifest` keeps hand-added history while the file is unchanged, so adding it needs no rebuild and no version bump; status ignores the version. A card that was only used (favourite, tags, a new chat, an editor save without a change) keeps its image bytes and its fingerprint, and a card whose text was edited stays `modified` (`tests/managed-content-app-roundtrip.test.js`, `tests/unit/sillybunny-managed-content.test.js` "brings an untouched card to the bundled version and keeps what the user set on it").
- **Every writer of an image must drop its cached thumbnails, because the thumbnail route never re-checks a cached file:** `GET /thumbnail` (`src/endpoints/thumbnails.js`) serves a cached thumbnail whenever one exists; the "original is newer than the thumbnail" test lives only in `generateThumbnail`, which the route reaches when no cached file exists. Upstream's model is that whoever replaces an image calls `invalidateThumbnail(directories, type, file)`, which removes the desktop and the mobile copy, and `characters.js` does. Managed content wrote cards without it, so after the start-time update, **Update** or **Restore** a tester's Home still showed the old Reisen from the 28,750 B mobile thumbnail (the browser's 304 came from the server's own ETag, so clearing the browser cache changed nothing). `createManagedContent` now takes an `invalidateThumbnail(filename)` hook, calls it once after each card file it writes (never for a world or sprite file, never when nothing was written), and logs a hook that throws without failing the update; the router (`src/endpoints/sillybunny-managed-content.js`) and `seedContentForUser` (`src/endpoints/content-manager.js`) pass it, because that module cannot import `thumbnails.js` (it reads the configuration when it loads). The start also drops the thumbnails of a managed card whose cached copy is older than the card file (`mtimeMs` of the card over `ctimeMs` of the thumbnail, the comparison `generateThumbnail` makes), which repairs the cards that earlier builds replaced. ### Route errors and crashes

- **Breaks:** one request that fails outside its route's error handling ends the server, and the server stays down.
- **Cause:** Express 4 ignores the promise that a route handler or middleware returns, so a rejected async route got no answer and reached the `unhandledRejection` handler in `src/server-main.js`. That handler and the `uncaughtException` handler exited with code 0, which the supervisor passes on as a stop. A throw in a stream, readline or timer callback still reaches `uncaughtException`, because no route is on the stack there.
- **Breaks:** the client's CSRF retry (#475) never runs.
- **Cause:** `fetchWithCsrfRetry()` in `public/scripts/csrf-token-refresh.js` refreshes the token and repeats the request only for a 403 whose body contains `Invalid CSRF token`. Express's default error handler sends only the status text in production, and `server.js` defaults `NODE_ENV` to production, as `Start.bat`, `Start-Node.bat`, `start.sh`, the `Dockerfile` and `docker/docker-compose.yml` set it, so the 403 said only `Forbidden`.
- **Files:** `src/route-errors.js`, `src/server-main.js`, `src/server-supervisor.js`.
- **Guards:**
  - `forwardAsyncRouteErrors()` in `src/route-errors.js` replaces `handle_request()` and `handle_error()` on the Express 4 `Layer` prototype, so a rejected promise from a handler or an error handler goes to `next()`, as the Express 5 router does. It covers every app, router and route made from the server's copy of Express, including the routers that server plugins get. It does not cover a router made from another copy of Express or code that runs outside a route. A falsy rejection reason becomes `Error('Rejected promise')`, because `next()` with a falsy value goes on to the next route. Express 5 does this itself, so the module goes with an upgrade to Express 5.
  - `handleRouteError()` is registered after the not-found handler, before the server listens. Express calls a four-parameter middleware only for errors and skips the not-found handler for them, so both only have to come after every route, plugin routes included. It logs the error as Express's default handler did, and a client disconnect as the same warning as the process handlers. It answers with the error's own 4xx or 5xx status (400 or 413 from the body parser, 403 for a CSRF token) or 500, with only the status text as the body in every `NODE_ENV`; Express's default handler sent the stack trace outside production. It does not answer a response that has started: it destroys the socket of an unfinished one and leaves a finished one alone.
  - The CSRF refusal is the one error answered with its own message. csrf-sync 4.2.1 makes one `invalidCsrfTokenError` per protection object and passes that object to `next()` for every refused request. `src/server-main.js` sets its message and passes it to `answerWithErrorMessage()`, so `handleRouteError()` answers it with 403 and that message as `text/plain`, without the chalk color codes, which `stripVTControlCharacters()` from `node:util` removes under Bun and Node.js. The match is the object itself, not the `EBADCSRFTOKEN` code that other CSRF libraries also use, so another error with that code keeps the status text.
  - The `uncaughtException` and `unhandledRejection` handlers exit with `SERVER_CRASH_EXIT_CODE` (1) after the usual cleanup, or after `SUPERVISOR_FORCE_KILL_TIMEOUT_MS` when a cleanup step fails or does not finish.
  - `runSupervisor()` relaunches a child that reported startup (`SERVER_STARTUP_READY_MESSAGE`) and then exits with a non-zero code or a signal while no stop was requested. It waits `SUPERVISOR_CRASH_RESTART_DELAY_MS` (1 s), doubled for each crash restart within `SUPERVISOR_CRASH_WINDOW_MS` (10 minutes), and a crash after `SUPERVISOR_CRASH_RESTART_LIMIT` (5) such restarts ends the supervisor with the child's exit code. A stop request ends the wait at once. A failure before startup, exit code 0, the restart, plugin update and supervisor reload codes and a requested stop behave as before. The launchers loop only on exit code 75, and Docker's `restart: unless-stopped` restarts on any exit, so they need no change.
- **Limit:** a crash restart loses what the server process holds in memory, such as session-auth sessions and server-side generations that were running.
- **Tests:** `tests/route-errors.test.js`, `tests/server-supervisor-crash-restart.test.js`, `tests/csrf-refusal-retry.test.js` (the csrf-sync setup of `src/server-main.js` with a colored message, and `fetchWithCsrfRetry()` against its real answers).
- **Fixes:** `ae27417cc` (async route errors), `120fa5fbf` (crash restarts), `a41adfe62` (crash exit code), `b0735ddab` (CSRF refusal text).

### Character import and upload files

- **Breaks:** data in an imported card or archive, in an uploaded sprite or sprite pack, or in a create request decides which folder the server writes to, which file type it stores, or how long the card parser runs.
- **Cause:** the import and upload code takes names, extensions and chunk lengths from the data it receives. A name that sanitizes to nothing makes the parent folder the target folder, an archive or uploaded file keeps its own extension, `sanitize-filename` keeps only the first 255 bytes of a name and so can cut off an extension at its end, and `png-chunks-extract` allocates, copies and checksums the length that a chunk declares before it finds that the file is shorter.
- **Files:** `src/endpoints/characters.js`, `src/endpoints/sprites.js`, `src/image-file-type.js`, `src/character-card-parser.js`, `src/png/extract.js`, `src/charx.js`, `src/byaf.js`.
- **Guards:**
  - `getCardAssetFolder()` in `src/endpoints/characters.js` names the asset folder of a CHARX or BYAF card after the sanitized card name, or after the card's file name when the name sanitizes to nothing. A CHARX import skips its assets when that name is not a folder directly inside the characters and user images folders. A preserved name such as `...png` gives that on POSIX systems, where `getPreservedName()` does not sanitize.
  - `isImageFile()` in `src/image-file-type.js` accepts a file only when its extension is png, apng, jpg, jpeg, jfif, gif, webp, avif or bmp and its leading bytes are an image of that type. A BYAF import stores a background or an alternate icon, and a CHARX import an asset, only when it passes; `isArchiveImage()` in `characters.js` logs the others. The stored bytes are the archive's bytes. A BYAF chat names only the backgrounds that were stored.
  - `POST /api/sprites/upload-zip` stores a pack entry only when its sanitized name passes `isImageFile()`. `POST /api/sprites/upload` keeps the uploaded extension when that passes, takes the extension of the image type that the bytes are (`getImageExtension()`) when it does not, and answers 400 when the sanitized name still fails, before it replaces an existing sprite. A sprite uploaded from a URL arrives as `image.png` whatever its type, so a wrong image extension is replaced and not refused. `readImageSignature()` reads only the leading bytes of the upload.
  - `POST /api/characters/import` takes the import function only when `Object.hasOwn(formatImportFunctions, format)`, so every other file type gets the unsupported format answer.
  - `POST /api/characters/create` answers 400 to a `file_name` that sanitizes to nothing, such as `.` or `..`, because the same name also names the card's chats folder.
  - `src/png/extract.js` walks the chunk headers up to IEND before `png-chunks-extract` runs, and throws `PNG chunk at byte <n> runs past the end of the file` when a chunk header or the data length it declares does not fit in the file. `read()` and `write()` in `src/character-card-parser.js` use it. ### Macro whitespace

- **Breaks:** a trim in the macro engine removes whitespace that a template asks for with `{{newline}}`, `{{space}}` or `{{noop}}` (SillyTavern/SillyTavern#5673 and SillyTavern/SillyTavern#5674).

The legacy `{{trim}}` post-processor runs after `{{noop}}` is already an empty string, so `{{noop}}` does not stop it as it did in the legacy engine (`public/scripts/macros.js`).

- **Guards:** `public/scripts/macros/sillybunny-whitespace-markers.js`. The walker wraps `{{newline}}` and `{{space}}` output in U+FDD0 and `{{noop}}` output in U+FDD1, and removes them after each trim. `MacroEngine.evaluate()` removes them before it returns, except for the `{{if}}` branch, which `resolve(text, { keepWhitespaceMarkers: true })` returns with markers for the trim in the `{{if}}` handler. Only the `core:` post-processors see the markers.

### Client addresses behind proxies

- **Breaks:** the whitelist, a rate limit or `requireHttps` decides on a forwarded value that no trusted proxy set.
- **Cause:** a reverse proxy adds the address it received the request from at the right end of `X-Forwarded-For`, and it can pass the other forwarded headers on from the client unchanged. The server cannot tell which headers its proxy set.
- **Files:** `src/express-common.js`, `src/middleware/whitelist.js`, `src/middleware/requireHttps.js`, `src/middleware/basicAuth.js`, `src/middleware/hostWhitelist.js`.
- **Guards:**
  - The trusted hops are the valid entries of the `whitelist` setting (`getTrustedProxies()` in `src/express-common.js`). `whitelist.txt` and the Docker host addresses do not count. `getForwardedIps()` returns the address in each enabled forwarded header and reads `X-Forwarded-For` from the right: it skips trusted hops, and the first other entry is the client.
  - With `enableForwardedWhitelist` on, the whitelist blocks a request unless every address that `getForwardedIps()` returns is listed, and it names the first unlisted one.
  - `getIpAddress()` adds a forwarded address only when the socket address is a trusted hop and every enabled header names the same valid address. Otherwise it returns the socket address. The basic auth, account login, account recovery, password reset and conversation message limiters and the access log read their address through it.
  - `isIpInPatterns()` parses addresses strictly and treats a value that is not an IP address as unlisted, so a malformed forwarded value or a socket without an address gets 403, not 500. An IPv4-mapped value matches its IPv4 entry.
  - `requireHttps` lets plain HTTP through only from a loopback socket address without forwarding headers, whatever the `Host` header says. It reads the first `X-Forwarded-Proto` value, and only from a trusted hop.
  - Basic auth matches no request when the configured username or password is empty or is not a string, and it compares the configured user with `crypto.timingSafeEqual()` over SHA-256 digests.
  - `hostWhitelist.enabled` goes through the `'boolean'` converter, so `SILLYTAVERN_HOSTWHITELIST_ENABLED=false` turns the host check off.
- **Tests:** `tests/forwarded-client-address.test.js`, `tests/require-https-client-address.test.js`, `tests/basic-auth-configured-credentials.test.js`, `tests/host-whitelist-enabled-switch.test.js`, `tests/middleware-whitelist.test.js`, `tests/middleware-host-whitelist.test.js`, `tests/middleware-basic-auth.test.js`, `tests/middleware-require-https.test.js`.
- **Fixes:** `1b127a865` (whitelist), `06dc7a6e0` (rate-limit keys), `e059e5d23` (`requireHttps`), `0a836ed40` (basic auth credentials), `30ecce06d` (host whitelist switch).

### Slash commands and STscript

- **Breaks:** the STscript parser reads a script differently from how it is written. A closing mark, a pipe or an escaped character is skipped or taken twice, so a command ends up in another command's value, a value gains text such as `undefined` or `[Closure]`, or the parser throws a `TypeError` instead of a parser error.
- **Cause:** the parser moves one index through the text. Branches that return from a nested parse (a nested block comment, the quoted rest of a split-count command, an unclosed quote in lenient parsing) took one more character. Positions were counted back from an index that had already moved past whitespace or a closing quote. The split branches lost an escaped first character, because the parser took it before it started to split.
- **Files:** `public/scripts/slash-commands/SlashCommandParser.js`, `public/scripts/slash-commands/SlashCommandParserError.js`.
- **Guards:** every `SlashCommandParserError` carries the text and the index. The error handler of `executeSlashCommandsWithOptions()` reads its line, column and hint, and without them it throws a `TypeError` instead of showing the parser error.
- **Tests:** `tests/frontend/StscriptParserFixes.e2e.js` (one test or more for each fix, through `tests/frontend/stscript-parser-harness.js`).
- **Limit:** macro positions are still counted back from the end of a value, so a macro is indexed one character late for each escape that follows it in the value. With `REPLACE_GETVAR`, the macro index describes the replaced text, not the source.
- **Open:** `SlashCommandExecutionError.hint` slices its source as the parser error did, so an execution error on a line that another line follows shows the line without its last character (`/let x 1 | /let x 2` followed by a new line shows `/let x `).
- **Fixes:** `15b28ab1b` (nested block comments), `cebf47278` (`/let` with an empty `key=`), `627eb8cc8` (split argument error without text), `aa6f61ce1` (escaped first split value), `b420e832d` (`/parser-flag` without a name), `996ce24cf` (quote flags for closures), `f3e74ca1d` (quoted split-count rest), `87bd300e0` (closure in a joined rest), `cfc4fcf73` (macro positions in quoted values), `5e17bdc22` (unclosed quote in lenient parsing), `039e44a8e` (unknown command position), `643ad824a` (error hint line).
